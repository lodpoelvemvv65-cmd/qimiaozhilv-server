## 1. ★ 最重要的两条限制（不先看会白抓）

### 1.1 `pktmon` 抓不到**任何本机自连**（不只是回环 127.0.0.1）

`tools/capture_traffic.ps1` 的文件头注释就写着，历史记录也印证：

```
_work/pcap_run_20260918.txt
  local-activity-hurt-20260827-123024.pcapng   包=64   帧=0     ← 0 帧
  local-boss-hurt-20260827-v2.pcapng           包=0    帧=0     ← 0 帧
  local-title-basic-attack-20260820.pcapng     包=0    帧=0     ← 0 帧
  online-*.pcapng（101.43.6.155）             包=4886 帧=462   ← 有帧
```

**2026-09-18 在本机（Win10 19045，本机 IP `192.168.x.x`、TAP 地址 `10.x.x.x`）实测三次，结论比"抓不到回环"更强：**

| 试验 | 做法 | 结果 |
|------|------|------|
| ① 回环 + 按组件 | 筛选器 `-i 127.0.0.1 -t TCP`，`--comp nics` | 真跑了 5 次回环收发，**抓到 0 包** |
| ② 回环 + 全组件 | 同上但不写 `--comp`（默认 all） | 仍然 **0 包**（排除"组件选错"） |
| ③ 本机自己的 LAN / TAP 地址 | 连 `192.168.x.x:7757`、`10.x.x.x:7757`（服务端 bind 0.0.0.0） | 各 **0 包** |

**⇒ Windows 把"自己发给自己"的流量整个绕开了 pktmon 能挂的组件，改地址也绕不过去。
本地服的流量在本机根本抓不到，只能抓远程服**（`101.43.6.155`）。
要在本地服上验证协议，只能用 `server-mysql/test/` 里连 `127.0.0.1` 的实测脚本，或在服务端插探针。

### 1.2 目标 IP 必须与客户端实际连接的地址一致

`pktmon` 的筛选器是**按 IP** 过滤的（默认**不限端口**，因为登录网关与游戏服端口不同）。
抓之前先确认客户端连的是哪个 IP —— 原版客户端的地址在
`梦幻奇遇记_Data/resources.assets` 里的 `GlobalProto`：

```json
{ "_t":"GlobalProto",
  "AssetBundleServerUrl":"http://101.43.6.155:2083/",
  "Address":"101.43.6.155:7756",
  "LocalAddress":"127.0.0.1:7756", "isLocal":false, "ClientVersion":"2.5" }
```

> 客户端配的端口是 **7756**，但实际游戏流量走 **7757/7758**（登录后重定向）
> ⇒ **筛选器千万不要限端口**。
>
> ⚠ **注意**：现有两份线上抓包里**一个 7756 的包都没有**，而且都**不含 SYN**（包从会话中途开始），
> 所以"登录走 7756、之后重定向到 7757/7758"这件事**目前是推断、不是抓包实证**。
> 要坐实它，必须**从客户端启动前就开始抓**（筛选器按 IP、不限端口），把登录那一段也录进去。

## 2. 抓包三步（全部用 Bash 调 `pktmon`）

> ⚠ **必须用 Bash 调 `pktmon`**。经实测：通过 PowerShell 工具调用时它**无输出、无退出码、不生成 ETL**，
> 完全没生效。另外本环境的 PowerShell 工具**不回显 stdout**，要写文件再读。

```bash
# ① 清掉旧筛选器 + 加筛选器（按 IP，不限端口）
/c/Windows/System32/pktmon.exe filter remove
/c/Windows/System32/pktmon.exe filter add MHQCapture -i 101.43.6.155 -t TCP
/c/Windows/System32/pktmon.exe filter list          # 确认筛选器在

# ② 开始抓（--pkt-size 0 = 整包；--file-size 是循环覆盖上限 MB）
/c/Windows/System32/pktmon.exe start --capture --comp nics --pkt-size 0 \
  --file-size 2048 --file-name "C:\\Users\\Administrator\\AppData\\Local\\Temp\\mhq_capture.etl"

# ③ 打完之后停
/c/Windows/System32/pktmon.exe stop
/c/Windows/System32/pktmon.exe status               # 看「丢失的事件」应为 0
```

**转换 + 归档**（`--out` 必须给 **Windows 绝对路径**，给 `/tmp/x.pcapng` 会落到 `C:\tmp\`）：

```bash
cd "./参考数据/抓包归档"
/c/Windows/System32/pktmon.exe etl2pcap \
  "C:\\Users\\Administrator\\AppData\\Local\\Temp\\mhq_capture.etl" \
  --out "D:\\代码\\项目包-不含构建缓存\\参考数据\\抓包归档\\online-<标签>-<日期>.pcapng"
cp "/c/Users/Administrator/AppData/Local/Temp/mhq_capture.etl" "online-<标签>-<日期>.etl"
```

**解帧**（入参也要给 **Windows 路径**，MSYS 的 `/c/...` 会报 `missing`）：

```bash
cd "."
python tools/_pcap_frames.py \
  "./参考数据/抓包归档/online-<标签>-<日期>.pcapng"
# 产出：_work/pcap_frames/<同名>.jsonl 与 .stat.txt
```

**帧格式**：`[u16 LE 总长度][u16 LE opcode][protobuf body]`。

## 5. 解包时必踩的 9 个坑（都踩过；其中第 7 条是**误判，已作废**）

| # | 坑 | 解法 |
|---|----|------|
| 1 | **5 开时同一广播在多条流上各出现一次** | 先按 `stream` 去重，或只取一条流。**但注意每流另有 289 帧是私有的**（§3.1 第 3 条），要按 opcode 判断是不是广播 |
| 2 | **玩家会陆续阵亡**，不按存活期过滤会把「阵亡」误读成「抗性差异」 | 用 `20083`（`M2C_UnitDead`）取阵亡时刻，按 `[0, death)` 过滤 |
| 3 | **`20078` 的伤害是 uint64 编码的负数**（`18446744073709551117` = −499） | `v - 2**64 if v >= 2**63` |
| 4 | **jsonl 里浮点是字符串** `"<f32 489eb34a>"`；`<8B ...>`/`<4B ...>` 是**字节数前缀** | 自己解：`struct.unpack('<f', bytes.fromhex(h))` |
| 5 | **`20170` 是打包下发**（`[2]` 是 `<8B ...>` 列表，每个 = `08<varint numericType>15<float>`），**而且 `20169`（单推）同时也在用** | 两路都要解：`20170` 逐 blob 解 protobuf；`20169` 是普通三元组 `{1:UnitId, 2:NumericType, 3:float}` |
| 6 | **怪物技能目标是 `SelectMultiTarget` 随机子集**，不是全体 ⇒「施法次数」不能直接当分母 | 用伤害帧反推本次实际打到谁 |
