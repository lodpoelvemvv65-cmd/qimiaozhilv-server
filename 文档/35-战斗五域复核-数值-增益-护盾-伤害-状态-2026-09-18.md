### 2.2 ★ F1：Refresh 语义（F1a/F1b 已证实正确，F1c「不恢复盾池」仍存疑）

`battle_effects.go` `addPersistentEffect` 的三条分支对护盾（`kind=3`）的处理：

```go
case CombatEffectRefresh:                      // ← attribute=8 走这里
    existing.modifierID = spec.ModifierID
    existing.modifierTag = spec.ModifierTag
    existing.value = spec.Value               // 只改 value
    existing.percent = spec.Percent
    if existing.kind == DoT || existing.kind == HoT {
        existing.overlayValue = clampEffectAmount(int64(spec.Value) * int64(existing.stacks))
    }
    existing.criticalChance = spec.CriticalChance
    existing.criticalMultiplier = spec.CriticalMultiplier
    existing.expiresAt = expiry(now, spec.Duration)   // 只续时长
    // ← 没有任何 existing.shield = ... 的赋值
case CombatEffectStack:                        // ← attribute=4/12 走这里
    ...
    case CombatEffectShield:
        existing.shield += int64(spec.Value)   // 累加
default:                                       // Replace
    r.detachEffect(existing)                   // 删掉重建 → 池恢复
```

**护盾唯一有意义的字段是 `shield`，而 Refresh 分支不碰它** → 对护盾来说，
`attribute=8` 的「刷新」退化成「只延长持续时间」，被消耗掉的额度**不会补回**。

**实测证据（临时探针单元测试）**

```
施加后 totalShield=808112
被 662634 打一次后 totalShield=145478
再次施加（Refresh）后 totalShield=145478   ← 不恢复
Replace 分支：再次施加后 totalShield=808112（恢复）
Stack 分支：再次施加后 totalShield=953590（145478+808112 累加）
```

**线上证据（临时探针日志）**

```
[probe.shield] CREATE target=1:2 key=modifier:10000113:shield kind=3 mode=1 value=19740501 duration=10s
[probe.shield] APPLY-EXISTING target=1:2 key=modifier:10000113:shield kind=3 mode=1 \
    old_value=19740501 old_shield=19019992 new_value=19740501
```

→ 盾已被消耗 720,509，Refresh 时 `value` 被写回 19,740,501 而 `shield` 停在 19,019,992，
两者从此不一致（`value` 对护盾无消费方，所以表现为「额度不补」）。

**先说已经证实为「正确」的两部分（2026-09-18 补充）**

翻遍全部线上抓包（`online-*.jsonl`），对**每一个 buff** 按「单位 + icon + 持续」聚合，
统计同一单位的相邻两次施加间隔，与它自己的 `Time`（field 7）比较：

```
相邻间隔总数 727  |  间隔 < 自身持续 的个数 162
```

其中 `bufficon_dfeAdd`（增加防御力，`Time=14000` = 14s）在同一单位上**每 5 秒重施一次**：

```
unit 27225: 145.07 → 150.08 (5.01s)  220.91 → 225.91 (5.0s)  258.80 → 263.80 (5.0s)
unit 27204: 130.47 → 143.36 (12.89s) 160.25 → 165.27 (5.02s) 181.31 → 186.32 (5.01s) ...
```

而 `bufficon_dfeAdd` 对应的 modifier **全部是 `attribute=8`**（11010111 / 11020112 / 11020211 /
11030113 / 11030316 / 11030412 / 11040113 / 11050111 / 11050311 / 11060113 / 11060213 /
11060413 / 12010119 / 12020116 / 31030411 / 31040412 / 31050112 / 41030412 / 41060412 / 42020117 …，
共 30 个，无一例外）。

**由此得到两条硬结论：**

- **F1a ✓ 线上允许 `attribute=8` 的 buff 在未过期时重复施加，并且每次把持续时间重置为满**
  （每次 20080 的 `Time` 都是 14000，不是剩余值）。
  → 服务端 `existing.expiresAt = expiry(now, spec.Duration)` **是对的**。
- **F1b ✓ 线上每次重施都发一条新的 20080 Add**（`Id` 每次都是新的）。
  → 服务端在 `CombatEventEffectRefreshed` 上也发 `ChangeType_Add`
  （`battle_skill_events.go:121`）**是对的**。

**剩下真正未决的只有「池要不要补满」（F1c）**

线上抓包里**护盾从来没有在未过期时被重复施加过**：

| 抓包 | 护盾帧 | 同一单位相邻间隔 | 结论 |
|------|--------|------------------|------|
| `online-skill-effects-20260906`（5 人） | 54 帧 / 15 单位 | 39 个间隔，**最小 11.32s** | 全部 > 10s 持续 |
| `online-battle-effect-exit-20260913`（单人军官 27502） | 3 帧 / 1 单位 | **20.54s、20.48s** | 全部 > 10s 持续 |

**单人抓包的细节值得记一笔**：27502 的 100001 施法在 75.10 / 81.10 / 96.64 / 102.64 / 117.13 / 123.13，
护盾落在 78.10 / 98.64 / 119.12。**护盾在场时的 3 次施法（81.10、102.64、123.13）一次 20080 都没发**，
不在场时的 3 次施法全部发出 —— 完美交替。若纯按 66% 独立掷骰，出现这个模式的概率
= 0.66³ × 0.34³ ≈ **1.1%**。

这**弱**提示线上可能在「同 modifier 已在场时直接跳过施加」（第三种语义：Ignore），
但同一份数据里 `attribute=8` 的 `bufficon_dfeAdd` 又确实在持续内反复施加，
两者矛盾 → **更可能是 66% 掷骰的偶然**，样本太小（n=6），不足以定案。

**要定案需要**：一段「同一单位在 10s 内被重复挂盾」的线上抓包。目前所有抓包都不含这个场景。

**影响面**：`attribute=8` 的 modifier 共 270 个，但只有护盾（`kind=3`）会因「池不恢复」而被观察到；
属性类 buff 走 `EffectivePercentAttribute`，`value` 一改就生效，不受影响。
（顺带核实：客户端元数据里**没有** `overlayType` / `valueK` / `stateK` / `continueTime` 这些字段名，
`SkillLogicConfig` 是通用结构解析的 → **客户端 IL 无法判定 `attribute` 的位掩码语义**，
这套「bit2=可叠加 / bit3=可刷新」是服务端侧的推断，没有客户端证据。）

**临时缓解**：把 10000113 的 `attribute` 从 8 改成 4（Stack，会累加）或 0（Replace，会重建），
即可得到「补满」语义。**但这会改变行为，需先确认线上语义再动手。**

### 2.3 多盾吸收顺序

```go
func (r *CombatRuntime) shieldsFor(ref) []*activeCombatEffect {
    ...
    sort.SliceStable(shields, func(i, j int) bool { return shields[i].id < shields[j].id })
}
```

→ **先挂的盾先被扣**（`effect.id` 升序）。探针实测：两个盾 totalShield=80，
吸收帧 `key=shield-A absorbed=30 / key=shield-B absorbed=10` ✓

盾被打空时立即 `removeEffect(..., "depleted")`，下一次施加会走 CREATE 分支拿到满额池 ——
**所以护盾只会在「被彻底打空」之后才补满，而不是每次重新施加都补满。**

### 2.4 ★ F3：客户端护盾条恒为 0（非偏差）

- `HotfixView` TypeDef 19 `HudCharacter.RefreshHp` 是 `SetHpAndShield` 的**唯一调用方**，IL 里把护盾参数写死 `ldc.r4 0.0`。
- 服务端 `CombatUnitSnapshot.Shield`（`battle_effects.go:439`）计算了但**从未被任何非测试代码读取**。
- 线上 20080 护盾帧：`{"3": "bufficon_shield", "4": "护盾，可以减少一定伤害", "6": 1, "7": 10000, "8": 1}` ——
  **没有任何数值字段**，客户端只能知道「有个 10 秒的护盾」。

**结论**：原版客户端同样没有护盾数值条，服务端不下发护盾值是**正确的**，不需要补协议。

## 3. 数值域（数值问题）

### 3.1 ★ F2：护盾量 = 55% maxHP 的完整溯源（结论：非 bug）

线上探针：

```
[probe.treat] source=1:2 target=1:2 selfStat=physical_attack selfPct=0 \
    targetStat=max_hp targetPct=5 rawAmount=1.7945902e+06 base=1794591 auxRaw=7049.061775455475
[probe.treat] auxClamped=1000 result=19740501
```

算术闭合：`maxHP 35,891,804 × 5% = 1,794,591`，`1,794,591 × 11 = 19,740,501` ✓
（×11 = `1 + min(1000, 7049.06)/100`，被 `battle_treatment.go:19` 的 `math.Min(1000, ...)` 夹住）

**`auxRaw = 7049.06` 从哪来？**

```
playerExtraNumeric(1017) = 70.4906
  = directNumericBonus(1017) + characterGrowthValue(19)
  = (装备 + 星魂 + 转生 + 宠物) + Str × 0.0002
basePointAttribute() 对 1013..1023 统一 ×100（ratioNumericType）→ 70.4906 × 100 = 7049.06
```

**量纲核实（关键）**：`CharacterGrowth` 行 191（attributeType 19 → NumericType 1017，
职业族 1）在原版表里就是 `{"Str": 0.0002, "Wim": 0}`，与线上抓包面板完全吻合：

| 等级 | 原版面板 1017 | 推算 Str | Str × 0.0002 |
|------|---------------|----------|--------------|
| Lv1  | 0.0002 | 1 | 0.0002 ✓ |
| Lv56 | 0.0012 | 6 | 0.0012 ✓ |
| Lv67 | 0.0014 | 7 | 0.0014 ✓ |
| Lv74 | 0.0016 | 8 | 0.0016 ✓ |

> 顺带核实：`SkillConfig` 3202010x 的 `Desc = "1：辅助值增加20%。" Args0 = 20`，
> 说明 1017 的原始量纲是**小数比率**（0.20 = 20%），`×100` 转成百分点是**对的**。

**uid 2 是 GM 号**：`players.str_add = 302,002`，`level = 215,001`，`trans = 3`。
`naturalPrimaryStat = ceil((215001 − 21500)/10) = 19,351` → `Str ≈ 321,353 + 装备`。
`辅助值 = 321,353 × 0.0002 ≈ 64.3`（+ 装备/星魂 ≈ 70.49）。

**结论**：正常号（Str 8~500）的辅助值只有 0.0016~0.1，`1 + aux/100` = ×1.0016~×1.1，
护盾量正常。**×11 完全来自 GM 号被灌爆的力量，不是公式错误。**
（`treatmentAmount` 的 clamp `[-100, 1000]` 是服务端自己的护栏，线上是否有此上限未知。）

## 4. 伤害域（伤害问题）

### 4.1 公式链路（`battle_skill_runtime.go:1203`）

```
if Self.Percent != 0:
    base = formulaBase(Self.Stat, source)
    if (Stat ∈ {物攻, 魔攻}) and (Type ∈ {物理, 法术}):
        base -= EffectiveAttribute(target, 物防 or 魔防); if base < 1 → base = 1
    amount += base × Self.Percent / 100
if Target.Percent != 0:
    amount += formulaBase(Target.Stat, target) × Target.Percent / 100     # 不扣防
if Limited and Limit.Percent > 0:  amount = min(amount, 上限)
amount *= DamageMultiplier(source) × ctx.damageMultiplier
if Type == 物理:  amount *= 1 + min(1000, numeric(1045))/100
if Type == 法术:  amount *= 1 + min(1000, numeric(1046))/100
if Type != 真实:
    reduction = 全局免伤 + 对应物理/精神免伤，夹到 [-1000, 100]
    amount *= 1 − reduction/100
if CanCrit and amount > 0:
    chance = (暴击率 + 对应物理/精神暴击率) − 目标抗性侧
    critValue = (暴击效果 + 对应物理/精神暴击值) − 目标抗性侧
    critical = roll()*100 < clamp(chance, 0, 100)
    if critical: amount *= clamp(1.5 + critValue/100, 1, 10)
return ceil(amount), critical
```

**自洽性检查**

- 真实伤害（`Type == 真实`）：不扣防、不吃 1045/1046 增伤、不吃免伤 ✓
  （18 个 DoT 节点里 17 个是 `type: true`，500023 是 `spiritual`）
- `plan.Target.Percent` 分支不扣防 —— 符合「按目标最大生命值百分比」的语义 ✓
- 百分比先乘、减伤后乘，顺序与 doc 34 §2 记录一致 ✓

### 4.2 反伤 / 反击无递归

```go
if actual > 0 && !request.Periodic && !request.Reflected {
    ... lifesteal ...
    if reflectPercent > 0 && r.unitAlive(request.Source) {
        reflected := percentAmount(actual, reflectPercent)
        r.applyDamageInternal(CombatDamageRequest{... Reflected: true}, at)
    }
    if !targetDied && !request.Counter { counterAttackReaction(...) }
}
```

`!request.Reflected` 与 `!request.Counter` 两道闸把递归堵死；周期伤害也不能吸血/反伤 ✓

### 4.4 ★ F9：`percentAmount` 的隐患

```go
func percentAmount(amount int64, percent float64) int32 {
    raw := math.Ceil(float64(amount) * percent / 100)
    if math.IsNaN(raw) || raw <= 0 {
        return 1            // ← amount=0 或 percent=0 也返回 1
    }
    ...
}
```

`percentAmount(0, 100)` 会返回 **1** 而不是 0。当前 4 个调用点都有 `> 0` 前置守卫
（`actual > 0`、`triggerAmount > 0`、`reflectPercent > 0`），**未被触发**；
但这是一个只要有人新加调用点就会踩的坑。建议把 `raw <= 0` 拆成
`raw <= 0 && percent > 0 && amount > 0` 才返回 1，否则返回 0。

### 5.3 ★ F8：`overlayBucket` 与线上实例化的分歧

服务端把同 `overlayType` + 同 `stateK` 的周期效果合并到一个 key

**判定：设计分歧，不是明确 bug。** 服务端的理由（避免客户端看不见的重复 DoT）

要定案需要看客户端 `BuffComponent` 的显示层是否按 `StateType` 去重 —— 目前没有反汇编证据。

## 8. 复核结论

本轮对五个域的复核，**没有发现「公式写错」这一类的硬 bug**。
上一轮一度怀疑的「护盾量 55% 异常放大」经溯源确认是 **GM 号 `str_add=302,002` 灌爆力量**
导致的辅助值溢出，公式与原版表量纲完全吻合（`CharacterGrowth` 行 191 = `{"Str": 0.0002}`）。

**唯一值得跟进的实质问题是 F1c**：`CombatEffectRefresh` 分支对护盾不恢复盾池，
而全部 5 个玩家护盾 modifier 的 `attribute` 都是 8。它的**可观察后果**是
「军官 66% 几率的 5% 护盾只有在被彻底打空之后才会补满，中途重新施加只延长持续时间」，
即护盾的实际收益低于「每次施加都补满」的预期。

F1 的另外两半在本轮已经**证实为正确**（见 §2.2）：
持续时间重置为满 ✓、Refresh 补发 20080 Add ✓ —— 这两条都有线上抓包实证。

剩下的 F1c（池要不要补满）**在所有线上抓包里都不出现**：
5 人抓包护盾相邻间隔最小 11.32s、单人抓包 20.5s，全部大于 10s 持续。
单人抓包里「护盾在场时的 3 次施法都没发 20080」这个完美交替（p≈1.1%）值得记一笔，
但样本太小，且与同抓包内 `attribute=8` 的 `bufficon_dfeAdd` 每 5s 重施一次的事实相矛盾，
**不能据此推断出第三种「Ignore」语义**。

**在拿到 U1 的证据之前，不建议改动行为。** 如果确实要改，把 10000113 的 `attribute`
从 8 改成 4（Stack，累加）或 0（Replace，重建）即可，且必须单独提交。

其余 F3~F8 均为「已核实无误」或「已排除」或「设计取舍」，按现状保留即可，F9 建议顺手加固。

**F10 例外**：2026-09-18 线上抓包实测证实「DoT 3.5s / HOT 4.0s 不同频」，
我们一个全局 4000ms 对 DoT 是错的 —— **但补齐 §4.5.1 两条证据前不要改**，
且改动必须单独提交（会连带改 `battle_periodic_tick_test.go` 的断言）。
