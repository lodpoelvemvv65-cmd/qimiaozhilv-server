## 3. 客户端处理链路（Handler / UI 反汇编 IL 关键点）

### 3.1 普通商店 ShopUI（HotfixView 623）

- `Awake`：`zoneScene = ZoneScene()`；`ui = GetParent<FUI_ShopUI>()`；`AwakeAsync().Coroutine()`。
- `AwakeAsync`：`m_pageList.selectedIndex = 0` → `ShowItems()`；`m_pageList.onClickItem → ShowItems(选中页)`；`m_slotList.onDrop → SellItem`（从背包拖到商店）。
- `ShowItems`：遍历本地数据表 `ZoneScene().GetShopBase()`（即 ShopBase 全部行），`AddItemFromPool` 生成格子，`icon = UIPackage.GetItemURL(BagHelper.GetIconName(shopBase.ItemId))`；`onRollOver → 提示(GetAdditionalPrice(ItemId, 1.0))`（价格倍率 1.0）；购买只响应双击：普通双击直接 `Count=1`，按住 Ctrl 双击才弹数量 Tip（`Int32.TryParse(m_IptTxt.text)` → count）→ `SendBuyProto(count)`。
- **`<ShowItems>g__SendBuyProto|3.MoveNext`**（购买核心）：
  ```
  zoneScene.GetComponent<SessionComponent>()
  new C2M_BuyInShop { PageIndex = ui.m_pageList.selectedIndex,
                      SlotIndex = temp,          // 该商店条目在页内的序号
                      Count     = count }
  → SessionComponentSystem.Call<M2C_BuyInShop>()
  → 响应: if (!StringUtil.IsNullOrEmpty(resp.Message)) OpenUI(错误 Tip)
         Game.EventSystem.Publish_Sync<UpdateBagUI>(new UpdateBagUI { list = resp.BagMapList })
  ```
- `SellItem`（拖拽卖出）：`context.data as UIDragArgs`（`uiType`/`index`）→ `bagIndex = index`；`inputEvent.ctrl` 直接 `SendPutProto`；否则弹 Tip 输入数量 → `SendPutProto(bagIndex, count)`。
- **`<SendPutProto>d__6.MoveNext`**（卖出核心）：
  ```
  new C2M_SellItem { SlotIndex = bagIndex, Count = count }
  → Call<M2C_SellItem>()
  → 响应: Message 非空 → OpenUI(错误 Tip)；否则 Publish_Sync<UpdateBagUI>(list = resp.BagMapList)
  ```

### 3.2 元宝市场 MarketUI（HotfixView 619）

- `Awake`：同 ShopUI 模式（GetParent<FUI_MarketUI> → AwakeAsync）。
- **`<AwakeAsync>d__3.MoveNext`**（首次拉取）：

- `ShowItems`：遍历 `marketRet.MarketIdList` → `Get<Cal.DataTable.MarketBase>(id)`；只渲染 `marketBase.Page == m_pageList.selectedIndex` 的条目；`onRollOver → GetAdditionalPrice(ItemId, marketRet.Discount, marketType)`；`onClick → <AwakeAsync>b__5`：`if (marketBase.OnlyYuanBao && marketType != YuanBaoMarket) → OpenUI("该物品只能用元宝购买")`；Ctrl 直接买，否则弹数量 Tip。
- **`<AwakeAsync>g__SendBuyProto|7`**：

- `m_slotList.onDrop → <AwakeAsync>b__2`：把背包物品拖入市场（`SendPutProto(zoneScene, index)`，复用 `C2M_SellItem` 卖入市场）。
- 客户端价格展示（`TabHelper.GetAdditionalPrice(MarketBase, discount, marketType)`）：原价 `Price_YuanBao`、折后 `RoundToInt(Price_YuanBao × discount)`、兑换券市场另显 `RoundToInt(Price_YuanBao × 2.0)`、`OnlyYuanBao` 商品只显元宝价；ShopBase 用 `GetCoinFormat(Price)` 显示金/银/铜。

- 扩容：先 `new C2M_QueryExtandPrice()` → `Call<M2C_QueryExtandPrice>` → 弹确认（显示响应 `Coin`/`Voucher`）→ `new C2M_ExtandStore()` → `Call<M2C_ExtandStore>`。
- 钱数显示：`m_txtGold/m_txtSliver/m_txtCoin = GetCoinFormat(...)`（10000 铜=1 金、100 铜=1 银）。
- 分页与索引：`ShowSlot` 明确用 `currPage * 60` 计算页首，循环范围为 60 格；构造器把 `totalPage` 初始化为 2。仓库全局 `Index` 为 0 基：第 1 页 `0..59`，第 2 页 `60..119`。搜索结果同样以 `Index/60+1`、`Index%60+1` 显示页号和格号。
- 搜索：`m_btnSearch` 只遍历 `ClientItemDataComponent.StoreItemDic`，按物品名做本地 `Contains`，最多列出约 30 条；不发送任何协议。
- 扩容刷新：`M2C_ExtandStore` 是空响应，成功回调没有修改 `totalPage`；页数在下一次 `C2M_GetStore` 返回 `Total` 时刷新，这是当前客户端自身行为。

#### 3.5.1 数量交互结论

数量由客户端操作路径决定，并非服务端随机行为：

- 普通商店：普通双击直接购买 1 个；按住 Ctrl 双击弹数量输入框。单击只用于选中/查看，不购买。
- 元宝市场和其他商店以各自反汇编分支为准；出现“有时直接 1、有时弹数量”是客户端不同 UI 路径，不是服务端随机。
- 多商店：点击商品弹数量 Tip，确认后把输入值写入 `C2M_BuyInMultiShop.Count`。
- 普通商店卖出：普通拖拽弹数量 Tip；Ctrl 拖拽直接卖出 1 个。
- 仓库存入/取出：`C2M_PutInStore.Count` / `C2M_TakeOffStore.Count` 是正式字段。普通双击/拖入走单个模式
  `Count=1`；按住 Ctrl 操作走数量输入分支，弹出“请输入您要存储/取出的数量”。服务端已接受并原子处理
  `Count>1`，例如一次存入 50、取出 17；若客户端只发 1，服务端不能自行猜成整组。

服务端实现：严格按客户端使用每页 60 格、默认 2 页（120 格）、0 基索引；存入、取出和排序都限制在请求 `Page`。旧的“40 格/页、1 基索引”存档会一次性换算页数并把格子左移，不丢物品。扩容一次增加一页，当前自建服查询并扣 100000 铜币、上限 10 页；**价格和上限由线上服务端响应决定，客户端 DLL 中没有可反推出线上值的常量**。页数写入 `players.store_pages`，与 `store_json`、`store_coin` 一起跨重启保留。

### 3.6 背包快照更新 UpdateBagUIEvent（HotfixView 140）——响应 BagMapList 如何更新背包

`UpdateBagUIEvent.Run`（`M2C_SendBagHandler` 与所有购买/卖出/存取响应都走这里）：
1. 若背包 UI 已存在，先把现有所有格子序号填入 `_needClearIndex`；
2. 遍历 `args.list`（BagMapList）：对每个 `BagMap` 把 `Index` 从 `_needClearIndex` 移除；在 `ClientItemDataComponent.Instance.ItemDic` 按格子 `Index` 建/取 `ClientItemData`（`ItemId/ItemType/Count/IsLock/GetSource`；`EquipItem` 时用 `EquipTransMessage` 构造 `Equip`）；
3. 遍历结束后，**把 `_needClearIndex` 里（响应未出现的）旧格子清空/移除**，再刷新 UI。

→ 结论：**服务器所有携带 `BagMapList` 的响应必须返回背包全量非空格子快照**，否则客户端会误删物品。仓库不同：`StoreUI.ShowSlot` 只清除当前页的 60 个缓存索引，所以 `StoreList` 至少要包含当前页完整快照；当前服务端返回全仓快照，也兼容客户端本地跨页搜索。

### 3.7 货币推送路径

`M2C_SyncUnitAttributeHandler`（Hotfix 246）：`unit.GetComponent<NumericComponent>().Set(msg.NumericType, msg.Value)`。

## 4. 相关数据表结构与字段语义

### 4.1 ShopBase（普通商店，44 行）

`datatable_json/ShopBase.json`（[key,{...}] 二元组）字段：`_id, ItemType, Page, ItemId, Price`。
- `Price`：铜币价格（int），无独立币种字段 → 固定铜币结算。
- `Page`：商店页签（0/1/4），客户端 `C2M_BuyInShop.PageIndex` 取自页签选中。
- `ItemType`：2=GoodsItem（消耗品）、3=MaterialsItem（材料）。

示例：
```json
[10001, {"_id":10001, "ItemType":2, "Page":0, "ItemId":110305, "Price":500}],     // 超小型生命药水 500铜
[11001, {"_id":11001, "ItemType":3, "Page":1, "ItemId":110343, "Price":990000}],  // 金条 99万铜
[14001, {"_id":14001, "ItemType":2, "Page":4, "ItemId":110385, "Price":1000000}]  // 宠物粮食 100万铜
```

### 4.2 MarketBase（元宝市场，442 行）

字段：`_id, Period, ItemType, Page, ItemId, Price_YuanBao, OnlyYuanBao`。
- `Price_YuanBao`：元宝价（int）；`OnlyYuanBao`：仅限元宝市场购买（兑换券市场禁买）。
- `Page`：页签 0..4；客户端 `ShowItems` 只渲染 `marketBase.Page == m_pageList.selectedIndex` 的条目（客户端侧过滤，见 §3.2）。
- `Period`：442 行中仅 `_id=10001` 一行含 `Period=0`，其余 441 行**无该字段**——不存在 1..4 的限时/兑换期取值，期数语义无法从包内证实，需服务端配置。
- 服务器回 `M2C_GetMarket.MarketIdList` 即该表 `_id` 列表；`Discount`（float，如 0.5）为服务器下发的折扣系数，客户端展示 `RoundToInt(Price_YuanBao × Discount)`，扣费以服务器计算为准。

示例：
```json
[10001, {"_id":10001, "Period":0, "ItemType":2, "Page":0, "ItemId":110342, "Price_YuanBao":10}],
[10002, {"_id":10002, "ItemType":2, "Page":0, "ItemId":110327, "Price_YuanBao":5}],
[10017, {"_id":10017, "ItemType":2, "Page":0, "ItemId":110362, "Price_YuanBao":9999989, "OnlyYuanBao":true}]
```

### 4.3 MultiShop（多商店，155 行）

字段：`_id, Type, ItemId, Price`。
- `Type` ∈ {1,2,3,4}：对应客户端 4 个页签，`C2M_BuyInMultiShop.shopType = Type`。
- `Price`：int，币种由 Type 决定（`Cal.DataTable.MultiShopCategory` 类**存在于客户端**——Hotfix TypeDef 31，方法 `GetByType`——但 `MultiShopCategory.json` 数据表未提取到，币种映射无法从包内证实；需服务端按 Type 映射币种，常见做法：Type1=元宝/高额、Type2..4=铜币/荣誉/家族贡献等；下表 Price 数量级可供参考）。

示例（按 Type 采样）：
```json
[11001, {"_id":11001, "Type":1, "ItemId":20258, "Price":8888888}],     // Type1 8,888,888
[12001, {"_id":12001, "Type":2, "ItemId":120343, "Price":1000}],       // Type2 1,000
[13001, {"_id":13001, "Type":3, "ItemId":20085,  "Price":588}],        // Type3 588
[14001, {"_id":14001, "Type":4, "ItemId":20216,  "Price":100}]         // Type4 100
```

### 4.4 辅助表

- **GoodsBase**（175 行）：物品主表，字段含 `_id, Name, IconName, Type(1=使用道具), Price(卖出基准价), MaxAmount(堆叠上限), IsLock, Description...`。卖出价语义：`C2M_SellItem` 按 `GoodsBase.Price × Count` 结算铜币（110305 超小型生命药水 Price=500，110343 金条 Price=500）。
- **ServerItemLimit**（232 行）：`_id, Name, MinCount, MaxCount`——物品服务器数量上下限（寄售行库存/世界存量控制参考）。
- **ArenaShop / HonorShop / FamilyShop / StarShop**：其他货币商店变体——ArenaShop`{_id, Itemid}`；HonorShop`{_id, ItemType, ItemId, Price}`（荣誉=1030）；FamilyShop`{_id, ItemType, ItemId, Price}`（家族贡献=1037）；StarShop`{_id, Itemid, Price}`。客户端无独立 UI 类，均由多商店/功能系统按 `C2M_BuyInMultiShop.shopType` 或对应协议消费（本包未提取到 `MultiShopCategory.json` 映射数据，需服务端配置）。

### 4.5 能否增加商城商品（2026-08-17 实证边界）

可以，但必须同时满足客户端本地表和服务端表一致，不能只改服务器：

- 已存在于客户端 `GoodsBase/MaterialBase/EquipBase` 的物品，可以新增 `ShopBase`、`MarketBase`
  或 `MultiShop` 行；客户端按本地表生成图标、名称和页内序号，服务端按同一排序定位购买请求。
- 普通商店行使用 `_id,ItemType,Page,ItemId,Price`；元宝市场使用
  `_id,ItemType,Page,ItemId,Price_YuanBao,OnlyYuanBao`；多商店使用 `_id,Type,ItemId,Price`。
- `Page/Type` 必须是现有 UI 能到达的页签，`_id` 必须唯一；同页/同 Type 按 `_id` 升序，
  客户端发送的是排序后的 `SlotIndex/Index`，两端条目不同会买到错误物品。
- 若 `ItemId` 在客户端三张物品主表中不存在，客户端无法解析名字、图标或装备详情；若还缺图标/模型资源，
  仅增加 JSON 也无效，必须补齐资源 bundle 与 manifest 依赖。

本轮按用户要求只完成能力分析，没有增加或改动任何商城商品。

### 5.2 购买通用流程（Shop / Market / MultiShop 一致）

```
HandleBuy(req, resp):
```

### 5.3 卖出 C2M_SellItem（2026-09-14 更正）

> ⚠ 原文写的“一律 `GoodsBase.Price × Count` 进铜币”**不成立**。实际是**两条结算路径**，
> 见 `server-mysql/shop.go:636 onSellItem` / `:703 saleCurrencyDelta`。

```
// 路径 A：元宝市场批次「卖回元宝市场」→ 按“实付单价”折算代金券
if 出售目标 == 元宝市场 && item.PurchaseSource == 元宝市场购入
   && item.PurchaseCurrency ∈ {元宝, 代金券} && item.PurchaseUnitPrice > 0 {
    total = PurchaseUnitPrice × Count
    gain  = floor(total × market_recovery_percent / 100)   // 整数安全写法：total/100*p + total%100*p/100
    玩家 代金券(1025) += gain                              // 当前 85% 回收
}
// 路径 B：其他来源 / 其他出售目标 → 按物品价进铜币
else {
    unit = 商店回收价表(sale rule) 命中则用配置价，否则
           装备取 EquipBase.Price，其余取 GoodsBase.Price（再退到 MaterialBase.Price）
           最终兜底 Gameplay.shop_sale.fallback_price_coin（默认 500）
    玩家 铜币(1028) += unit × Count
}
背包删除 Count（SlotIndex 定位）；随后推 M2C_SendBag 全量 + 货币同步
```

**「出售目标」怎么来的（原文完全没写，细节关键）**：原生 `C2M_SellItem` 请求体里
**只有 SlotIndex 和 Count，没有目标字段**。目标是按会话隐含选定的：

- 发过 `C2M_GetMarket` ⇒ 本次会话出售目标 = **元宝市场**；
- 收到 `M2C_OpenShopUI` ⇒ 目标 = **普通商店**（含远程商店路径）；
- 服务器自动下发的商城配置推送**不会**改变这个选择；从未选定 ⇒ 按铜币结算。
- 元宝市场**所有分页共用同一规则**；MultiShop 购入会记录自己的支付币种，
  **不会**被当成元宝市场批次走 85% 回收。

要点（原文未写、易踩）：

- **必须记录“购买来源”才能算出回收价**：`bagItem` 上带
  `PurchaseSource / PurchaseCurrency / PurchaseUnitPrice`，落库在三张规范化子表
  （`player_item_purchase_origins`、`player_mail_item_purchase_origins`、
  `consignment_item_purchase_origins`，见 `item_purchase_origin.go` + `normalized_store.go`）。
  **没有这组字段就无法区分“花元宝买的”和“打怪掉的”**，会退化成按物品价回收。
  来源编码：`0 未知/奖励、1 商店、2 元宝市场、3 多商店、4 寄售行`；
  币种编码：`0 无、1 铜币、2 元宝、3 代金券、4 星币、5 荣誉、6 竞技币、7 家族贡献`。
  **仅来源与币种完全相同的批次才能叠堆**；拆分、整理、仓库、直接交易、装备持久化和退件邮件都会保留来源。
  买下寄售品会把来源改写为 `寄售行/星币`；寄售过期未售出则**恢复原来源**。
- 回收比例来自 `config/operations/Gameplay.yaml` 的 `shop_sale.market_recovery_percent`（当前 **85**）。
  取整发生在**请求的总价**上，所以拆成多次出售会丢掉不足 1 的代金券零头。
- `M2C_SellItem` 的部分客户端构建里**没有**字段级 `BagMapList`，所以服务端在响应之外
  **补发一次 `M2C_SendBag` 全量快照**，再推货币；顺序不能颠倒，否则连续快速出售会丢一次 UI 刷新。
- 货币/经验物品 `110201~110206`（`isProtectedCurrencyItem`）**禁止出售**；
  出售前先做 `canApplyCurrencyDelta` 上限校验，**超限或取整后为 0 都直接拒绝且不消耗物品**（`shop.go:670` 起会回滚物品数量）。
- 客户端与其 tooltip 资源**未改动**；原生拖拽/悬浮显示的视觉效果仍需客户端验收，
  服务端 handler 测试不能替代这一步（见 `server-mysql/docs/shop-sale-origin.md`）。

### 5.4 寄售行（Consignment）（2026-09-14 更正）

> ⚠ 原文“买家扣 **Coin(1028)**、卖家收 `Price×0.9x` 手续费”**是错的**。
> 寄售行的结算货币**不是铜币，而是物品形态的“星币” `GoodsBase 110205`**；
> `server-mysql/consignment.go:527` 注释原文：*"The online client treats GoodsBase 110205 as
> the consignment currency; NumericType 1028 copper coins are unrelated to this transaction."*

```
PutIn(req):  校验背包格、Count、Price>0；扣包 → 生成 ConsignMap{ConsignItemId, UnitId=玩家, Name, RemainTime=72h, Item, EquipTransMessage, Price, NeedPwd=(Pwd!="")}
             存 Pwd(哈希)；resp.BagMapList = FullBagMapList
Get(req):    按 JobType/ItemType 筛选 + 分页(Page/TotalPage)，resp.ConsignMapList = 页数据
Buy(req):    按 ConsignmentId 定位；NeedPwd 则校验 Pwd（错误密码/无密码不一致要报错，不泄露）
             买家扣 星币(物品 110205) 数量 = Price；不足时报“星币不足”
             物品转给买家，并写入 PurchaseOrigin{来源=寄售行, 币种=星币, 单价=Price}
             卖家收 Price 全额（无手续费）→ 走「寄售成交」邮件附件发放
过期处理：RemainTime 到期原物品退回寄售人背包；背包满或卖家离线时改走附件邮件返还
```

**星币不是 NumericType 余额，是背包里的物品堆叠**，这是原文档最容易误导人的地方：

- 星币固定占用背包槽位 `starCoinBagSlot = -1000000`（`state_extra.go:42`），
  **不参与背包排序**，`bag_sort_ghost_test.go` 专门回归这一点。
- 因此 `currencyDelta` 结构体**刻意不含星币**（`state_extra.go` 注释明说），
  上限/回滚逻辑按物品数量而非数值余额走。
- 购买寄售品时若背包里星币被打散，先 `canonicalizeStarCoins` 归并再扣（`consignment.go:506`）。

### 5.5 仓库（Store）

```
GetStore(page):  resp.StoreList = 仓库分页全量快照；resp.Coin = 库内铜币；resp.Total = 总页数
PutInStore:      背包 BagIndex 物品 → 仓库（按 Page 分页）；resp.StoreList + resp.BagMapList 双全量
TakeOffStore:    仓库 StoreIndex → 背包；同上双全量
PutCoin/TakeCoinInStore: 移动 Coin；resp.Coin = 库内余额（同步推 M2C_SyncUnitAttribute(Coin)）
QueryExtandPrice: resp.Coin / resp.Voucher = 本次扩容费用（数值由服务端返回，客户端无线上价格常量）
ExtandStore:     扣费 → 仓库容量 +1 页（当前客户端每页 60 格）
SortStore:       只整理请求 Page（按 ItemType/ItemId/品质/强化/星级），resp.StoreList 全量回
```

### 5.6 远程商店

```
GetOpenRemoteStore: resp.Price = 配置价（客户端显示 X/10000）
OpenRemoteStore:    扣 Price（币种由配置定，如 铜币或元宝）→ 成功后由服务器推 M2C_OpenShopUI 打开商店（或直接发奖励）
```

### 5.7 关键约束

- **所有 BagMapList/StoreList 必须全量**（见 §3.6），否则客户端清空未出现格子。
- 所有 IActorLocationRequest 均在玩家 Unit 上执行，需校验 Page/Index/Slot 越界、Count>0、库存/货币足额；**扣款与入包要原子**（同事务或同锁）。
- 货币数值用 NumericType（元宝 1024 / 兑换券 1025 / 铜币 1028 / 体力 1039 / 荣誉 1030 / 家族贡献 1037），扣款后推 `M2C_SyncUnitAttribute` 或 `M2C_SyncUnitAttributeList`。
- `C2M_BuyInShop.PageIndex` 由客户端页签决定，服务器可按 ShopBase.Page 过滤校验。

## 6. 验证要点（协议脚本可断言）

1. **打开链路**：连接后由服务器推 `M2C_OpenShopUI(20209)` / `M2C_OpenStoreUI(20187)` / `M2C_OpenConsignmentUI(20210)`，客户端应弹出对应 UI；推 `M2C_SendBag(20260)` 背包刷新。
2. **购买回包**：发 `C2M_BuyInShop(20174){PageIndex:0, SlotIndex:0, Count:1}` → 收到 `M2C_BuyInShop(20175)`，断言 `Error==0` 且 `BagMapList` 与背包实际一致（全量快照：响应中出现 ItemId=110305 数量 +1，且所有其它格子仍存在）。
3. **货币联动**：购买后应额外收到 `M2C_SyncUnitAttribute(20169)`（NumericType=1028 铜币 / 1024 元宝）或 `M2C_SyncUnitAttributeList(20170)`，数值 = 扣费前余额 − 单价×数量。
4. **市场折扣**：`C2M_GetMarket(20172)` → `M2C_GetMarket(20173)` 断言 `MarketIdList` 数量与 MarketBase 行数一致、`Discount` 为服务器配置值；`C2M_BuyInMarket(20176){Type:YuanBaoMarket(2)}` 扣元宝 = `round(Price_YuanBao × Discount)`；`Type:VoucherMarket(1)` 且商品 `OnlyYuanBao=true` 应返回错误。
5. **多商店**：`C2M_BuyInMultiShop(20417){shopType:2, index:0, count:1}` 按 Type=2 的 MultiShop 行扣费入包。
6. **寄售行**：`C2M_GetConsignment(20181){Page:0}` → 断言 `TotalPage` 与 `ConsignMapList` 分页一致；`C2M_PutInConsignment(20183)` 后背包快照减少、再 `C2M_GetConsignment` 能查到该条目（含 Price/NeedPwd/RemainTime）；带 Pwd 的条目 `C2M_BuyInConsignment(20185)` 传错密码应报错。
7. **仓库**：`C2M_GetStore(20188){Page:0}` → `M2C_GetStore(20189)` 断言 `Total`/`StoreList`/`Coin`；`C2M_PutInStore(20192)` 后同一响应里 `BagMapList` 与 `StoreList` 同时为全量；`C2M_PutCoinInStore(20196){Coin:1000}` 后 `M2C_PutCoinInStore(20197).Coin` 为库内总额，且推 `M2C_SyncUnitAttribute(Coin)` 扣减。
8. **远程商店**：`C2M_GetOpenRemoteStore(20294)` → `M2C_GetOpenRemoteStore(20295).Price` 与配置一致；`C2M_OpenRemoteStore(20296)` 成功后应看到后续开店推送或奖励入包。
9. **卖出**：`C2M_SellItem(20178){SlotIndex, Count}` → **分两种情况断言**（见 §5.3）：
   打怪掉落/普通物品进 **铜币(1028)** = 回收单价 × Count；**商城元宝/代金券购入批次卖回商城**进
   **代金券(1025)** = 实付价 × `market_recovery_percent`。响应之外应再收到一次 `M2C_SendBag` 全量。
10. **寄售结算币种**：`C2M_BuyInConsignment(20185)` 扣的是**星币物品 110205**（背包槽 `-1000000`），
    **不是铜币 1028**；星币不足应返回“星币不足”。成交后卖家通过「寄售成交」邮件附件收到**全额**货款（无手续费）。
