## 1. ★ F12：驱散链路是死代码

### 1.1 服务端实现是完整的

```go
// battle_effects.go
CombatDispelHarmful / CombatDispelBeneficial / CombatDispelAll   // 三种筛选
func (r *CombatRuntime) Dispel(source, target, filter, count)      // 公开 API，1261
func (r *CombatRuntime) dispelInternal(...)                        // 实现，1265
CombatEventEffectDispelled                                          // 事件，151
```

`dispelInternal` 的逻辑也没问题：按 `effect.id` 升序、跳过 `undispellable`、按 filter 过滤、`count` 截断。

### 1.2 但**没有任何代码能构造它**

| 检查项 | 命令 | 结果 |
|--------|------|------|
| `CombatEffectDispel` 的构造点 | `grep -rn "CombatEffectDispel" --include=*.go` | 只有**枚举定义**（112）、**apply 分支**（757）、**校验分支**（795）—— **零构造** |
| `SkillEffectKind` 里有没有 dispel | `skill_logic.go:317-333` | **15 个 kind 里没有 dispel** |
| 配置里的技能选项类型 | 遍历 `SkillLogicConfig.skillDic` 统计全部 `_t` | **17 种，没有「驱散」** |
| `Dispel(...)` 的调用方 | `grep -rn "\.Dispel(" --include=*.go` | **零调用方** |
| 技能文案 | 遍历 `SkillConfig` 找 `驱散/净化/免疫/解除` | **0 行命中** |

配置里全部 17 种技能选项类型（出现次数）：

```
396  SelectSingleTarget              58  SelectMultiTarget
217  SkillOption_应用Modifier         42  SkillOption_播放特效
102  SkillOption_伤害                  9  SkillOption_治愈
 92  SkillOption_几率                  8  SkillOption_护盾
 63  SkillOption_创建携带Modifier的子弹   3  SkillOption_反击
                                       3  SkillOption_改变伤害倍率
                                       2  SkillOption_延迟操作
                                       2  SkillOption_反伤
                                       2  SkillOption_修改Modifier数据
                                       1  SkillOption_吸血
                                       1  SkillOption_改变释放次数
                                       1  SkillOption_改变公共CD
```

**结论**：原版游戏**本来就没有驱散机制**。服务端那段实现是照着通用战斗系统写的预留代码，
**永远不会被执行**。

> 对比：同批的 `改变伤害倍率` / `改变释放次数` / `改变公共CD` / `修改Modifier数据`
> 都在 `SkillEffectKind` 里有对应 kind 且在 `executeSkillEffectAtContext` 的 switch 里处理了，
> 是真在用的。只有 **dispel 一个没有 kind**。

### 1.3 ★ 连带后果：`canBeClear` 是个死字段

`canBeClear` 是 `SkillLogicConfig` 的 modifier 字段（配置里两种取值都有：
`31060113` 是 `true`、`10000113` 是 `false`），服务端把它翻成 `EffectSpec.Undispellable`：

```
写入（8 处）：battle_periodic.go:59, battle_skill_runtime.go:772/785/815/850/889/961,
              battle_effects.go:885
读取（1 处）：battle_effects.go:1275 —— dispelInternal 里
```

**唯一的读取点在死代码里** ⇒ `canBeClear` 对游戏行为**没有任何影响**。

（死亡清理 `clearUnitEffects`（`battle_effects.go:1409`）**不**看 `undispellable` ——
这是对的：死亡应该清掉一切，而不是「驱散」。）

**建议**：把 `CombatEffectDispel` / `Dispel` / `dispelInternal` / `CombatEventEffectDispelled`
与 `Undispellable` 字段一起标注为「预留，当前无入口」，或直接删除。
**不要**因为「实现了却没人用」就去给某个技能硬加驱散 —— 原版没有这个机制。

> ✅ **这条已经被现有测试守住**：`TestSkillLogicCatalogCoversEveryConfiguredOption`
> （`skill_logic_test.go:17`）断言了 15 种 option kind 的**精确计数**，并且
> `len(gotCounts) != len(wantCounts)` 会直接 fail ——
> 也就是说**一旦有人在配置里加了 `SkillOption_驱散`，这个测试立刻红**。
> 所以 F12 不需要新测试，只需要登记「服务端那段是预留代码」。

## 2. ★ F13：`stateK=4`「不死」与 `stateK=5`「死亡复活」被合并

### 2.1 配置证据：它们是两个不同的状态

| stateK | modifier | 技能 | name | iconId | iconDesc |
|--------|----------|------|------|--------|----------|
| 4 | 21060219 | 210602 幸运宠儿 | `{11}%的几率给自己添加【不死】，持续{12}秒。` | `bufficon_nodie` | — |
| 5 | 31060113 | 310601 人体学 | `{3}%【死亡复活】，持续{4}秒。` | **`bufficon_resurgence`** | **`该目标具有死亡复活效果`** |

310601 人体学（护士）的技能文案：

> 3：治疗友方单体160%精神攻击加成的生命值，暴击时给目标添加15%自身生命值上限的【护盾】，
> 持续14秒、**【死亡复活】，持续7秒**。

技能 desc 也写着「甚至**起死回生**」。
`31060113` 的 `continueTime` 由 `Args3` 给出 = **7 秒**（level 3）。

**名字不同、图标不同、iconDesc 不同、stateK 值不同** —— 客户端把它们当两个状态。

### 2.2 服务端把两者合并了

```go
// battle_skill_runtime.go:1380
func combatStatusForStateKey(key int32) CombatStatus {
	switch key {
	case 1:      return CombatStatusInvincible
	case 4, 5:   return CombatStatusUndying      // ← 4 和 5 合并
	...
```

而 `CombatStatusUndying` 全仓库只在一个地方被读：

```go
// battle_effects.go:1093
minimumHP := int64(0)
if r.hasAnyStatus(request.Target, CombatStatusUndying) {
    minimumHP = 1                             // 血量钉在 1，永远不会死
}
```

`grep -rn "复活\|Revive\|revive"` 在服务端只命中世界 BOSS / 家族 BOSS 的**到期刷新**，
**没有任何「死亡后复活」的战斗机制**。

### 2.3 差异在哪（以及为什么可以接受）

| | 服务端当前（Undying） | 「死亡复活」的字面语义 |
|---|---|---|
| 血量降到 0 | **不会**（钉在 1） | **会死**，然后复活 |
| 死亡事件 | 不发 | 发（死亡动画、清 buff、击杀结算、任务进度） |
| 复活后血量 | — | 线上未给参数（`valueK=0` / `valueV=0`，**没有复活血量字段**） |
| 客户端表现 | 血条卡在 1；**图标与描述是对的**（来自 modifier，不是状态枚举） | 显示复活特效 |

**判定：语义简化，不建议盲改。**

理由：
1. 配置里**没有任何复活血量参数**，说明即使原版是「复活」，血量也是隐式约定（全满？1 点？无从得知）；
2. 单人战斗里玩家死亡会直接结束战斗，先死后复活反而会走到「已结算失败」的状态上，
   钉血是**更务实**的实现；
3. **玩家看不出差别** —— 客户端拿到的 `IconId`/`IconDesc` 来自 modifier
   （`bufficon_resurgence` / `该目标具有死亡复活效果`），不是从 `CombatStatus` 反推的，
   所以图标和提示都正确。

**登记即可。** 如果将来要严格实现，需要在 `applyDamageInternal` 的 `targetDied` 分支里
加一条「若持有 revive 状态则回血并跳过死亡流程」的旁路，并确定复活血量。

## 3. F14：「无敌」只挡伤害，不挡 debuff（非缺陷）

```go
// battle_effects.go:1053 —— 唯一的读取点
if r.hasAnyStatus(request.Target, CombatStatusInvincible) {
    event := r.event(at, CombatEventImmune, ...)   // 伤害被完全免疫
    ...
}
```

`CombatStatusInvincible` 全仓库**只在这一个地方**被读。也就是说：

- 无敌期间：**伤害全免** ✓
- 无敌期间：**仍然会被挂眩晕 / 沉默 / 石化 / 中毒 / 流血**（`applyStatusEffectWithContext` 不看无敌）

技能 410504 无敌的文案是「给友方释放无敌状态，**增加其攻击力**。」—— 只提伤害免疫，
没提状态免疫。**所以这是符合文案的**，不是缺陷。

> 如果策划想要「无敌 = 完全免疫」，那是一个**需求变更**，不是 bug 修复。

## 4. 状态机制全景（本文件 + doc 36 的合并视图）

| stateK | 语义 | 服务端落点 | 状态 |
|--------|------|-----------|------|
| 1 | 无敌 | `Invincible` → 只免伤害 | ✓ |
| 4 | 不死 | `Undying` → HP 钉 1 | ✓ |
| 5 | 死亡复活 | **合并进 `Undying`** | ⚠ F13 语义简化 |
| 8 | 沉默 | `Silenced` → `CanCast` 为假 | ✓ |
| 9 | 眩晕 | `Stunned` → `CanAct` 为假 | ✓ |
| 10 | 冰冻 | `Frozen` → `CanAct` 为假 | ✓ |
| 11 | 石化 | `Petrified` → `CanAct` 为假 | ✓ |
| 14 | 必定暴击 | **无映射、无兜底** | ✗ **doc 36 §4.5 的缺口** |
| 15 | 隐身 | `Invisible` → `CanBeTargeted` 为假 | ✓ |
| 100/101/102 | 护盾 / 反伤 / 反击 | 无映射，**子节点**承载 | ✓ |
| 104/105/106 | 中毒 / 流血 / 点燃 | 无映射，**子节点 DoT** 承载 | ✓ |
| 107 | 持续治疗 | 无映射，**子节点 HoT** 承载 | ✓ |

**状态的删除通道**：
- 自然过期（`expiresAt`）✓
- 死亡清理（`clearUnitEffects`，清一切）✓
- 战斗结束（`Cancel`，不发 `Time=0`，客户端按 Add 里的 Time 自毁）✓

## 6. 小结

本轮把**控制之外的其余状态机制**补完了：

- **状态映射**：14 个非零 stateK 里，**只有 `14`（必定暴击）是真空缺**（doc 36 §4.5），
  `5`（死亡复活）是语义简化（F13），其余全部正确。
- **状态删除**：自然过期 / 死亡清理 / 战斗结束三条通道都正常；
  **驱散整条链路是死代码**（F12），连带 **`canBeClear` 配置字段完全无效**（F12b）。
- **无敌**：只免伤害不免状态，与文案一致（F14）。

**没有发现新的「功能不生效」缺陷** —— 唯一的功能缺口仍然是 doc 36 §4.5 的 `stateK=14`。
