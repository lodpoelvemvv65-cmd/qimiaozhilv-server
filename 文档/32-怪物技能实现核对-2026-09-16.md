# 怪物技能实现核对（2026-09-16）

> 本文核对**怪物技能 500001–500042**（共 42 个）的服务端实现是否与客户端分发的 `SkillLogicConfig` 一致，
> 重点是各类**效果**：伤害、反伤、中毒 / 流血 / 燃烧 / 持续治疗、护盾、控制、加减益、子弹、延迟。
> 基准与文档 30 / 31 相同：`_test_runs/skill-description-audit-20260915/SkillLogicConfig.json`（权威逻辑）
> + `datatable_json/SkillConfig.json`（UI 文案）+ `datatable_json/MonsterBase.json` / `SkillGroupBase.json`（谁用它）。
>
> 结论一句话：**服务端怪物技能的运行时实现与配置一致，未发现实现缺陷**；
> 真正的问题是 `monster_battle.go` 里那张**已死的近似表**和几条**原版配置/文案自身的矛盾**。
>
> **本文的核对纪律**：所有"有缺陷"的结论都必须有实测支撑。本轮先按静态阅读提出过三条
> 「实现缺陷」候选（500032 反伤未实现、多目标弹道只画一条、辅助技文案与节点不符），
> **实测后三条全部证伪**，证据记在 §4.2 / §4.5 / §五 末尾的「明确核过、确认没问题」一节。
> 记录这些证伪结果是为了让后来人不必重复排查同一批怀疑。

## 二、运行时路径：怪物技能根本不查那张近似表

关键事实（决定了下面所有判定）：

```
battle_monster_attack.go:139   plan, err := skillLogicCatalog.Plan(skillID, 1)
```

怪物选技是 `selectMonsterSkillID()`（`battle_skill_runtime.go:1439`）从 `SkillGroupBase.SkillsArr`
**等概率随机**取（组内重复写同一个技能 id 表示权重），然后**用真实配置构计划**，
再走 `executeSkillPlanWithContext` —— 与玩家技能完全同一条结算路径。

也就是说 `monster_battle.go` 里的 `monsterSkillSpecs`（按 skillId 硬编码 `mode`+`percent` 的近似表）
**在生产路径里完全没有被读取**。它只被 `monster_battle_test.go` 调用。

## 三、死代码：`monsterSkillSpecs` / `monsterDamage`

```

### 3.3 处置建议

**建议删除** `monsterSkillSpecs` / `monsterSkillSpecFor` / `monsterDamage` 与 `monster_battle_test.go` 里对应的 4 个用例。
理由：

- 生产路径不用它，留着只会让后来人误以为怪物伤害走这张表；
- 它的值和权威配置不一致，**一旦有人接上去就是静默错误**；
- 删除后怪物伤害完全由 `SkillLogicConfig` 单点决定，符合「配置唯一权威」的项目原则。

> ⚠ 这条是**代码清理**，不是行为修复——删除**不改变任何运行时行为**（因为没有调用方）。
> 若要保留，必须同时修掉 3.2 表里的偏差并在注释里写明「仅供测试基线，不参与结算」。

## 四、各类效果逐项核对（全部实测）

判定手段：临时 Go 探针（跑完已删除），在真实 `*monsterUnit` 状态上执行配置计划并观察事件与血量。

### 4.1 伤害 —— 一致

42 个技能的 `monsterSkillSpecs` 与配置对照中，**成批一致**的：
500001/002/003/004、500008/019/022、500013、500014/028、500015/016/017/018、500020、500025、
500029/030、500031、500033–500038、500039–500041 —— 其 `damageCalculate_Self/Target` 与配置逐项吻合。

> 注：怪物伤害在运行时还会叠加**百分比攻击加成**（`battle_skill_runtime.go:1238-1242` 读 `monster.extraNumeric[1045/1046]`）
> 和**暴击**（`EffectivePercentAttribute(source, CombatAttributeCritRate)` → `MonsterBase.Mcri × 100`）；
> 死表这两样都没有。这也是死表不能当真的原因之一。

### 4.2 反伤（`SkillOption_反伤`）—— 一致，**实测有效**

全表**只有 500032「打我试试」**带反伤：
`modifier 50003228`，`stateK 101`，`continueTime 11`，事件 6 挂 `SkillOption_反伤 param=100`，
目标 `SelectSingleTarget targetType=3`（持有者）。文案：「给自身添加100%【反伤】，持续11秒。」

实测（怪物 1000 物攻 / 玩家 10000 血 / 1000 魔攻场景）：

```
PROBE apply events=2
    type=16 src=2:9001 dst=2:9001 key= amount=0
    type=1  src=2:9001 dst=2:9001 key=modifier:50003228:reflect amount=0
PROBE monster reflect percent = 100
PROBE damage events=3
    type=7  src=1:1234 dst=2:9001 amount=1000     ← 玩家打怪 1000
    type=14 src=2:9001 dst=1:1234 amount=1000     ← 怪反伤回 1000
    type=7  src=2:9001 dst=1:1234 amount=1000
PROBE playerHP after=9000 monsterHP=99000
```

**结论：反伤正常装载并生效。**
代码落点：事件 2/5/6 的 `反伤/反击/吸血` 被 `isReactiveSkillEffect`
识别后**不进 `dynamic` 钩子**，而是由下面的循环以 `ctx.triggerEvent=0` 直接执行，
落到 `SkillEffectReflect` 分支的持久化安装路径（`battle_skill_runtime.go:610-630`），
装成 `CombatEffectReflect`；受击时 `battle_effects.go:1114-1123` 读它返伤。

**真实服务端 TCP 验收（2026-09-16，`test/verify_monster_reflect.py`，pass）**：
家族 5 阶 BOSS 抽到 500032 后，玩家主动出手，服务端日志同时刻出现成对两条：

```
[combat.damage] source=1:4066   target=2:1000000001 requested=1 ... reflected=false   ← 我打 BOSS 1 点
[combat.damage] source=2:1000000001 target=1:4066   requested=1 ... reflected=true    ← 反伤：反回我 1 点
```

脚本侧独立判据（不读服务端日志）：同一批里出现「我打中 BOSS」与「等量打回我」两帧，
实测 `dt=0.000s`、数值 1 → 1（100% 反伤）。

> **反伤不受 §八 那条缺陷影响**：50003228 的 `buffType=0` → `statusPolarity` 判为
> `CombatEffectBeneficial`，而 `applyStatusEffectWithContext` 里两个 `return nil` 的
> 状态对抗都只在 `CombatEffectHarmful` 时生效。因此本文里**所有 `buffType=0` 的增益
> （反伤 / 护盾 / 无敌 / 王防 / 加攻防）都不走那条判定**，与 §八 的有害状态是两条路。

> 可达性：技能组 `10024`（含 500032）被 `MonsterBase` 的 10160 ※恐怖杰瑞、10429 ※恐怖杰瑞※转生、
> 10277 暗、30282 暗（试炼）引用；`10028`（3阶boss）、`10030`（5阶boss）也带 500032。

### 4.3 中毒 / 流血 / 燃烧（周期伤害）—— 一致，**实测会 tick**

42 个怪物技能里**每一条事件 8 节点都是 `SkillOption_伤害`**，没有事件 8 的 `SkillOption_治愈`
（500033–500038 的治疗/护盾都是事件 0 的瞬发节点）→ **怪物 HOT 在这批技能里不存在**。

| 技能 | Modifier | overlayType / 时长 / stateK | 每跳公式 | 可达 |
| --- | --- | --- | --- | --- |
| 500007 / 500021 刺杀 | 50000730 / 50002133 | 2 流血 / 11s / 105 | `Target=(ct 2, 10.0)` | 是（组 10013/10014/10040） |
| 500009 / 500023 熔岩击 | 50000928 / 50002332 | 3 燃烧 / 14s / 106 | `Self=(ct 0, 100.0)` + `Target=(ct 2, 12.0)` | 是（组 10018/10020/10023/10032/10043 等） |
| 500010 / 500024 烈风 | 50001033 / 50002438 | 1 中毒 / 26s / 104 | `Self=(ct 0, 30.0)` + `Target=(ct 2, 10.0)` | 是（组 10018/10022/10027/10028/10029/10030/10033/10044） |

实测（怪物对玩家施放，推进 3 个节拍）：

```
PROBE skill=500009 teamType=1 events=3 playerHP=1000
    type=1 src=2:9001 dst=1:1000 key=overlay:3:dot amount=1120     ← 燃烧落地
    +4s tick: damage=1 playerHP=0
PROBE skill=500010 teamType=1 events=4 playerHP=701
    type=7 src=2:9001 dst=1:1000 amount=299                        ← 直接伤害
    type=1 src=2:9001 dst=1:1000 key=overlay:1:dot amount=1100     ← 中毒落地
    +4s tick: damage=1
```

**⚠ 上面这段是进程内探针，不能作为结论。** 它把 `ctx.roll` 固定成 `0`（`newSkillExecutionContext(battle, func() float64 { return 0 })`），
于是**绕过了状态命中判定**。真实服务端上这两个 DOT **一次都没有落地** —— 见 §八。

**在真实服务端上能够确认的只有机制本身**：DOT 一旦装上，节拍来自
`Gameplay.yaml:113 effect_tick_interval_ms: 4000`（`battle_periodic.go:12-48` 的注释记录了它是从线上抓包量出来的），
第一跳延后一个间隔、跳数 = `floor(时长 / 间隔)`；栈上限 `effect_max_stacks: 10`。

> **`amount` 的构成要理解清楚**：`1120 = 100% × 怪物物攻(1000) + 12% × 目标最大生命(1000)`。
>
> **哪些 DOT 带物攻项、哪些不带，实测如下**（全部来自 `SkillLogicConfig` 的 event-8 节点）：
>
> | 技能 | 每跳公式 | 是否带物攻项 |
> | --- | --- | --- |
> | 500009 / 500023 燃烧 | `Self=(ct 0, 100.0)` + `Target=(ct 2, 12.0)` | **带**（100%） |
> | 500010 / 500024 中毒 | `Self=(ct 0, 100.0)` + `Target=(ct 2, 10.0)` | **带**（100%） |
> | 500007 / 500021 流血 | `Self=(ct 0, **0.0**)` + `Target=(ct 2, 10.0)` | 不带 |
>
> 对照玩家 DOT：11050319 流血、11060318 燃烧、21050214 流血的 `Self` 也都是 `ct 0, param 0`。
> **服务端照配置算，没有算错**——差异在文案：只用一句话描述 DOT 的 `Desc` 不会提到这个物攻项。
> 登记为 §五 的 M1。

### 4.5 子弹与延迟 —— 一致

实测怪物多目标技能的弹道**没有丢目标**：

```
PROBE skill=500001 launches=3 impacts=3 travel=1s
    launch effect=3001 src=2:9001 dst=1:1001
    launch effect=3001 src=2:9001 dst=1:1002
    launch effect=3001 src=2:9001 dst=1:1003
PROBE skill=500001 damage-events=3      ← 伤害目标数一致

PROBE skill=500015 launches=3 damage-events=3

`monsterProjectilePresentation`（`battle_monster_attack.go:324-357`）遍历技能事件 1 的

`resolveSkillTargets(effect.Target, …)` 重新解析**配置里的多目标选择器**，
所以「打 3 个敌人」会画 3 条弹道。

42 个技能里只有 **500027（未被任何技能组使用）** 带 `SkillOption_延迟操作`，伤害路径
（`battle_skill_runtime.go:526-527`）与表现遍历都处理了它。

## 八、🔴 真实服务端实测：怪物所有有害状态几乎落不下来（2026-09-16 定位，**已修复**）

> **状态：已修复**。真正根因是**量纲**（`Hit`/`Res` 被当成比率型 ×100），修于 `57647a7`，
> 见 **§8.8**。`b8096ff` 与 `6b89f0a` 是排查途中的两次"绕过"（§8.5 / §8.7），已被取代。
> 修法：`statusContestChance` 里加怪物→玩家豁免，与既有的 `directDamageHits`
> 完全同形，**PvP 保留对抗**（PvP 敌方的 Hit/Resistance 是从对位玩家拷贝的真实
> 数值，那边对抗仍有意义）。验收记录见 §8.6。
>
> **这一节是本文唯一确认的运行时缺陷**，也是它推翻了 §4.3 初版结论的地方。

### 8.1 现场证据

### 8.2 机制

`battle_status_accuracy.go:36 statusContestChance`：

```
命中率 = 配置几率 × (100 + 施法者命中) / (100 + 目标抗性)
       = 100        × (100 + 0)        / (100 + 1560.364)   = 6.02%
```

- **怪物命中恒为 0**：线上 `MonsterBase` **整张表没有 `Hit` 字段**（50005 的完整行只有
  `Hp/PhyAtk/SpiAtk/PhyDef/SpiDef/Pcrir/Mcrir/Pcri/Mcri/Dvo/Rpcrir/Rmcrir/Rpcri/Rmcri/Nphyi/Nmeni`）。
  `battle.go:947` 按 `equipFieldToNumeric` 只搬非零字段，所以 `extraNumeric[1032] = 0`。
- **目标抗性 > 0**：`playerExtraNumeric(1033)` = `characterGrowthValue(ss, 26)`，
  即 `CharacterGrowth` 第 261 行 `{"Spi": 0.00028, "Sta": 1.2}` 对主属性的加权。
  1 级角色就有值，而且**随等级只增不减**。

**影响面远超 DOT**：这条判定对**所有有害状态**生效，不只是燃燒/中毒/流血 ——
怪物技能里的**眩晕（500006/500020/500039-500041）、沉默（500011/500025）、
石化（500013/500027）、各类减益（500005/500008/500019/500022）同样受害**。
唯一不受影响的是 `buffType=0` 的增益（如 500032 反伤、500036-500038 护盾、
500031 无敌、500042 王防），它们在 §4.4 的进程内探针与本次 TCP 中都正常。

### 8.3 与既有注释的矛盾

`battle_damage_accuracy.go` 里已经为**直伤**绕开过同一个坑，注释写得很清楚：

```go
// Online MonsterBase has no Hit/Res fields on any encounter monster.
// Applying a player's percentage-form Resistance to direct monster damage
// therefore makes late-game monsters miss almost forever. Resistance still
// contests harmful monster statuses through statusContestChance; only the
// direct PvE damage component is guaranteed to land.
```

最后一句「Resistance still contests harmful monster statuses」是**有意保留**的，
但既然怪物命中恒为 0、玩家抗性随等级增长，**保留这条判定的效果就是"怪物的状态几乎永远是摆设"**。
这更像是一个未一并处理的遗漏，而不是刻意的平衡设计。

### 8.4 当时的两条候选修复方向（**均未采用，最终走了 §8.8 的量纲修正**）

两条路，**都不能拍脑袋选**，因为"怪物状态该不该按玩家抗性打折"是设计问题：

1. **对齐直伤的做法**：怪物 → 玩家时，有害状态也跳过抗性对抗（`statusContestChance` 返回配置值）。
   代价：玩家抗性对 PvE 完全失效（与直伤一致），但怪物控制会恢复到配置的标称几率。
2. **给怪物补命中**：为 `MonsterBase` 引入/映射一个 `Hit`（或按等级给怪物一个基准命中），
   让对抗公式两边都非零。代价：需要原版数值依据，目前**没有证据**说明线上怪物的命中是多少。

**在拿到原版运行时证据（抓包/录屏）之前，建议先不动**，只把它登记为已知缺陷；
若要动，优先方案 1，因为它与直伤路径的既有决定自洽。

### 8.7 中间步骤二：玩家 → 怪物「豁免」（已被 §8.8 取代）

> ⚠ 同上：绕过，代价是玩家的命中在 PvE 里失效。保留作为排查过程记录。

修完 §8.5 之后，用同一套插桩在**真实服务端**复查时发现：对抗公式**两个方向都退化**，
而第一次只修了一半。实测（账号 `a12312304` 打家族 5 阶 BOSS）：

```
[DBG.contest] src=1:3905 tgt=2:1000000001 configured=18.00 hit=19129.122 res=0.000 => chance=100.000
[DBG.monskip] 本轮怪物 50004 不能行动（被控或已死），跳过这一轮
```

| 方向 | 施法者命中 | 目标抗性 | 算出来的几率 |
| --- | --- | --- | --- |
| 怪物 → 玩家 | **0** | 1560 | ≈ 6% |
| **玩家 → 怪物** | **19129** | **0** | **100%** |

- 玩家命中 19129 的来源：`EquipBase` 里 **116 件装备带 `Hit` 字段**（最高 200），
  毕业装全套 → 原始 191.29122 → 比率型字段 ×100 → **19129.122**；
- 怪物抗性 **0**：线上 `MonsterBase` 713 行没有 `Res` 字段（也没有 `Hit`）；
- 倍率 `(100+19129.122)/(100+0)` = **192.29** → 任何配置几率 > **0.52%** 都被
  `clampStatusChance` 夹到 **100%**。

**后果**：玩家的**一切**"有几率"的控制与减益对怪物都变成必中 —— 400001 沉默 18%、
110302 眩晕 20%、110304 冰冻 20%、110402 沉默 25% …全部 100%。

**用户观察到的现象由此完整解释**：超能力普攻的 18% 沉默变成必中 → 怪物每隔一轮
必被沉默 → 表现成"怪物每 12 秒才出手一次"。**那不是独立缺陷，是本条的症狀。**

**修复**（提交 `6b89f0a`）：两个方向是同一个根因，所以按同一条规则处理 ——
**任一侧是「不带评分的怪物」时不做对抗**，直接走配置几率：

```go
if battle.pvp == nil && (battle.lacksStatusRatings(source) || battle.lacksStatusRatings(target)) {
    return clampStatusChance(configured)
}
```

`lacksStatusRatings()` 只看这个单位是不是「怪物」且 `1032`/`1033` 都是 0。这样既覆盖
真实怪物，又不会误伤两类"有数据"的单位：测试里手工注入过抗性的怪物、以及 PvP 里从
对位玩家拷贝了评分的敌方（`pvp.go` 的 `pvpEnemyUnit`）。PvP 另有 `battle.pvp == nil`
兜底，**从不豁免**。

**反向验证**：回退修复后新增断言直接打印 `配置 18% 被算成 100%` —— 与线上实测吻合。
既有 5 条对抗用例（注入的怪物抗性非零，走"有数据"分支）全部保持通过。

**顺带**：确认了玩家与怪物的节拍本身**互相独立**（怪物 `monsterReadyAt`、玩家
`battleActionReadyAt`），实测玩家在怪物被沉默的那些回合仍然每 6 秒出手一次，
一次不漏。只有**自动出手**会被并进怪物那一波（有意的批次合并）。
清理掉了一个从不被读取的死字段 `pendingBattleSkillID`（它的注释声称"排队等共享
6 秒回合"，而那套机制早已不存在），提交 `27d6713`。

**关于"怪物对我的中毒概率偏高"**：不是缺陷。500010 的中毒配置就是 **60% 几率 /
26 秒**（文案也这么写），只是 §8.5 之前它被压到 6%，修完还回 60%（**10 倍**），
所以体感变化明显。另外 **26 秒是同类里最长的一档** —— 流血 10–11 秒、燃烧 10–14 秒，
中毒只有 26 秒这一个取值。按技能组 10030 里 500010 占 2/7、每 6 秒一波估算，
平均 21 秒放一次 × 60% → 约 35 秒挂一次、持续 26 秒 ⇒ **覆盖率约 74%**。

### 8.8 最终修复：量纲（`Hit`/`Res` 不是比率型字段）

**根因**：`ratioNumericType()` 把 `1032(Hit) / 1033(Res)` 当成"比率型"字段 ×100。
四条独立证据说明它们是**整数点数**：

| # | 证据 |
| --- | --- |
| 1 | `EquipBase` 里真正的比率字段取值 **0.005–0.9**（`Pcrir`/`Mcrir`/`Dvo`/`Rpcri`/`Nphyi`…），而 **`Hit`(1–200) / `Res`(1–170) 与 `PhyAtk`/`PhyDef`/`Hp` 一样是整数点数** |
| 2 | 客户端把小数显示成百分比的工具 `GetFloatPercent` **只覆盖到「辅助值」**，`Hit`/`Res` 不在名单里 |
| 3 | 线上抓包（3 份）里比率字段**全部以小数下发**（`Dvo=0.05266`、`Pcrir=0.30`、`Pcri=0.48`），而 `1031/1032/1033` **一次都没出现过** |
| 4 | 服务端内部两条路径**自相矛盾**：整数路径 `baseAttribute` 对玩家返回 `191.29`，百分比路径 `basePointAttribute` 返回 `19129` |

×100 造成的后果（实测）：怪物 → 玩家 `0 ÷ 1560` ⇒ **6%**；玩家 → 怪物 `19129 ÷ 0` ⇒ 放大 **192 倍** ⇒ 配置 18% 被夹成 **100%**。

**改动**（提交 `57647a7`）：

1. `ratioNumericType()` 去掉 `1032`/`1033`（保留 `1013–1023`，那些确实是比率）；
2. 对抗的豁免**只看目标**（`lacksStatusRatings(target)`）——目标是怪物（没有抗性数据）时按配置几率；
   目标有抗性（玩家）时正常对抗。`battle.pvp == nil` 兜底保留，**PvP 从不豁免**。

**客户端不受影响**：下发给客户端的快照走 `playerExtraNumeric()`，本来就不含这个 ×100。

#### 参与矩阵（用运行中的真实代码实测，配置 60%）

| 场景 | 实际 | 参与的属性 |
| --- | --- | --- |
| PvE 怪物→玩家（毕业装 Res 245.6） | **17.4%** | ✅ **玩家抗性**；怪物命中恒 0 不参与 |
| PvE 怪物→玩家（抗性改成 500） | 10.0% | ✅ 抗性越高越低 |
| PvE 玩家→怪物（命中 191.29） | **60.0%** | ❌ 命中、抗性**都不参与**（按配置原值） |
| PvE 玩家→怪物（**命中改成 5000**） | **60.0%** | ❌ **一丁点都不变** |
| PvE 玩家→怪物（给怪物注入 500 抗性） | 29.1% | 机制仍在，只是**真实怪物没有抗性数据** |
| PvP（敌方带玩家拷贝的评分） | 50.6% | ✅ 命中和抗性**都参与** |
| PvP（敌方命中改成 5000） | 100.0% | ✅ 命中生效 |

**一句话结论**：
- **玩家 → 怪物**：只看配置概率，**不看命中、不看抗性**
- **怪物 → 玩家**：看**玩家抗性**（`配置 × 100/(100+抗性)`），**不看命中**（怪物命中恒为 0）
- **PvP**：命中和抗性**都参与**

> **这一整套"谁参与判定"的口径已单独整理成 [33-属性对抗与状态命中判定](33-属性对抗与状态命中判定.md)，**
> 含参与矩阵、数值来源、暴击（另一条路径）、以及遗留项。本文只保留"怎么查出来的"。

#### 顺带更正：`Dvo` 不是「闪避」

排查中发现 `ET.NumericType.Dvo = 1017` 这个名字容易误导。客户端另一张表 `Cal.AttributeType`
把同一个槽位叫 **「辅助值」**（19），装备 tooltip 也显示 `辅助值:{0:p2}`，服务端正是把它当
治疗加成读（`battle_treatment.go` 的 `CombatAttributeAuxiliary → 1017`）。
佐证是量级：`EquipBase.Dvo` 取值 0.005–3.8，当闪避意味着最高 **380% 闪避**（荒谬）。
**客户端枚举里没有闪避成员，服务端也没有任何闪避判定**；攻击命中走的是「命中(1032) vs 抵抗(1033)」。
详见 `文档/11-背包装备与线上数值.md` §2.5 的命名更正。
