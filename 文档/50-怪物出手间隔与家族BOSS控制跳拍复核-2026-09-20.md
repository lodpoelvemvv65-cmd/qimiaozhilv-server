## 1. 结论

玩家与怪物使用同一个“速度换算为公共间隔”的函数：

```text
interval_ms = clamp(round(6000 - Speed), 4000, 6000)
```

两者的 **Speed 来源不同**：

| 对象 | Speed 来源 | 当前结果 |
|---|---|---:|
| 玩家 | 完整数值链 `NumericType 1031` | 抓包已有 6000 / 4746 / 4554 / 4000ms |
| 普通怪物 | 当前两组线上样本拟合 `round(MonsterBase.Level * 0.045)` | Level 10 -> 6000ms；Level 7600 -> 5658ms |
| 家族 BOSS | 家族战独立实测网格 | 4710ms |

普通怪物的 `0.045` 是根据当前两个等级样本拟合的服务端公式，不是从线上服务端源码恢复的常量。家族 BOSS 不能直接套 Level 公式：五阶 `50005` 的实测约为 `4706.68ms`，当前运营配置按抓包精度取 `4710ms`。

## 2. 普通怪物抓包证据

### 2.1 Level 7600 样本

抓包 `online-skill-effects-20260906.pcapng` 中：

- `20050 M2C_MainStoryMonsterInfo` 一次下发 10 个怪物，嵌套 `MonsterUnitInfo.MonsterId` 均为 `10161`；
- 原版表 `MonsterBase[10161].Level = 7600`；
- 10 个单位每拍同时发送 `20075`，技能均为 `500001`；
- 每个单位连续 25 次施法，共 24 个相邻间隔；
- 平均 `5657.732ms`，最小 `5655.285ms`，最大 `5660.097ms`；四舍五入后的主峰是 `5658ms`（9 次）。

计算：

```text
Speed = round(7600 * 0.045) = 342
interval = 6000 - 342 = 5658ms
```

十只怪始终同拍，且连续 25 拍没有整拍缺失，因此该样本没有被单体控制效果扭曲。

### 2.2 Level 10 样本

最初主线怪物 `10001` 的原版表等级为 10，抓包连续间隔为 6000ms：

```text
Speed = round(10 * 0.045) = 0
interval = 6000ms（上限）
```

这两个样本支持“相同换算函数、不同 Speed 来源”，但仍需更多普通怪物等级样本检验 `0.045` 是否全表恒定。

## 3. 家族 BOSS 是否被控制干扰

会干扰“相邻两次施法直接相减”，但不会改变基础网格。

五阶家族 BOSS 单流共有 62 次施法、61 个相邻间隔：

| 间隔类型 | 数量 | 含义 |
|---|---:|---|
| 约 4.71s | 51 | 正常一拍 |
| 约 9.41s | 7 | 控制期间跳过一拍 |
| 约 14.12s | 3 | 控制期间跳过两拍 |

线性网格拟合周期为 `4.706684684s`。典型长间隔：

```text
82.189 -> 91.603   = 2 拍
91.603 -> 105.723  = 3 拍
133.964 -> 148.084 = 3 拍
```

本场玩家反复使用会造成眩晕、冰冻、沉默或石化的技能，包括 `210401`、`110304`、`410202`、`410303`、`410503`、`410603`。长间隔落在这些控制窗口内；控制结束后，BOSS 继续落在原来的 4.71s 网格上，没有从解除时刻重新起算。

因此正确模型是：

```text
到达 BOSS 网格点 -> 先占用该拍 -> 若当前不能施法则跳过 -> 下一拍仍沿原网格
```

不能用长间隔的 9.41s 或 14.12s 作为 BOSS 基础间隔，也不能在控制解除时重置计时器。

### 3.1 修复前本地日志复核

`server-mysql/logs/runtime/local-20260920-095541.stderr.log` 同时暴露了两个因素：

- 旧二进制中的 BOSS 起手时间为 `09:57:14.050 / 20.050 / 26.050 / 32.050 / 38.051`，严格每 6 秒一次，证明旧服务端确实仍在使用错误的固定 6000ms；
- `09:57:20` 的 BOSS 已进入 start，但 `09:57:21` 前摇结束时以 `source_cannot_cast_before_launch` 取消，说明前摇期间受到控制；
- `09:57:38 -> 09:57:50` 间隔 12 秒，中间一整个 6 秒旧网格点没有 start，说明到拍时 BOSS 已处于不能施法状态。

因此本地看到的“慢”和“不齐”不能只归因于一个问题：旧代码的 6000ms 基础周期需要修复，而控制导致的整拍跳过是应保留的线上行为。本提交只把基础周期改正确，不会让受控 BOSS 强行出手。

## 4. 服务端修改

- 普通怪物不再固定为 6000ms；从当前战斗怪物的 `MonsterBase.Level` 拟合 Speed，再走与玩家相同的 `6000-Speed` 和 4000~6000ms 边界。
- 家族 BOSS 使用 `Gameplay.FamilyBoss.AttributeStackIntervalMS`，当前为 4710ms。
- 怪物回合时间戳计算与下一窗口推进统一调用同一函数，避免展示时间与权威窗口不同步。
- 控制导致不能施法时仍消耗当前网格点，解除后不会产生相位漂移。
- 配置表或怪物行缺失时保守回退 6000ms。

当前架构是一场战斗共享一条怪物波次时钟，因而取本场首个有效怪物行计算间隔。当前线上普通怪物样本为同 ID、同等级、同拍阵容；混合等级阵容尚无线上样本，不宣称已闭环。
