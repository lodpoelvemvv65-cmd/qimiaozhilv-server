## 4. 【已定位 / A1】家族BOSS「治疗量」把被动回血算成了治疗

### 4.1 现象

面板「治疗量」在**没有任何治疗职业、没有任何治疗技能被释放**的战斗里，
出现 4.9 亿量级的数字，且与伤害量完全不成比例：

| uid | 攻击命中 | 伤害量 | 治疗量 | 治疗/命中 | 占血上限 |
|---|---|---|---|---|---|
| 2 | 303 | **303** | **72,087,151** | 237,911 | 0.66% |
| 3902 | 218 | 218 | 34,465,088 | 158,096 | 0.98% |
| 3903 | 291 | 409 | 42,283,194 | 145,303 | 1.51% |
| 3904 | 38 | 1,895,115,729 | 493,452,788 | 12,985,599 | 113.94% |
| 3905 | 170 | 104,883,341 | 36,497,414 | 214,690 | 2.36% |

**打出 303 点伤害的角色记了 7208 万治疗量** —— 这不可能是队友治疗。

### 4.2 根因（代码链路）

| 文件:行 | 内容 |
|---|---|
| `battle_effects.go:1211` | `ApplyHealthRecovery` → `applyHealInternal(ref, ref, amount, CombatEventHeal, ...)`，即 **自己→自己** 的 `CombatEventHeal` |
| `battle_monster_attack.go:250` | 每次攻击波落地后调用 `ApplyHealthRecovery(cast.source)` |
| `battle_skill_runtime.go:229` | 非延迟技能释放后同样调用一次 |
| `battle_skill_events.go:27-31` | 统计条件仅 `source.Side == 玩家 && target.Side == 玩家` → 自我回血**正好通过** |

```go
// battle_skill_events.go:27-31
if (event.Type == CombatEventHeal || event.Type == CombatEventLifesteal) &&
    event.Source.Side == CombatSidePlayer && event.Target.Side == CombatSidePlayer {
    recordFamilyBossTreatment(ch.session.familyID, bossID, event.Source.ID, event.Amount)
}
```

`battle_effects.go:1211`：

```go
func (r *CombatRuntime) ApplyHealthRecovery(ref CombatUnitRef) ([]CombatEvent, error) {
	percent := r.numericPercentValue(ref, 1044)   // 1044 = HpRecover 生命回复
	amount := percentAmount(int64(maximum), percent)
	return r.applyHealInternal(ref, ref, amount, CombatEventHeal, r.clock.Now())
}
```

**旁证**：`family.go` 内 `encodeBossDamageRankWithParticipation` 的注释自述该榜本意是
*"a healer can restore a teammate"*，自我回血不属于该语义。

### 4.3 附带事实

- ⚠ **下面这条已于 2026-09-18 被推翻**（`[combat.attack]` 的 `uid=` 是 wave.origin 会话、
  且它只记录"攻击波"，非伤害技能走另一条日志）：~~全场只出现过 4 个技能：100001 / 200001 /
  300001 / 400001，全部是各职业普攻，没有任何 `SkillOption_治疗` 技能被释放。~~
  实际护士放了 310301×63 / 310401×63 / 310501×63 / 310504×62 / 310601×62，
  见 §17.1。
- 全配置树里 `SkillOption_吸血` **只有 1 处**，挂在技能 **200001（运动员普攻）** 的
  modifier 上（节点 387670，`iconDesc=吸血`）。也就是说吸血只可能来自运动员（3903），
  但 3903 的伤害量只有 409，无法解释其 4228 万治疗量。
- 回血**不会溢出**：`applyHealInternal` 把 `actual` 限制在"已损失血量"以内；
  `recordFamilyBossStat` 在 `previous + amount` 超过 `MaxInt32` 时饱和截断，
  不会回绕成负数。

### 4.4 建议修法

`battle_skill_events.go:27` 条件追加 `event.Source != event.Target`，
把自我回血与自我吸血排除，只保留真正作用于队友的 `CombatEventHeal`。
影响面最小、可单测覆盖。

## 5. 【待确认 / B1】反伤对周期性伤害不生效

### 5.1 配置

```
skillEventDic → SkillOption_应用Modifier (uniqeId=12)
    modifierId = 50003228    selectTarget = SelectSingleTarget targetType=0 (自身)
modifierDic → 50003228 (节点 411030)
    effectId = 3028, stateK = 101, iconId = 0, name = (空)
    modifierEventDic → SkillOption_反伤 (节点 411053, uniqeId=14)
        param { skillSourcetype = 2 }
        selectTarget = SelectSingleTarget targetType=3
```

即：BOSS 给自己挂「反伤」，谁打它谁受伤。

### 5.2 问题

`battle_effects.go:1121` 的守卫把周期性伤害排除在反伤之外：

```go
if actual > 0 && !request.Periodic && !request.Reflected {
```

- `!request.Reflected` 是必要的（防止反弹无限递归）
- **`!request.Periodic` 没有注释解释、没有单测锁定、文档中亦无记录**

**反伤的作用范围（由这段守卫决定，实测已印证）：**

| 伤害类型 | 是否触发反伤 |
|---|---|
| 普通攻击的直接伤害 | ✅ |
| **技能的直接伤害** | ✅（和普攻走同一条 `applyDamageInternal`，**不区分是不是普攻**） |
| 反击（`counter=true`）的伤害 | ✅（守卫里**没有** `!request.Counter`） |
| **周期性伤害（DoT / 中毒跳伤）** | ❌ 被 `!request.Periodic` 挡掉 |

> 所以早期"反伤是不是只能反普攻"这个疑问，答案是：**不是** —— 反伤对
> **所有直接伤害**（普攻 / 技能 / 反击）一视同仁，**唯一被排除的是持续性伤害**。
>
> 另外两条实测副产物：
> 1. 反弹值按 `actual` 算（即**护盾吸收和血量钳制之后**的实际掉血），不是按名义伤害；
> 2. 反弹出去的伤害**不会再次被反伤**（`!request.Reflected`）。

**186 次挨打全部被盾完全挡下，一次都没掉血。** 这就是"全程没死过"的来源。

对照组：`party-down` 记录里 **3903（20:08:06）和 3905（20:11:54）确实被打死了** ——
他们是被 30000114 / 50001033 的**持续伤害**磨死的（真实伤害按最大生命值百分比，
一跳对 959 万血的 3903 约 147 万），而不是被 BOSS 的普攻打死的。

### 10.3 机制拆解（都是原版配置，服务端照表实现）

| 机制 | 配置出处 | 效果 |
|---|---|---|
| 军官普攻给**全体友军**上盾 | `100001` → `modifier 10000113 护盾`，应用时 `SelectMultiTarget` + `teamType = 2`（友方）；`treatCalculate_Target: calculateType=2`（按目标最大生命值） | 每回合一次，全队刷新；`stackMode` → `CombatEffectReplace`（刷新而非叠加） |
| 每次攻击后自我回血 | `battle_effects.go:1211 ApplyHealthRecovery`，读数值属性 **1044 HpRecover**；触发点 `battle_monster_attack.go:250`（攻击落地）+ `battle_skill_runtime.go:229`（技能释放） | 每个号每回合回一截，累计 4~12 倍血上限 |

**这两条都不是服务端的实现错误**：`10000113` 的目标选择器在原版表里就写着
`teamType = 2`（友方），`1044` 也是线上 NumericType。问题在于：

1. 5 阶 BOSS 的 `PhyAtk`（240 万）跟玩家的血上限（900 万 ~ 3600 万）比太低，
   而玩家一边有"每回合刷新的全队盾"、一边有"每次攻击都回血"，**受到的伤害来不及累积**；
2. 反过来玩家的攻击力又低于 BOSS 的 `PhyDef`（209 万），**打不出伤害**。

**即：这场战斗里"打不动 BOSS"和"自己死不了"是同一件事的两面 —— 都是
`max(1, atk − def)` 这个先扣防公式把双方的攻防差放大成了两个极端。**

## 11. 回血到底从哪来 —— 逐来源排查

问：面板上"治疗量"动辄几千万，**真的能加这么多血吗？这个治疗是从哪里来的？**

### 11.1 服务端里所有会产生治疗/回血的路径

| 路径 | 代码位置 | 数值来源 |
|---|---|---|
| 被动回血 | `battle_effects.go:1211 ApplyHealthRecovery` | `numericPercentValue(ref, 1044)` = **HpRecover 生命回复** |
| 吸血（触发式） | `battle_skill_runtime.go:1085` → `applyTriggeredReactive` | `SkillOption_吸血`（全配置树**只有 1 处**，挂在技能 200001 运动员普攻上） |
| 吸血（静态） | `battle_effects.go:1175 staticLifestealPercent` | 数值 **1042**（几率）+ **1043**（量），**两者必须同时 > 0** |
| 治疗技能 | `battle_skill_runtime.go` `SkillEffectHeal` | `SkillOption_治疗`（全配置树 9 处） |

### 11.2 逐来源排除

|---|---|---|

### 11.3 唯一来源：星魂副属性 1148

`StarSoulAttributeConfig.json`：

```json
{"_id": 1146, "Key": 27, "Value": 0.008 }   // 吸血几率 → 1042
{"_id": 1147, "Key": 28, "Value": 0.01  }   // 吸血量   → 1043
{"_id": 1148, "Key": 29, "Value": 0.0125}   // 生命回复 → 1044   ← 就是这个
```

`starsoul.go:starSoulBonus`：`out[1044] += Value × (1 + 副属性加成) × 品质系数`
`starSoulQualityCoefficient`：品质 ≤2 → 0.48，≤4 → 0.8，否则 1.0
`numericPercentValue`：最终百分比 = 原始值 × 100

这 5 个号**装备中**带 1148 的星魂（2026-09-18 复核后的正确值）：

| uid | 装备中的回血星魂 | 1044 原始值 | 每次攻击回血 | 血上限 | 单次回血量 |
|---|---|---|---|---|---|
| 2（军官） | 1148 ×1（品质 6） | 0.0125 | **1.25%** | 35,891,804 | **≈ 448,648** |
| 3902（军官） | 1148 ×1（品质 6） | 0.0125 | **1.25%** | 16,162,257 | **≈ 202,028** |
| 3903（运动员） | 1148 ×1（品质 6） | 0.0125 | **1.25%** | 9,593,673 | **≈ 119,921** |
| 3904（护士） | 1148 ×1（品质 6） | 0.0125 | **1.25%** | 11,396,474 | **≈ 142,456** |
| 3905（超人） | 1148 ×1（品质 6） | 0.0125 | **1.25%** | 9,116,034 | **≈ 113,950** |

> ⚠ **2026-09-18 复核更正（本节原表 3902/3905 两行是错的）**
>
> 原文用 **`pos_type > 0`** 当"已装备"的判据，但 `pos_type` 是**星魂自身的部位属性**（0..11），
> 背包里的星魂同样有 `pos_type > 0`。**真正的装备判定是 `player_star_soul_slots` 连接**
> （`normalized_store.go:loadStarSoul` 就是先读 `player_star_souls`、再读 slots 表来置 `IsUsed`）。
>
> 按 slots 表重查（`server-mysql` 本地库，5 个号各 12 件装备中星魂、**类型全是 1001、品质全是 6**）：
>
> ```
> 2    1148 ×1 q6+0
> 3902 1148 ×1 q6+0      ← 原文写成 "1148×1(品质6) + 1148×1(品质2)"，那条品质 2 的星魂在背包里
> 3903 1148 ×1 q6+0
> 3904 1148 ×1 q6+0
> 3905 1148 ×1 q6+0      ← 原文写成 "1148×1(品质6) + 1148×1(品质4)"，那条品质 4 的也在背包里
> ```
>
> **所以 5 个号一律是 `0.0125 × 1.0 × 1.0 = 1.25%`**，原文 3902 的 2.45% / 395,975 与
> 3905 的 3.25% / 296,271 均作废（`(1+viceAdd) × 品质系数` 的公式本身无误，
> 错的是"哪些星魂算装备中"）。
>
> **总结论不变**：回血来源唯一 = 星魂副属性 `1148`，且按**最大生命值**百分比结算。

**与实测吻合**：日志里实测的"回血/命中"平均值（表在 §10.1）
是 0.66% / 0.98% / 1.51% / 2.36% —— 全部**低于**上表的额定值，
符合 `applyHealInternal` 的"回血上限 = 已损失血量"（满血时回 0，把平均值拉低）。

### 11.4 结论

1. **不是"一次加很多血"**，是 **每一次普攻都回 1.25% ~ 3.25% 的最大生命值**，
   一次几十万；30 分钟打 200~300 次，累加就是几千万。
   面板上 a12312303 的 4.9 亿治疗量是这个累加值（且是**当天跨场次累计**，见 §7.1）。
2. **来源只有星魂副属性 1148 一条**：装备、宝石、转生、宠物、星魂套装、吸血、治疗技能
   全部排查过，一条都不产生回血。
3. **触发频率存疑（待确认）**：`ApplyHealthRecovery` 挂在
   * `battle_monster_attack.go:250` —— **每一次攻击落地**
   * `battle_skill_runtime.go:229` —— 每一次非伤害技能释放

   而且**反击也算一次攻击**（`cast.counter` 的 wave 同样走 250）。
   也就是说"生命回复"在服务端是**按每次攻击落地**结算。
   （本游戏一回合一出手，所以"每次攻击"与"每回合"在正常流程里等价，
   多出来的只有反击那 14% —— 详见 §12.3 的勘误与实测数据。）

## 12. 深挖：生命回复 ≠ 吸血；以及触发频率的取证结果

### 12.1 "普攻只打 1 点，凭什么回 44.9 万血"——因为这是两条不同的属性

`NumericType` 里这一组是**三个独立属性**，语义完全不同：

| 属性 | NumericType | 语义 | 服务端实现 |
|---|---|---|---|
| `SuckR` 吸血几率 | 1042 | 触发概率 | `staticLifestealPercent` 的 `chance` |
| `SuckV` 吸血量 | 1043 | **按「造成的伤害」的百分比**回血 | `staticLifestealPercent` 的 `amount` |
| `HpRecover` 生命回复 | 1044 | **按「自身最大生命值」的百分比**回血 | `ApplyHealthRecovery` |

**打 1 点伤害只影响 1043（吸血量），跟 1044（生命回复）无关。**
`1044 = 1.25%` 时，35,891,804 血的军官每次攻击回 `35,891,804 × 1.25% = 448,648`，
**跟他打出去多少伤害一点关系都没有**。

而且这 5 个号的 **1042 和 1043 没有同时非零**（见 §11.2），
`staticLifestealPercent` 要求两者都 > 0 才生效 → **全场零吸血**。
所以"打 1 点就该回 1 点"那条路本来就没被触发。

### 12.2 线上抓包实证：线上**不封顶**，客户端看到的大数字是"名义治疗量"

`参考数据/抓包归档/online-skill-effects-20260906.pcapng`
（线上服，玩家 unit=24295，护士技能）：

* 玩家最大生命值 **5,885,730**，整场 `20169 numeric=1001` **一直等于 5,885,730**（满血，全程没掉）；
* 玩家释放技能 12 次（310401×5、310501×3、310601×2、310101×1、300001×1）；
* 玩家身上收到 **19 条正数 `20078`（治疗帧）**，例如
  `+1779371`、`+2339689`、`+2565879`、`+2141074`、`+2094263` …

**关键点：血量一直是满的，线上照样把 `+1779371` 这种大数字下发给客户端。**
也就是说**线上不会把治疗量按"已损失血量"截断** —— 客户端飘出来的那个大绿字是
**名义治疗量**，血条一点都没动。

> 我们的服务端 `applyHealInternal` 会把 `actual` 限制在"已损失血量"以内，
> 满血时回 0，`recordFamilyBossStat` 也会因为 `amount <= 0` 直接跳过。
> **所以我们的"治疗量"口径比线上显示更保守，不存在"靠溢出治疗刷榜"。**

另外这 19 条治疗帧的数值**每条都不同**（1.2M ~ 2.6M），
说明它们全是**技能自身的治疗**（`SkillOption_治疗`），
**该角色 `HpRecover = 0`** → 这份抓包观测不到生命回复的频率。

### 12.3 "每次攻击触发"和"每回合触发"其实是一回事

**这游戏一回合一出手**，每个回合必然有一次出手，所以"攻击落地 → 回血"和
"回合 → 回血"在正常流程里**完全等价**。

真正会多出来的只有一处：**反击也算一次攻击**，因此反击也会各回一次血
（`cast.counter` 的 wave 同样走 `battle_monster_attack.go:250`）。

实测（`local-server-20260917.log` 原始那场 5 阶 BOSS 战，玩家出手按 reason 分类）：

| 出手类型 | 次数 |
|---|---|
| `automatic_round`（正常回合出手） | **1037** |
| `counter_basic_attack`（反击） | **175** |
| `manual`（手动） | 1 |

**反击多出来的只有 175 次 ≈ 14%。**

> ⚠ **勘误**：本文件早期版本在这里写过"如果线上按回合结算，我们的回血会被放大数倍"。
> 这个说法是**错的** —— 差别只有反击那 14%，不是数倍。

**子结论：触发"次数"基本不是问题。剩下的差别只有两处：**

1. 反击该不该也触发（差 14%）；
2. **更大的一处：线上到底在战斗里触发，还是只在战斗外/挂机时触发。**

### 12.4 真正的未知：战斗内触发 vs 战斗外触发

`HpRecover`（生命回复）这类属性在同类游戏里很常见是**脱战回复 / 挂机回复**。
如果是那样，我们在战斗里每次攻击都回血，性质不是"多算几倍"，
而是"**这一项本来就不该出现在战斗中**"——这是量级差别最大的可能。

**目前能查到的证据：**

| 取证方向 | 结果 |
|---|---|
| 线上抓包 `online-skill-effects-20260906` | 该角色 19 条治疗帧**数值各不相同**（1.2M~2.6M）→ 全是技能治疗，**其 `HpRecover = 0`**，观测不到 |
| 线上抓包 `online-starsoul-boss-effects-20260827` | 该角色被直接打死，**没有任何治疗帧** |
| 线上抓包 `online-battle-effect-exit-20260913` | 帧数太少（14 条 20078），无效 |
| 客户端 | `NumericWatcher_*` 一共只有 15 个，**没有 `NumericWatcher_HpRecover`** → 客户端对 1044 零响应逻辑，只是面板显示，问不出语义 |
| 旧 `server/`（SQLite 版） | **完全没有生命回复逻辑**（只有战斗后的 `applyMagicBallRecover`）→ 当前实现是**新加**的，没有旧实现可对照 |
| 单测 | `TestCombatRuntimeHealthRecoveryUsesMaximumHPPercent` 只锁了**数值**（0.1 → 10% 最大生命值），**没有锁触发时机** |

**全部 4 份含战斗的线上抓包都无法观测**：角色要么 `HpRecover = 0`，要么直接阵亡。

### 12.5 本节结论

| 问题 | 状态 |
|---|---|
| 回血来源 = 星魂副属性 `1148` | ✅ 已确认（§11.3） |
| 数值语义 = 按**最大生命值**百分比，**与造成多少伤害无关** | ✅ 已确认，有单测 `TestCombatRuntimeHealthRecoveryUsesMaximumHPPercent` 锁定 |
| 我们服务端 = 每次攻击落地触发（含反击） | ✅ 已确认（代码两个调用点 + 日志零例外） |
| 线上对治疗量**不做**"已损失血量"截断，客户端大绿字是名义值 | ✅ 已确认（线上抓包：满血仍下发 `+1779371`）。我们的口径更保守，**不存在靠溢出治疗刷榜** |
| "每次攻击" vs "每回合" | ✅ **差别只有反击的 14%，基本不是问题**（本节勘误） |
| **线上是战斗内触发还是战斗外触发** | ❌ **未知，缺证据 —— 这才是关键未知项** |

### 12.6 要给出终局结论，需要哪一种抓包

一份**线上抓包**，同时满足：

1. 角色身上**有 `1148` 星魂**（即 `HpRecover > 0`）—— 高级号基本都有，随机挑一个
   带星魂的号即可；
2. **在战斗中挨打但不会死**（死了就看不到后续回血帧）。

做法：拿这样的号去打一只**打不死自己、自己也不打死它**的低级怪，挂机 2 分钟，
然后看 `20078` 里**正数帧**（治疗）出现的位置：

| 现象 | 结论 |
|---|---|
| 每次自己出手后紧跟一条治疗帧 | 线上面也是战斗中、每次攻击触发 → **我们的实现正确** |
| 完全没有治疗帧 | 线上面**战斗中不触发**（脱战回复）→ **我们需要把 `ApplyHealthRecovery` 从战斗路径移除** |
| 按固定节拍出现、与出手无关 | 线上是按回合/定时器触发 → 需要改触发点 |

现成工具：`server-mysql/test/inspect_combat_capture.py <pcapng>`。

## 15.1 【B4 闭合】治疗量分母 = 全队治疗量合计，"客户端写死"被证伪

# 18. 为什么"回复那么多"、为什么"盾能挡那么多"（2026-09-18 数值溯源）

两个现象都在**原版配置**里，不是实现发挥；下面给出出处、公式与量级。

## 18.1 治疗的公式就在配置里（`SkillOption_治愈` 的 `treatCalculate_*`）

服务端实现（`battle_treatment.go:treatmentAmount`）与配置一一对应：

```
治疗量 = 施法者属性(Self.Stat)   × Self.Percent/100
       + 目标属性(Target.Stat)   × Target.Percent/100
       × (1 + 辅助值(1017)/100)          ← 治疗加成
       × 暴击倍率（暴击时，chance = 暴击率之和）
```

护士的五个来源（`SkillLogicConfig` 原值）：

| 技能 | CD | 自身项 | 目标项 |
|---|---|---|---|
| **300001 护士普攻**「治愈」 | 5.0s | — | **目标最大生命值 × 4%** |
| 310301 急救 | 7.2s | 精神攻击力 × 100/102/106/110/**115%**（Lv1-5） | — |
| 310401 高级急救 | 8.1s | 精神攻击力 × 60/70/80/90/**100%** | Lv5 另挂「目标最大生命值 × 9%」 |
| 310501 连锁注射（HoT） | 9.6s | — | 目标最大生命值 × 1/2/3/**3%**（每跳） |
| 310601 人体学 | 12.0s | 精神攻击力 × 150/152/**160%** | — |

**量级从哪来**：这批测试号血上限 9.1M~35.9M（+20 装备、等级 21.5 万），
于是"4% 上限"= 36 万~143 万、"9% 上限"= 82 万~323 万，一次普攻就回这么多；
护士平均每 6 秒一次出手、一场 30 分钟放 250+ 次治疗技能 → 合计自然到**亿级**。

**线上对照**：线上抓包 `online-skill-effects-20260906` 里，护士在 5,885,732 上限的角色上
打出 `+1,779,371`、`+2,335,689`、`+2,565,879` 等治疗帧 = **30%~44% 上限**，同一量级、
同一公式；`300001` 的 4% 也能对上（线上小号 11,152 血收到 `+595` = 4% × (1+辅助值 33%~45%)）。
→ **不是我们算错，是这套数值本身就这么大。**

（另有星魂副属性 1148 → `1044 生命回复`：**每次自己出手回自己上限的 1.25%~3.25%**，约 45 万/次。）

## 18.2 军官普攻的盾 = 目标最大生命值 × 5%（覆盖式刷新）

`100001 普通攻击` 的配置原文（`SkillLogicConfig`，技能 100001）：

```
skillEventDic[1] → SkillOption_伤害 (modifier 10000112)
    └─ modifierEventDic[0] → SkillOption_几率 (66%)
         succeedOptionList → SkillOption_应用Modifier (10000113 护盾)
              selectTarget = SelectMultiTarget{isRndom=true, minCount=0, maxCount=5,
                                               teamType=2（友方）, flags=1}
         failOptionList    → SkillOption_应用Modifier (10000114 反击)

modifier 10000113「护盾」: iconId=bufficon_shield, stateK=100, attribute=8（可刷新）,
    continueTime=10 秒
    └─ modifierEventDic[0] → SkillOption_护盾
           treatCalculate_Target = {calculateType: 2（目标最大生命值）, value: 5.0}
```

即：**军官每次普攻有 66% 几率，给随机 0~5 个友方（含自己）各套一个
「该目标最大生命值 × 5%」的护盾，持续 10 秒，且是刷新不是叠加。**

为什么"几乎挡掉一切"：

1. 护盾量按**目标自己**的上限算 → uid=2（35.89M）就是 **1,794,590**；
2. 军官每 ~5 秒一次普攻、盾持续 10 秒且可刷新 → 全队**长期顶着新鲜盾**；
3. 而 5 阶 BOSS 打到玩家身上的伤害 = `max(1, 攻 − 防)`：
   物攻 2,400,000 − uid=2 物防 2,268,694 = **76,678**（日志实测值就是这个数）。
   76,678 只占 1.79M 盾的 4% → 一轮打不穿，永远看不到掉血；
4. doc §6.1 那个"合计吸收 4.90 亿"是**30 分钟里约 1000 次刷盾/命中累计**出来的，不是一次挡了 4.9 亿。

> 盾和治疗共用同一条公式（都走 `treatmentAmount`），所以两者的量级观感一致；
> `treatCalculate_Target.calculateType` 的 0/1/2/3 = 物理攻击/精神攻击/目标最大生命/持当前生命。

## 18.3 结论一句话

- **治疗大** = 原版配置「按 % 结算 + 目标最大生命值项」，叠加在这批号 9M~36M 的血上限上；
- **盾硬** = 原版配置「5% 目标上限 + 每回合刷新」，而 BOSS 的实际单次伤害被 `攻−防` 压到 7.7 万；
- 我们能自己决定的只有 §17.3 那条（生命上限 buff 到期是否立刻夹血）与 A1 的口径（已修）。

## 18.4 实测：那个 5% 到底是多少（2026-09-18，干净服务端 + 只读日志）

## 18.5 【有争议】「5%」是**盾的额度**还是「打 100 变 95」的百分比减伤（2026-09-18）

> ⚠ **本条是争议项，不是定论**。两种读法都列出来，谁也没拿到线上运行时样本；
> 现行实现按"额度"做，但用户的读法（"5% 减伤"）同样能用配置字段名解释，见下表。

| | **A：额度池（现行实现）** | **B：百分比减伤（用户读法）** |
|---|---|---|
| 配置读法 | `treatCalculate_Target{calculateType: 2（目标最大生命值）, value: 5}` → 先算出**一个绝对量**（目标上限×5%），当作可被伤害消耗的池 | 5 = 减免 5%，怪物打 100 → 到身上 95 |
| 支持证据 | ① 节点类型是 `SkillOption_护盾`，而"减伤"在本作是**另一套属性**（`NumpyType 1045 PhyDA/1046 MicDA` = 物理/精神**增伤**，`1022/1023 Nphyi/Nmeni` = 物理/精神**免伤**），护盾不在这条通道上；② 客户端有 `Common_pbHpAndShield{m_shield}` + `SetMaxShield/SetHpAndShield`，把护盾当"叠在血条上的额外血"画（`血条宽=hp/(hp+shield)`），百分比减伤没有绝对量可画；③ 实测 `requested=3,001,300 → absorbed=1,500,950 → actual=1,500,350`，只有池子能解释；④ uid=2 那 186/186 次"完全挡下（actual=0）" | 文案 `护盾，可以减少一定伤害` 里的"一定"可读作"一定比例"；"每回合给随机 0~5 个友方各加 5% 上限的额度"效力偏强（等效每人 +5% 血且每 5 秒刷新），直觉上不太合理 |
| 反证/疑点 | 若真按"每回合刷新 5% 上限的池"，在低攻 BOSS 面前等于**永久免伤**（§19 会算清楚这条链） | 与 `treatCalculate_*` 这套"先算数值"的字段语义冲突；也解释不了 `absorbed` 这个量 |
| 定案需要 | **线上录屏/抓包**：一个"身上有护盾、连续挨打"的样本 —— 看伤害是否在某一击之后突然恢复全额（池子破）还是每击都少 5%（减伤） | 同左 |

> 现行实现按 A。**要不要改成 B 需等证据**；本文不把 A 当已证实结论。

## 19.3 那为什么"盾在就永远打不动"——把这批测试号的数字摊开看

链条（全部用实测/配置值）：

1. BOSS 5 物攻 **2,400,000**；uid=2 物防 **2,268,694** → `max(1, 攻−防) = **76,678**`
   （09-17 日志里 uid=2 挨的伤害实测就是 76,678），再乘 `(1 − 玩家物理免伤)` 只会更低；
2. 盾 = 目标上限 5% = **1,794,590** → 一击只吃掉盾的 **4%**；
3. 军官每 ~5 秒一次普攻就会把盾**刷新**（§18.2），而 BOSS 每 ~6 秒才打一次
   → **刷新速度 > 消耗速度**；
4. 就算漏了 7.7 万进血，`1044 生命回复`（uid=2 每次出手 = 1.25% × 上限 = 448,647）立刻补满。

四条叠加 = "打不动"。**其中没有一条来自 BOSS 属性配错，全部来自这批号的数值**：
它们是 clone 出来的 **转生 3、阶段等级 193,501（是 BOSS Level 31,500 的 6 倍）、12 件 +20 满强化**。

**对照设计意图的量级**（文档 27 §8.1 的"达人 4"怪）：怪物精攻 188,888 / 玩家精防 117,394
= 防御只占攻击的 **62%**，于是单次伤害 `(188888−117394)×200% = 142,988` 是有威胁的。
我们这边 `226.9万 / 240万 = **94.5%**` —— 防御几乎顶到 BOSS 攻击，伤害自然塌成 1 点量级。

**换成正常练度的号**（例：防 20 万、血 100~200 万）：BOSS 一击 `(240万−20万)` 再乘免伤，
远大于 5% 上限的盾（5~10 万）→ **盾一击就破，第二击掉大血**。
所以"盾"并没有把这个游戏变成永久免伤；是我们的号把 BOSS 压成了蚊子。

## 19.4 本节结论

- **BOSS 5 的属性配置没错**，服务端也基本用全（唯一漏项 `CharacterAdd`，待取证）；
- "打不动"是**战力比**问题：`我防≈BOSS攻` + `盾>单次伤害` + `盾刷新>消耗` + `1044 回血兜底`；
- 若要恢复 5 阶 BOSS 的威胁感，应调的是**测试号（或确认 `CharacterAdd`）**，不是改盾模型、也不是改 `MonsterBase`；
- 与 §18.5 的争议**互相独立**：即使盾改成"减伤 5%"，在 76,678 这个量级上照样打不动。

# 21. `FamilyBossConfig.CharacterAdd` 到底是什么（2026-09-18 取证记录）

## 21.1 能确定的（已核实）

## 21.2 候选语义（三种，全部是推断，按名字+量级排序）

| # | 读法 | 5 阶 Boss 会变成 |
