## 五、SkillConfig 的两个层次（以及 `Args*` 为什么不能当比对源）

`SkillConfig` 共 538 行 / 130 个技能，每技能一行**基础行**加若干**逐等级行**，键 = `技能ID × 100 + 等级`：

| 层次 | 键 | 内容 |
| --- | --- | --- |
| 基础行 | `11030100` | `Name`、技能总述 `Desc`、`CD`、`CastType/CastValue`、`MaxLevel`、`PreSkillId`、`EffectId`、`HurtEffectId`、`Icon` |
| 逐等级行 | `11030101`…`11030105` | 该等级的 `Desc`（带具体数值，就是面板上显示的那句）+ 同行 `Args0`…`Args10` |

**`Args*` 不能作为比对源**（文档 30 的这条结论在等级行上同样成立），实证：

| 技能 | 自己的 `Desc` 说 | 同一行 `Args*` 却是 | 说明 |
| --- | --- | --- | --- |
| 致命打击（110503） | Lv1-4 文案：当前生命值 1/2/4/7% | 同一行 `Args0` = 10/14/17/19 | 逐项比 110501 铜墙铁壁的 `Args0`（11/15/18/20）**小 1**，跨技能串行 |
| 双面镜（310604） | Lv1-3 文案：攻击力 +25/30/35% | 同一行 `Args0` = 23/32/48 | 与自己的 Desc 冲突 |
| 风火双龙弹（110603） | Lv1 文案：最大生命值 2% | 同一行 `Args0` = 30 | 与自己的 Desc 冲突 |
| 殊途同归（110602） | Lv1 文案：20%【反伤】 | 同一行 `Args1` = 210 | 与自己的 Desc 冲突 |
| 普通攻击（400001） | 超能力普攻文案 193% | `Args1` = 188 | 与自己的 Desc 冲突 |

任何“按 `Args*` 批量改数值”的做法都会引入新错误；要改只能照分等级 `Desc` 手抄。

>    而 110503 的 `Args0`（10/14/17/19）与它是**逐项差 1**，不是“几乎对应”。已按实际值改正。
> 2. “不能作为比对源”这句的**适用范围被本轮全局复核收窄**：404 条带百分数的等级行里，
>    **315 条** `Desc` 百分数能在同一行 `Args` 里找到、**89 条**找不到。也就是说 `Args*` 并非
>    “整列串行”，而是**部分技能逐行对得上、部分技能错**：
>    - 对得上的例子：110302（142/144/146/148/150）、110303、110304、110203/110204 等，`Args0` 逐项等于自己 `Desc` 的主数值；
>    - 对不上的例子：110501、110503、110502、110401、110601/110602/110604（`Args0` 恒为 5，是“5 个友方”而非数值）等。
> 3. 结论不变、而且更硬：`Args*` **既不能整体信、也不能整体弃**，该行 **`Desc` 才是该行文案的唯一来源**；
>    判定技能时用「该行 `Desc`」对照 `SkillLogicConfig` 两两核对即可，不要引入 `Args*` 做中间量。
> 4. 本条可复跑：`python _test_runs/skill-description-audit-20260915/recheck_args_vs_desc.py`
>    （只读 `datatable_json/SkillConfig.json`，输出同目录 `recheck_args_vs_desc.txt`）。

## 六、判定基准（避免再次混淆）

- 问“**是否与原版客户端一致**” → 比客户端 `SkillLogicConfig`。服务端跑的就是它，所以 A 类是服务端偏离了配置，B 类是配置本身就与文案不符。
- 问“**是否与描述一致**” → 比客户端 `SkillConfig` 的等级行 `Desc`。B 类问题全部出在这一层。
- B 类三条可选路径：(a) 保持原版【本项目选择】；(b) 改客户端文案（走文档 25 的补丁/回滚流程）；(c) 逻辑也按文案改（**明确偏离原版**，需产品决策）。
- 若将来要动 B 类中的 `teamType`（310604 / 410404），工程上只需加一张**技能级**定点覆盖表（仿 `skill_logic.go` 的 `onlineModifierLevelOverrides`，那条表目前只覆盖 modifier 级），落点在 `Plan()` 的 `TeamType` 赋值与 `battle_skill_runtime.go` 的友/敌主目标判定；但需先实测客户端是否允许给这两个技能选中队友。

### 7.2 为什么 B10/B11 不能"照文案改"就完事 —— 客户端卡死在第一步

反汇编客户端 `Hotfix.dll` 的 `ET.ClickBattleTargetEvent`（`MoveNext`）得到的事实：

```
IL_0032  ldfld  args.unitType                 // 点到的单位类型
IL_0039  ldc.i4.4  beq  → C2M_SelectEnermy     // UnitType.Enermy    = 4
IL_003d  ldc.i4.5  beq  → C2M_SelectTeamMember // UnitType.TeamMember = 5
IL_0043  br        → 其它类型：什么都不做
```

`ET.UnitType = { None=0, Player=1, Monster=2, OtherPlayer=3, Enermy=4, TeamMember=5, NPC=6, MapMonster=7 }`；
`GlobalVariable.SelectBattleUnitId` 是客户端记录"当前点中的战斗单位"的字段，作为 `Id` 发出去。

**客户端是「按点到的单位类型」分派的，从头到尾没有读过 `teamType`**。服务端同样按收到的 RPC 分流：

| 收到 | 处理函数 | 落点 |
| --- | --- | --- |
| `C2M_SelectEnermy`(20071) | `battle_actions.go:803 onSelectEnermy`（目标必须存在于 `b.monsters`） | `battle.selectedID` |
| `C2M_SelectTeamMember`(20072) | `team_battle.go:307 onSelectTeamMember`（目标必须是本队活着成员） | `battle.selectedAllyID` |

施法时才用它：`battle_skill_runtime.go:347 playerSkillPrimaryTarget` ——
`plan.TeamType == 2`（友方）**才**看 `selectedAllyID`，否则看 `selectedID`，都没有就取第一个活着的东西。

**推论**：对 B10/B11，玩家点队友发的是 `SelectTeamMember`，服务端把它存进 `selectedAllyID` **但从不读取**（因为 `TeamType=1` 走的是敌人分支）→ 落点被强制到怪身上。**只要 `TeamType=1`，玩家就永远无法指定队友**。

### 7.3 方案 A（推荐，不动客户端）：技能级 `teamType` 定点覆盖 + 队友兜底

#### 改动点

**① 新增技能级覆盖表**（放在 `server-mysql/skill_logic.go`，紧挨现有 `onlineModifierLevelOverrides`）：

```go
// A tiny set of shipped skills whose teamType contradicts every sibling skill
// of the same profession. Both are the only teamType=1 skill among their
// profession's friendly skills, and their own descriptions say 友方单体.
// Keep this table minimal; it changes the cast-side阵营 only.
var onlineSkillTeamTypeOverrides = map[int32]int32{
	310604: 2, // 双面镜：护士 8 个友方技全部 teamType=2，唯它是 1
	410404: 2, // 柳暗花明：超能力 4 个友方技全部 teamType=2，唯它是 1
}
```

**② `Plan()` 里覆盖**（`skill_logic.go:454` 附近，`SkillPlan{...}` 构造之后、遍历事件之前）：

```go
if override, ok := onlineSkillTeamTypeOverrides[skillID]; ok {
	plan.TeamType = override
}
```

**③ 兜底目标改为「当前选中的友方」优先**（`battle_skill_runtime.go:351-370`）。现有逻辑是"没有选中队友就选血量百分比最低的队友"，**保持不变**即可；只需确认 `selectedAllyID` 在 `TeamType=2` 时被优先读取 —— **现有代码已经这么做了**，所以 ③ 无需改动。

#### 改完之后的实际行为

| 场景 | 结果 |
| --- | --- |
| 玩家点队友（`SelectTeamMember`）后施放 | 按点击目标施加 ✅（和普通友方技能一致） |
| 玩家没点队友就施放 | 落到**血量百分比最低的存活队友**（现有兜底，非原版证据，属实现选择） |

#### 必须一起做的验证（否则不许合并）

1. `go test ./...` 全绿；
2. 新增 Go 断言：`Plan(310604, lv).TeamType == 2`、`Plan(410404, lv).TeamType == 2`，且**其余 128 个技能的 `TeamType` 与 `SkillLogicConfig` 逐字节一致**（防止覆盖表误伤）；
3. 真实 TCP 复测（沿用 `server-mysql/test/` 规范）：建立队伍 → **点队友** → 施放 310604，断言 `20080` 的 `Id=31060411` 落在**被点的队友**身上；410404 同理断言 `Id=41040411`（`bufficon_yinshen`）落在队友身上；
4. 顺手补一条反向用例：不点队友时落到**血量百分比最低**的队友（锁定兜底行为）；
5. 服务端二进制与配置 revision 归档到 `logs/runtime/`，抓包归档到 `参考数据/抓包归档/`。

#### 已知代价 / 风险

- **偏离原版**：这 2 处改完，服务端行为就不再等于原版客户端逻辑表的行为 —— 属于 7.4 里的 (c) 路径，**需要产品明确决策**；
- **无法指定目标时语义是猜的**：线上抓包里**没有** 310604 / 410404 的施放样本（已扫全部 9 份抓包的 20075 帧，玩家技能只出现 100001/300001/310101/310401/310501/310601），所以"原版是不是也自动选最残血"没有证据；
- 覆盖表本身会增加一处"服务端不照配置跑"的地方，必须靠上面的断言 2 锁住影响面。
