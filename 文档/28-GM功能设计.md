## 1. 设计结论

GM 后台是独立的管理控制面，由 React 前端、Go 管理 API 和一个连接当前游戏服的
控制通道组成。浏览器只访问 HTTP API，不能访问 MySQL、Redis 或游戏 TCP 端口。

```text
管理员浏览器
      |
      | HTTPS :443
      v
Nginx (静态 React + /api 反代)
      |
      v
gm-api :8080  -------- MySQL (只读/受控事务)
      |  \
      |   \------ Redis (会话、命令、配置通知)
      v
游戏服控制处理器  ---- 游戏服 TCP :7756 ---- 玩家客户端
```

核心原则：

1. GM 服务负责身份、权限、参数校验、审计和查询。
2. 游戏服负责在线角色的内存状态、战斗/队伍状态和最终一致性。
3. MySQL 是持久化事实来源，但不是在线角色的唯一实时状态来源。
4. 所有有副作用的请求必须有 `request_id`，可以安全重试且不能重复发奖。
5. 所有配置仍以 `server-mysql/config/operations/*.yaml` 为可编辑输入，经过同一套
   校验后写入 `game_config_nodes`，再通过 Redis 热重载。
6. 不提供任意 SQL、任意表更新或绕过业务规则的接口。

## 2. 与现有服务的边界

### 2.1 游戏服现状

- 游戏服是 Go 单进程，TCP 监听 `7756`，入口为 `server-mysql/main.go`。
- `Server.conns` 保存连接，`session` 保存在线角色的等级、货币、背包、装备、宠物、
  战斗和队伍状态。
- 玩家断线时会通过 `cleanupPlayerSession` 保存状态；新的登录会替换旧会话并发送
  `G2C_ForceOffLine(20328)`。
- Redis 当前使用 `mhq:online:player:*` 标记在线状态，使用
  `mhq:config:reload` 通知配置重载。
- MySQL 使用规范化表，不再使用旧 SQLite 或玩家 JSON 大字段。核心表包括
  `accounts`、`players`、`player_items`、`player_skills`、`player_tasks`、
  `player_pets`、`player_star_souls`、`player_mails`、家族和寄售相关表。
- 运行配置保存在 `game_config_nodes`，发布历史目前保存在
  `game_config_revisions`。

### 2.2 GM 服务职责

建议新增独立 Go 服务目录 `server-mysql/cmd/gm-api/`，共享数据库 schema 和配置
校验代码，但不复用游戏客户端 TCP 协议。GM 服务包含：

- 管理员登录、登出、会话续期和权限判断；
- 角色、账号、家族、寄售、Boss、配置和运行状态查询；
- 受控的角色修改请求；
- 操作审计、幂等记录和请求追踪；
- 配置 YAML 的校验、版本管理和发布请求；
- 游戏服健康检查和控制通道超时处理。

GM 服务不负责：

- 直接构造客户端 protobuf 或冒充玩家发送游戏协议；
- 直接修改在线玩家的 `players` 行后返回成功；
- 保存或展示游戏账号明文密码；
- 读取 `datatable_json/` 作为生产运行配置；
- 执行管理员提交的任意 SQL。

### 2.3 游戏服新增职责

游戏服增加一个内部 Redis 命令消费者，或者增加同进程的内部控制处理器。它是在线
角色操作的执行者，至少支持：

- 查询实时在线状态；
- 强制下线并等待保存完成；
- 增减货币、发邮件、发放物品；
- 修改等级、经验、属性点、技能、宠物等明确业务操作；
- 返回操作前后快照摘要；
- 返回当前配置 revision 和重载结果。

控制处理器只接受来自私有 Redis 网络的命令，不能绑定远程 HTTP 或远程 TCP。

## 3. 部署形态

### 3.1 本机开发

```text
游戏服       127.0.0.1:7756
GM API       127.0.0.1:8080
React/Vite   127.0.0.1:5173
MySQL        127.0.0.1:3306
Redis        127.0.0.1:6379
```

React 开发服务器通过 `/api` 代理到 `127.0.0.1:8080`，避免开发环境引入额外 CORS
逻辑。GM API 的默认监听地址必须是 `127.0.0.1:8080`，不能默认监听 `0.0.0.0`。

### 3.2 远程部署

远程 Docker 增加 `gm-api` 服务，但只在主机回环地址发布端口：

```yaml
gm-api:
  build:
    context: ./gm-runtime
  environment:
    MHQ_MYSQL_DSN: mhq:${MHQ_DB_PASSWORD}@tcp(mysql:3306)/mhq?parseTime=true
    MHQ_REDIS_ADDR: redis:6379
    GM_LISTEN: 0.0.0.0:8080
  ports:
    - "127.0.0.1:8080:8080"
  networks:
    - backend
```

游戏端口 `7756` 继续按现有方式对外提供；MySQL `3306` 和 Redis `6379` 不得发布到
远程。GM 镜像只包含 Linux ELF 管理 API 和构建后的前端静态文件，不上传 Go 源码、
SQL dump 或管理员密钥。

### 3.3 Nginx

建议使用独立域名，例如 `admin.example.com`，并让 React 与 API 同源：

```nginx
server {
    listen 443 ssl http2;
    server_name admin.example.com;

    root /var/www/mhq-gm;
    index index.html;

    location / {
        try_files $uri $uri/ /index.html;
    }

    location /api/ {
        proxy_pass http://127.0.0.1:8080;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 60s;
    }
}
```

Nginx 必须配置 TLS、请求体大小限制、基础限流和安全响应头。GM API 应只信任来自
Nginx 的 `X-Forwarded-*`，并根据可信代理地址重建审计 IP，不能让客户端任意伪造。

## 4. 身份、角色和权限

### 4.1 独立管理员账号

不能复用 `accounts` 表作为后台账号。当前游戏账号密码仍有明文兼容历史，GM 账号
必须单独使用哈希密码。

建议增加以下表：

```text
gm_admin_users
  id, username, password_hash, display_name, status, last_login_at,
  created_at, updated_at

gm_roles
  id, name, description

gm_admin_roles
  admin_id, role_id

gm_audit_logs
  id, request_id, admin_id, action, target_type, target_id,
  before_json, after_json, reason, client_ip, user_agent,
  result, error_code, created_at

gm_command_records
  request_id, action, target_id, status, payload_hash,
  game_revision, result_json, expires_at, created_at, finished_at
```

`before_json` 和 `after_json` 只用于审计快照，不作为游戏运行状态来源。密码使用
Argon2id 或 bcrypt，登录失败使用统一提示，不能泄露管理员账号是否存在。

### 4.2 初始角色

| 角色 | 查询 | 角色操作 | 发奖/货币 | 配置发布 | 管理员/审计 |
|---|---:|---:|---:|---:|---:|
| `superadmin` | 全部 | 全部 | 全部 | 全部 | 全部 |
| `operator` | 全部 | 踢人、邮件、物品 | 允许 | 允许运营配置 | 只读 |
| `support` | 角色详情 | 仅踢人/恢复类操作 | 不允许直接改货币 | 不允许 | 无 |
| `config-editor` | 配置和状态 | 不允许 | 不允许 | 允许指定配置 | 只读 |
| `auditor` | 全部 | 不允许 | 不允许 | 不允许 | 只读 |
| `readonly` | 白名单查询 | 不允许 | 不允许 | 不允许 | 无 |

权限判断必须在 API 中执行，React 隐藏按钮只能改善体验，不能作为安全控制。

### 4.3 会话安全

- 浏览器使用 Redis 会话和随机不可预测 session ID；Cookie 使用 `HttpOnly`、`Secure`、
  `SameSite=Lax` 或更严格设置。
- 写操作使用 CSRF token；所有写接口检查 `Origin`/`Referer`。
- 登录、发奖、货币调整和配置发布设置独立限流。
- 支持主动登出、全部会话失效和管理员禁用。
- 高风险操作支持二次认证或重新输入管理员密码。
- 管理后台应放在 VPN、IP 白名单或至少独立安全组之后。

## 5. 在线状态和一致性

### 5.1 状态判定

Redis 的 `mhq:online:player:*` 只能作为快速提示，不能单独决定是否可以修改角色。
GM 查询角色时同时返回：

```text
online          Redis 标记
realtimeOnline  游戏进程 conns 中的实时状态
sessionState    logged / in-game / superseded / offline
lastPersistedAt 最近一次持久化时间
```

如果 Redis 与游戏服状态不一致，界面标记为 `状态待确认`，写操作默认拒绝，直到游戏
服返回明确结果。

### 5.2 在线操作流程

所有影响货币、背包、装备、战斗、队伍或任务的写操作按以下流程处理：

1. GM API 生成 `request_id`，检查权限、参数、目标角色和幂等记录。
2. 通过私有 Redis 命令通道发送操作请求，设置短期过期时间。
3. 游戏服定位当前权威 session，取得对应锁并再次校验目标状态。
4. 在 session 快照上执行业务校验和变更；不能绕过背包容量、锁定物品、货币上限等
   现有规则。
5. 游戏服把结果持久化到 MySQL，并向客户端推送必要的原生同步消息。
6. 游戏服返回操作前后摘要、保存结果和当前会话 revision。
7. GM API 写入审计日志并返回统一响应。

执行失败时必须返回明确的业务错误，不能只返回 HTTP 500，也不能把“请求已发送”伪装
成“操作已完成”。命令超时返回 `pending`，由查询接口继续获取结果。

### 5.3 离线操作流程

离线角色可以由 GM API 在 MySQL 事务中执行受控修改，但要满足：

- 只更新明确的业务字段或规范化子表；
- 查询并锁定目标行，检查当前版本或 `updated_at`；
- 事务内写入角色和关联数据；
- 写入 `gm_audit_logs`；
- 返回新的角色摘要；
- 角色重新登录后由现有 `loadData` 完整加载。

不能以通用字段名和值的形式开放 `UPDATE players SET ...`。

### 5.4 强制下线

强制下线必须调用游戏服现有的会话替换/清理逻辑，不能只删除 Redis 在线 key：

1. 游戏服发送原生 `G2C_ForceOffLine(20328)`；
2. 立即排除旧会话的聊天、队伍和战斗路由；
3. 执行 `cleanupPlayerSession` 保存状态；
4. 在宽限期结束后关闭旧 TCP 连接；
5. GM API 收到保存完成或失败结果后再继续后续高风险写操作。

## 6. GM 功能范围

### 6.1 只读功能

第一版必须先完成只读功能，再开放写操作：

- 首页：账号数、角色数、实时在线数、最近登录、MySQL/Redis/游戏服健康状态、配置
  revision；
- 角色列表：账号、角色 ID、角色名、职业、等级、转生、家族、地图、最后登录、在线状态；
- 角色详情：基础属性、六种货币、属性点、背包、穿戴、仓库、技能、任务、宠物、星魂、
  邮件和活动状态；
- 家族、家族 Boss、寄售物品、世界 Boss 状态；
- 配置名称、当前 revision、发布时间、发布人和变更摘要；
- 审计日志和命令执行记录。

查询必须分页。`BIGINT`、角色 ID、货币、Unix 时间戳在 JSON 中使用字符串，避免
JavaScript `number` 精度丢失。

### 6.2 低风险写操作

- 强制下线；
- 向角色发送系统邮件；
- 发放明确的物品 ID 和数量；
- 恢复卡死的地图/战斗状态；
- 刷新角色快照或让角色重新加载；
- 修改公告类运营配置。

每次发邮件或发物品都必须指定数量、有效期和幂等 key。物品 ID 必须在当前
服务端配置中存在，且客户端没有对应资源时界面要给出警告。

### 6.2.1 全服作用域操作（2026-09-14 新增）

上面这些写操作全部是**单角色**的。全服操作是另一条作用域：命令以
`targetType=server`、空 `targetId` 下发，审计里同样是 `TargetType=server`，
游戏服侧由 `gmServerActionRegistry` 而不是角色动作表承接。当前有两个：

| 能力 | 接口 | 权限 | 生效范围 |
|---|---|---|---|
| 全服公告 | `POST /api/v1/broadcast/announce` | `server.broadcast` | 全部**在线**角色；离线不补发 |
| 全服邮件 | `POST /api/v1/broadcast/mail` | `server.mail_all` | 全部角色（含离线）；附件领取时到账 |

两者权限**分开授予**：公告只进聊天频道，全服邮件往每个角色的邮件箱写物品，发错了
只能一个个角色去删。`operator` 两项都有，`support`/`subgm`/`auditor` 两项都没有 ——
子 GM 在单角色命令上权限很宽，但绝不该有全服权限。

前端 `/broadcast` 页按权限显示页签；全服邮件的二次确认必须显示收件角色总数并勾选
确认，角色总数读不到时禁止提交。两个写操作都在打开确认框时固定一个 `Idempotency-Key`
并在重试时复用，双击或断网重连不会变成第二封。

**已知限制**（本地实测已确认行为，非缺陷）：

- 公告**不落库**，只发给当下的在线角色，之后登录的人不会收到 —— 这是公告本身的语义；
- 全服邮件在广播窗口（亚秒级）内恰好正在登录的角色可能漏收，重发一次即可（换新幂等 key）；
- 全服邮件是一次性 `INSERT ... SELECT` 全表写入，适合本项目量级；角色数上万时需要分批。

### 6.3 高风险写操作

高风险操作默认需要 `operator` 以上权限和二次确认：

- 增减铜币、元宝、代金券、荣誉、竞技币或仓库货币；
- 修改等级、经验、转生和属性点；
- 修改技能、自动技能、宠物和星魂；
- 删除角色；
- 批量发奖；
- 修改世界 Boss、家族 Boss 或寄售数据。

货币调整接口使用 `delta`（增减量）而不是无条件 `set`，并设置业务上下限。需要
“设为指定值”时，API 必须记录计算出的 delta、修改前值和修改后值。

### 6.4 配置发布

允许后台编辑的首批配置：

```text
Gameplay
ShopBase
MarketBase
MultiShop
ActivePerDayConfig
WorldBossConfig
FamilyBossConfig
CustomSkins
```

`GoodsBase`、`MonsterBase`、`SkillLogicConfig` 等大表第一版只读，避免误改原版表或
造成客户端资源不匹配。

发布流程：

1. API 根据配置名称加载对应 YAML schema，拒绝未知字段、错误类型和越界数值。
2. 写入草稿版本，不直接影响线上配置。
3. 展示差异、影响范围、客户端资源风险和预计 revision。
4. 有权限的管理员确认发布，生成 `request_id` 和审计记录。
5. 原子替换 `game_config_nodes`，写入 `game_config_revisions`。
6. 通过 Redis `mhq:config:reload` 通知游戏服。
7. 等待游戏服重新加载并确认 revision；失败时保留旧内存快照并返回失败。

生产环境必须明确配置发布者。若由 GM API 负责发布，应关闭游戏服内置 YAML watcher，
避免同一保存被发布两次；本机开发仍可使用 watcher。GM API 写 YAML 时必须使用临时
文件、校验后原子 rename，并保留上一版本备份。

当前 `game_config_revisions` 只有 revision、时间、发布人和备注。要支持可靠回滚，
应增加配置版本快照表，或把每次发布的规范化 YAML 存入受保护的版本存储；不能仅凭
revision 号恢复已删除的节点。

## 8. Redis 控制通道

独立 GM API 与游戏服之间建议使用 Redis Streams，而不是让 GM API 直接访问游戏服
内存。命令 envelope 示例：

```json
{
  "requestId": "01J...",
  "action": "player.currency_adjust",
  "targetPlayerId": "3250",
  "operatorId": "7",
  "payload": {"currency": "coin", "delta": "100000"},
  "expectedVersion": "1712345678",
  "expiresAt": "1770000000"
}
```

建议的 key：

```text
mhq:gm:commands       Redis Stream，GM -> 游戏服
mhq:gm:results:<id>   短期结果，游戏服 -> GM API
mhq:gm:events         游戏服状态/审计事件
```

命令处理要求：

- `requestId` 全局唯一，游戏服和 GM API 都要去重；
- 命令带过期时间，过期命令拒绝执行；
- 结果包含 `acceptedAt`、`completedAt`、`gameRevision` 和错误码；
- GM API 重启后可通过 `gm_command_records` 查询未完成命令；
- Redis 不可用时拒绝新的高风险操作，不降级为直接写数据库；
- 控制通道使用专用 Redis ACL 用户，只允许所需 key 和命令。

## 10. 审计、备份和回滚

所有写操作必须记录：

```text
request_id、管理员、角色、动作、目标、前值摘要、后值摘要、来源 IP、
User-Agent、幂等 key、游戏服结果、错误码、时间和耗时
```

审计日志只追加，不允许后台页面修改或删除。敏感字段脱敏：游戏账号密码、会话
token、Redis 密码和完整凭证不得进入日志。

部署和配置发布前：

1. 备份 MySQL（至少保留账号、角色和配置版本）；
2. 对 YAML 和构建产物计算 SHA256；
3. 发布后确认游戏服 revision 和健康状态；
4. 失败时恢复上一版本二进制或重新发布上一份配置快照；
5. 不删除远端 `mysql-data`、`redis-data` 卷，不用 GM 页面执行数据库重建。

## 11. 测试和验收

### 11.1 API 测试

- 管理员登录、错误密码、会话过期、登出和 CSRF；
- 每个角色权限的允许/拒绝矩阵；

### 11.2 在线一致性测试

- 在线角色货币调整后客户端数值、session 和 MySQL 一致；
- 在线角色背包满时发奖原子失败，不丢物品、不扣货币；
- 强制下线期间断线保存不会覆盖 GM 修改；
- 重复登录、战斗中、组队中、交易中强制下线均能清理状态；
- GM API 重启后仍可查询命令最终结果。

### 11.3 配置测试

- 合法 YAML 校验、未知字段拒绝、数值边界拒绝；
- 发布后 MySQL 节点、revision、Redis 通知和游戏服内存快照一致；
- 游戏服重载失败时保留旧快照；
- 回滚会产生新 revision，并能恢复完整配置；
- 生产模式关闭 watcher 后不会重复发布同一份配置。

### 11.4 远程验收

- 外网只能访问 Nginx `443` 和游戏 TCP `7756`；
- `3306`、`6379`、GM API `8080` 不对远程暴露；
- Nginx `/api` 代理、React history fallback、TLS 和限流正常；
- 审计日志能区分真实客户端 IP 与代理 IP；
- 游戏服和 GM 服务重启后数据、会话和配置均可恢复。

### 15.3 远程 Nginx 反向代理边界

推荐将构建后的 `web/dist/` 部署到独立域名，Nginx 只把 `/api/` 转发到 GM API 回环端口：

```nginx
server {
    listen 443 ssl http2;
    server_name admin.example.com;
    root /var/www/mhq-gm;
    index index.html;

    location / { try_files $uri $uri/ /index.html; }
    location /api/ {
        proxy_pass http://127.0.0.1:8080;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

远程只开放 HTTPS `443` 和游戏 TCP `7756`；MySQL `3306`、Redis `6379`、GM API `8080`
保持回环或 Docker 内网可见。GM API 不允许浏览器直连数据库，也不提供任意 SQL。

## 14. 首批实现任务清单

后续开发按下面的边界拆分，每个任务单独提交和验收；不要把 GM API、游戏服控制通道、
React 页面和部署脚本混在一个“大提交”中。所有新增协议实测脚本仍放在
`server-mysql/test/`，不在根目录新增临时回归脚本。

| 编号 | 独立任务 | 主要产物 | 完成标准 |
|---|---|---|---|
| GM-01 | GM 数据库迁移 | `gm_admin_users`、`gm_roles`、`gm_admin_roles`、`gm_audit_logs`、`gm_command_records` 及版本化迁移 | `go test ./...` 通过；迁移可重复执行；不修改现有账号、角色和玩家表数据 |
| GM-02 | GM API 骨架与健康检查 | `server-mysql/cmd/gm-api/`、配置加载、结构化日志、`/api/v1/health` | 默认仅监听 `127.0.0.1:8080`；MySQL/Redis/游戏服依赖异常可区分报告 |
| GM-03 | 管理员认证与 RBAC | Argon2id/bcrypt、Redis 会话、Cookie、CSRF、权限中间件 | 登录错误不泄露账号存在性；每个角色的允许/拒绝矩阵有测试；敏感值不进日志 |
| GM-04 | 只读查询 API | Dashboard、账号/角色、角色各子资源、家族/Boss/寄售、审计和命令查询 | 服务端分页；BIGINT/货币/时间戳按字符串序列化；查询不依赖客户端在线连接 |
| GM-05 | 游戏服控制通道 | Redis Streams 命令消费者、结果去重、超时和 pending 查询 | 游戏服重启或 GM API 重启后不重复执行；命令过期、未知动作和错误版本均拒绝 |
| GM-06 | 低风险角色操作 | 踢人、刷新、邮件、物品发放 | 在线操作先改 session 再持久化并推送原生同步；离线操作使用事务；幂等重试不重复发奖 |
| GM-07 | 高风险角色操作 | 货币、等级、技能、宠物、星魂、删除角色 | 二次确认、上下限、前后快照和完整审计齐全；在线/离线一致性测试通过 |
| GM-08 | 配置草稿与发布 | YAML schema、草稿/差异、`game_config_revisions` 快照、Redis 热重载 | 未知字段和越界值拒绝；发布/回滚均产生新 revision；重载失败保留旧内存快照 |
| GM-09 | React 管理端 | `web/`、登录、Dashboard、角色、配置、审计页面 | 仅调用同源 `/api`；权限控制与后端一致；写操作显示前值/后值/影响和 pending 状态 |
| GM-10 | 远程部署与 Nginx | Docker Compose、GM 镜像、Nginx 配置、部署/回滚脚本 | 外网只暴露 443 和游戏 TCP 7756；3306/6379/8080 仅回环或内网可见；部署失败可恢复 |
| GM-11 | 回归与安全验收 | `server-mysql/test/` API/控制通道脚本、权限矩阵和并发测试 | 覆盖重复请求、在线战斗/交易/组队踢人、背包满、Redis 故障、CSRF 和配置回滚 |

每个任务的提交说明应包含：变更范围、数据库/配置影响、回滚方式、执行过的测试命令
及结果。GM-05 之前不开放任何有副作用的后台按钮；GM-10 之前只允许本机或 VPN 访问
管理端。若实现过程中发现现有游戏服没有某项原生同步消息，应先在协议和客户端行为
层面核对，再决定是否增加兼容消息，不能为了让页面显示成功而直接改数据库。
