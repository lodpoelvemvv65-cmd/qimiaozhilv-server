## C 类：原"需反汇编才能定论"—— 已定论，归入 B 类

原 C1：军官 / 致命打击（110503）Lv4 文案写"造成自身**当前生命值** 7% 的物理伤害"（当前 200 / 上限 1000 时按文案应为 14），而配置 `SkillOption_伤害 damageCalculate_Self.param = Lv1:1,2:2,3:4,4:7` 且 `calculateType=2`；服务端按 `calculateType=2` 判为**最大生命值**，打出 70。

### B 类处理决策

三种自洽方案：

- **(a) 保持原版**：服务端不动，只把"描述与逻辑不一致"登记为已知差异。
- (b) 改客户端文案：让 `SkillConfig.Desc` 与逻辑表对齐（客户端补丁，需按文档 25 的流程备份/回滚）。
- (c) 逻辑也按文案改：**明确偏离原版**，只在确认"原版是错的、我们要修正"时采用。

**本项目采用 (a)**。理由：项目要求"完全、完整地实现每个功能，必须与客户端一致"，而客户端按约定不可修改。B 类的差异是**客户端自身**文案与数据的矛盾，服务端已经忠实复现了客户端真实行为；改服务端等于制造一个新的、与客户端不一致的行为。若将来要修正文案本身，走 (b)，并单独登记为客户端补丁。

### 二、4 个已解析但运行时无读者的字段 —— 已逐字段查明

`scan_field_coverage.py` 的结论是"61 个业务字段没有一个完全没被读过"（解析层全通），
但下面 4 个字段只在 `skill_logic.go` 被赋值进计划结构，**运行时代码里没有读者**。
用 `scan_unused_fields.py`（产物 `unused_fields.txt`）把每个字段的实际取值分布拉出来后，结论是：

| 字段 | 配置里的实际内容 | 判定 |
| --- | --- | --- |
| `thinkerType` | 264 个为 0，19 个非 0（1/2/3/4） | **与 `overlayType` 逐个同值（283/283 全等，见 `verify_dead_fields.py`）**，是编辑器同步写出的冗余字段。这 19 个也正是**全部**带 modifier 事件 8（周期节拍）的 modifier（双向差集都为空）。服务端已经读 `overlayType`（`overlayBucket` 叠层分槽），再读 `thinkerType` 不会带来任何新信息 → **无需读** |
| `perOverlay` | 184 个 `(skillSourcetype=0, 0.0)`；80 个 `skillSourcetype=1` 但 `values` **表是空的**（resolve 得 0）；**19 个 `(2, 1.0)`** | 非零的地方**只有 1.0**，而 1.0 就是"每层乘 1"的中性值；这 19 个恰好又是那 19 个事件 8 的 DOT/HOT modifier → 不读等于按 1.0 处理，**无差异** |
| `flagType` | 只有两个取值：`7`（123 个技能）和 `1`（7 个技能） | 语义**无法从客户端得到**（客户端不读这张表，见下「三」）。取值规律见下面「flagType 定稿」小节 → **保持现状、登记为已知差异** |
| `stateV` | **283 个全是 0** | 没有任何值，读不读完全一样 → **无差异** |

#### flagType 定稿（2026-09-16）

**取值规律**：`7` = 123 个技能（含全部 4 个职业的普攻、全部玩家技能、全部怪物伤害技）；`1` = 7 个技能，全是**怪物辅助技**：
吃我一口毒奶（500033）、吃我大口毒奶（500034）、超级奶（500035）、皮糙肉厚（500036）、脸皮变厚（500037）、臭不要脸（500038）、王八盾（500042）。

这 7 个的共同点（其余 123 个技能**没有**同时满足）：

- 全部 `teamType=2`（友方），技能里只挂一个 `SkillOption_应用Modifier`；
- 目标选择器是 `SelectMultiTarget(teamType=2, flags=0, isRndom=false, maxCount=10)`（即"给最多 10 个友方"）；
- 对应 modifier 的 `tag=0`、`stateK=0`、`canBeClear=false`、`attribute=8`；
- 只出现在**精英 / BOSS 怪**的技能组里：组 `10028`（3阶boss）、`10036`（火/土之领主左使）、`10037`（风/暗之领主左使）、`10041`（星魂守望者）。

**它是位掩码而不是枚举**：`7 = 0b111`、`1 = 0b001`，两类只在位 1、位 2 上不同。参照物：客户端里真正的位掩码枚举
`Cal.ModifierAttribute` 用的正是"2 的幂取并集"这套写法（`忽视无敌=2`、`可叠加=4`、`可刷新=8`、`所有=14`），
所以 `7` 读作"三项全开"是自洽的。而客户端 71 个枚举里只有 3 个真位掩码，且**没有一个与技能标记有关**
（详见下面「三」末尾的枚举复核），所以 `flagType` 对应的枚举不在客户端。

**它不能由表内其它字段推导**：`bruteforce_flagtype.py` 对 20 多类特征做了穷举（`skillType` / `teamType` / 事件码集合 /
modifier 事件码 / 选项种类 / 选择器组合 / 修饰符个数 / `tag` / `stateK` / `valueK` / `iconId` / `attribute` / `effectId` /
`canBeClear` / 名字是否为空 / 是否有单目标选择器 / 是否有友方多目标选择器 …），结论是
**没有任何单一特征能区分 `flagType=1` 与 `7`**；唯一能刚好圈出这 7 个的是组合谓词「有 `SelectMultiTarget(teamType=2)` ∧ 只挂 1 个 modifier」。
→ `flagType` 携带的是**独立信息**，不是 `thinkerType` 那种冗余字段。

**判定：保持现状（不实现），登记为已知差异。** 三条理由：

1. **客户端不读它**（下「三」已证），实现它不会让客户端表现更一致；
2. 它**不在网络协议里**——`M2C_PlaySkill` / `M2C_MonsterPlaySkill` / `M2C_PlaySkillEffect` / `M2C_BattleSkillRet` /
   `M2C_SyncUnitAttribute` 的字段里没有任何 flag 类字段，所以它不参与客户端表现；
3. 它**不影响任何已实现的结算路径**：服务端怪物选技是 `selectMonsterSkillID()` 从 `SkillGroupBase.SkillsArr` **等概率随机**取
   （组内会重复写同一个技能 id 来表示权重），这条路径本来就不查 `flagType`。

**何时需要回来重做**：如果以后拿到原版运行时证据（录屏 / 抓包 / 线上日志）显示怪物 AI 对辅助技有特殊处理
（例如"辅助技只在有队友受伤时释放"或"辅助技不占普攻顺序"），再按 `flagType` 分类补上。

#### 对照：`thinkInterval` 是**有意不用**

`thinkInterval` **是有意不用** —— 注释明确写"原版客户端表里没有任何地方可用"，
服务端改用自己的持续节拍，且 `battle_periodic_tick_test.go` 把它锁住（14 秒中毒落 +4/+8/+12 三跳，
不跟着它自己的 5 秒走）。这不算漏实现，是**有依据的偏离**。

另外顺带发现 `SkillStatusPlan.IsControl`（= `StateKey != 0`）在业务代码里也没有读者（只有 `skill_logic_test.go` 的覆盖统计读它）——

并在注释里说明了原因：把所有非零 stateK 当控制会让"抗性"错误地拒掉友方 buff。所以 `IsControl` 是遗留字段，不影响行为。

### 三、客户端到底读不读 `SkillLogicConfig`？—— 不读（2026-09-16 反汇编定稿）

这一条是上面 `flagType` 语义无法从客户端定论的**根因**，也是本轮反汇编的主要产出。五组独立证据（E1–E5），结论一致：

| # | 手段 | 结果 |
| --- | --- | --- |
| E1 | 在客户端**全部 7 个受托程序集**（`Hotfix.dll` / `HotfixView.dll` / `Unity.Model.dll` / `Unity.ModelView.dll` / `Cal.Core.dll` / `Assembly-CSharp.dll` / `Assembly-CSharp-firstpass.dll`）里按**元数据名**搜 `flagType` / `thinkerType` / `overlayType` / `perOverlay` / `stateV` / `stateK` / `valueK` / `skillDic` / `modifierDic` / `skillEventDic` 等，以及类名 `SkillLogicConfig` / `SkillLogicConfigCollection` / `SkillOption_` / `SelectSingleTarget` / `SelectMultiTarget` | **一个都没有** |
| E2 | 在上述 DLL 与两个 PDB 的**裸字节**里按 **UTF-8 与 UTF-16LE 双编码**搜同一批名字（覆盖 `#Strings`、`#US`、`#Blob` 三个堆） | 同上；同级 JSON 键名 `teamType` / `maxLevel` / `skillId` / `buffType` / `hideFlags` / `succeedOptionList` / `failOptionList` 也**一个都不在** → 不是"个别键被忽略"，而是**整个类家族都不在客户端** |
| E3 | **PDB 交叉验证**（PDB 只记录"有方法体的类型"，因此能提供独立视角） | 在：`ConfigComponent` / `DataTableHelper` / `SkillConfig` / `SkillGroupBase` / `MonsterBase`；**不在**：`SkillLogicConfig` / `SkillLogicConfigCollection` / `SkillOption_` / `flagType` |
| E4 | 搜资源名的引用 | `SkillLogicConfig`、`SkillLogicConfigCollection`、`SkillOption_延迟操作`、`SelectSingleTarget`、`SelectMultiTarget` 这些**只出现在配置资源自身**（以及包清单的资产名里），任何 DLL 都不引用 |
| E5 | 搜加载路径字面量 | `Hotfix.dll` / `HotfixView.dll` 里**连 `.json` 这个字面量都没有**。`Assets/Download/Config` 前缀确实存在，但那个目录下**唯一**被客户端读取的是 `Assets/Download/Config/GlobalConfig.txt`（引用点 `<GetClintVersion>d__1::MoveNext` @ IL_001d）。客户端读表走的是 `ET.PathHelper::GetDataTablePath()` = `Assets/Download/DataTable/`，对应 `Cal.DataTable.*` 那一套 —— 文案表 `SkillConfig` 在里面，`SkillLogicConfig` 不在 |

补充旁证：

- 客户端**没有战斗结算代码**。`Hotfix.dll` 的战斗相关类型只有 `ET.BattleComponent` / `ET.BuffComponent` / `ET.ClientSkillData`、
  以及 `M2C_PlaySkill*` / `M2C_BattleSkillRet` / `M2C_UnitDead` / `M2C_SyncUnitAttribute` 这类**处理器**和
  `PopupDamage` / `ShowSkillNameUI` 这类**表现事件** —— 战斗是服务端权威，客户端只播表现。
- 命名体系对不上：客户端 datatable 那一套的类名后缀是 `Category`（`Cal.DataTable.SkillConfigCategory`），
  而本表的 `_t` 是 `SkillLogicConfigCollection`；选项用的是 `SkillOption_延迟操作` 这种**中文类名**。
  这是线上**服务端 / 技能图工具**的模型命名，不是客户端 datatable 体系。

**结论**：`SkillLogicConfig.json` 是**线上服务端的战斗逻辑配置**，被构建流程一并打进了客户端热更目录
（`Assets/Download/Config/`，与 `Hotfix.dll.bytes`、`HotfixView.dll.bytes` 同目录），**客户端运行期不读它**。

**这对项目没有负面影响**：判定基准就是"随客户端分发的这张表"，它仍然是原版技能逻辑的权威定义，按它实现服务端依然正确；
只是"客户端战斗结算跑的是 `SkillLogicConfig`"这个说法不成立（正文开头已更正）。

**注意 `tools/_dump_all_enums.py` 的常数表读法**：枚举值在 `#Constant` 表，`Constant.Parent` 是 `HasConstant` 编码索引，
不能直接用 `fi.row_index` 去匹配（TypeDef.FieldList 给出的行对象不带行号）—— 必须先建 `id(field row) → 行号` 的映射，
再按 `Constant.Type`（ElementType）解释 `Constant.Value` 的原始字节。第一版脚本漏了这一步，输出的枚举值全是 `?`，
而当时的结论（"没有枚举的取值域含 7"）就是建立在这份全 `?` 的输出上的 —— **差点据此得出错误结论**。
修好之后复核（判据：成员取值不是连续的 `0..n`）：客户端 71 个枚举里只有 8 个非连续，
其中**真的按"2 的幂取并集"写的位掩码只有 3 个** —— `Cal.ModifierAttribute`（`忽视无敌=2` / `可叠加=4` / `可刷新=8` / `所有=14`）、
`ET.TitleType`（`颜色=1` / `缩放=2` / `流动=4` / `透明度=8` / `倾斜=16`）、`SlotUIEffect`（`1/2/4/8`）；
另外 5 个只是"不从 0 开始"或"中间有跳号"（`ET.MaterialsType` 1–2、`ET.GemType` 1–8、`ET.BuffWorkTypes` 1–14、
`ET.BattleType` 0–6 后跳 20、`Cal.ModifierStateType` 0–16 后跳 100）。三个真位掩码**没有一个与技能标记有关**
（`ModifierAttribute` 是 buff 叠加规则、`TitleType` 是称号特效、`SlotUIEffect` 是装备图标特效）
→ `flagType` 对应的枚举（如果存在）在**线上服务端程序集**里，客户端没有。
（顺带解释一个之前的疑点：怪物 modifier 的 `attribute=8` 不是越界值，就是 `Cal.ModifierAttribute.可刷新`。）


**教训**：字段语义**不能默认"客户端一定能查"**。先证明"客户端是否真的读这张表"，再决定要不要反汇编 ——
否则会在一条走不通的路上耗掉整轮。


### 四、盲区：文案与逻辑表一致的技能从未被逐项断言 —— 已闭合

本轮审计是"文案 vs 逻辑表"驱动的 —— 两边说法一样的技能不会产生任何条目。
所以 130 个技能里只有出过结论的 17 个被逐项核过，其余约 113 个只过了

## 反击机制与修复后验证

反击状态只请求一次额外普攻，触发事件的伤害量为 0；收到伤害时不会直接给攻击者扣一笔"反击返伤"。普攻技能按状态持有者自己的职业和属性解析：

| 状态持有者 | 执行的普通攻击 |
| --- | --- |
| 军官（职业 1/2） | `100001` |
| 足球运动员（职业 3/4） | `200001` |
| 护士（职业 5/6） | `300001` |
| 超能力（职业 7/8） | `400001` |

执行链为 `20081/StateType=102/UserData=0` → `20075` 普攻动作 → 前摇和 `20077` 弹道 → 命中特效与 `20078` 扣血。伤害在命中时按持有者的正常普攻计划结算，包含该普攻已有的附加效果，不使用施放战术反击的军官属性，也不读取本次入伤量计算输出。反击普攻不额外扣蓝、不重置普通攻击或公共冷却；反击产生的普攻不会继续触发反击链。死亡、无法行动、攻击目标消失或角色离场时取消尚未完成的反击。
