# 属性对抗与状态命中判定（2026-09-16）

> 本文回答一个被反复问到的问题：**角色身上的「命中 / 抗性 / 辅助值 / 速度」这些属性，
> 到底在哪些地方生效、哪些地方不生效？**
>
> 触发原因：2026-09-16 排到一个双向退化的 bug —— 怪物给玩家的状态永远落不下来、玩家给怪物的状态必定生效，
> 一路查到根因是**量纲**（`Hit`/`Res` 被当成比率型 ×100）。修完之后把"谁参与判定"整理成本文，
> 作为唯一权威口径。
>
> 相关：[11-背包装备与线上数值](11-背包装备与线上数值.md)（属性枚举与公式）、
> [32-怪物技能实现核对](32-怪物技能实现核对-2026-09-16.md) §8（缺陷定位与修复过程）。

> **2026-09-19 线上抓包更正**：本文“PvE 怪物 → 玩家有害状态由玩家抗性削减”的结论只描述当前自建服实现，
> 已被线上服抓包直接反证。五名线上玩家的穿戴装备抵抗均至少 130，而 95% 眩晕仍落地 30/33；
> 线上该 PvE 路径未使用本文的 `100/(100+抗性)`。以 `文档/40` §3 和 `文档/45` 为准。PvP 尚无线上样本。

## 一、结论速览

### 1.1 参与矩阵（实测，配置几率 60%）

| 场景 | 实际几率 | 参与的属性 |
| --- | --- | --- |
| **PvE 玩家 → 怪物** | **60.0%** | ❌ 命中、抗性**都不参与** → 就是配置原值 |
| PvE 玩家 → 怪物（把玩家命中从 191 改成 5000） | **60.0%** | ❌ 一丁点都不变 |
| **PvE 怪物 → 玩家** | **17.4%**（毕业装抗性 245.6 时） | ✅ **只看玩家抗性**；怪物命中恒 0，不参与 |
| PvE 怪物 → 玩家（抗性改成 500） | 10.0% | ✅ 抗性越高概率越低 |
| PvE 怪物 → 玩家（空号抗性 15.6） | 51.9% | ✅ 同上 |
| **PvP 敌方 → 玩家** | 50.6% | ✅ 命中与抗性**都参与** |
| PvP（敌方命中改成 5000） | 100.0% | ✅ 命中生效 |

**一句话**：
- **玩家 → 怪物**：只看配置概率，**不看命中、不看抗性**
- **怪物 → 玩家**：看**玩家抗性**（`配置 × 100/(100+抗性)`），**不看命中**（怪物命中恒为 0）
- **PvP**：两者都参与

### 1.2 属性生效总表

| 属性 | NumericType | 在战斗里做什么 | 状态 |
| --- | --- | --- | --- |
| **命中** `Hit` | 1032 | 状态命中判定、直伤命中判定的**分子** | ⚠ PvE 里不起作用（怪物没有抗性可对抗） |
| **抵抗/抗性** `Res` | 1033 | 同上，**分母** | ✅ PvE 里起作用（削减怪物对玩家的状态） |
| **辅助值** | 1017 | **治疗量加成**（`treatmentAmount`） | ✅ 起作用。⚠ 见 §5：它在 `ET.NumericType` 里的成员名叫 `Dvo`，**不是闪避** |
| **速度** `Spd` | 1031 | —— | ❌ 服务端没有任何地方读它 |
| **闪避** | —— | —— | ❌ **不存在**：客户端枚举里没有这个成员（见 §5） |
| 暴击率/暴击值/抗暴率/抗暴值/免伤 | 1013–1016、1018–1023 | 暴击判定（§4），**另一条路径** | ✅ 起作用，与状态判定无关 |

## 二、状态命中判定的实现

### 2.1 唯一收口：`statusContestChance`

`server-mysql/battle_status_accuracy.go`：

```go
func (battle *battleState) statusContestChance(configured float64, source, target CombatUnitRef) float64 {
	if battle == nil || battle.runtime == nil || source == target {
		return clampStatusChance(configured)
	}
	// 判定只看目标：目标是"不带评分的怪物"时按配置几率，目标有抗性时正常对抗
	if battle.pvp == nil && battle.lacksStatusRatings(target) {
		return clampStatusChance(configured)
	}
	hit := battle.runtime.EffectivePercentAttribute(source, CombatAttributeHit)
	resistance := battle.runtime.EffectivePercentAttribute(target, CombatAttributeResistance)
	hit = math.Max(-99, hit)
	resistance = math.Max(-99, resistance)
	return clampStatusChance(configured * (100 + hit) / (100 + resistance))
}
```

`clampStatusChance` 把结果夹到 `[0, 100]`。

### 2.2 三个调用点

| 调用点 | 文件 | 作用 |
| --- | --- | --- |
| `contestedStatusChance` | `battle_skill_runtime.go:515` | `SkillOption_几率` 节点的成功分支里含**有害状态**时，用对抗结果替换该几率 |
| `applyStatusEffectWithContext` | `battle_skill_runtime.go:734` | **状态落地**判定：有害状态要过这一关才装得上 |
| `directDamageHits` | `battle_damage_accuracy.go:23` | **直伤命中**判定（`配置` 固定传 100） |

### 2.3 `lacksStatusRatings`：什么叫"不带评分的怪物"

```go
func (battle *battleState) lacksStatusRatings(ref CombatUnitRef) bool {
	unit, ok := battle.runtime.resolve(ref)
	if !ok || unit.monster == nil { return false }        // 不是怪物 → 有评分
	for _, a := range []CombatAttribute{CombatAttributeHit, CombatAttributeResistance} {
		if n := combatAttributeNumericType(a); n != 0 && unit.monster.extraNumeric[n] != 0 {
			return false                                   // 有 1032 或 1033 → 有评分
		}
	}
	return true
}
```

**线上 `MonsterBase` 的 713 行既没有 `Hit` 也没有 `Res` 字段**，所以真实怪物恒为 `true`。
反过来，两类"有数据"的单位为 `false`、对抗照常：测试里手工注入过 1032/1033 的怪物、
以及 PvP 里从对位玩家**拷贝**了评分的敌方（`pvp.go` 的 `pvpEnemyUnit`）。

### 2.4 直伤命中另有一条独立的豁免

```go
// directDamageHits
if source.Side == CombatSideMonster && target.Side == CombatSidePlayer {
	return true                        // 怪物打玩家的直伤：必定命中（不判命中率）
}
```

也就是说 **PvE 的直伤两个方向都不判命中**（玩家→怪物走 `statusContestChance`，但目标没抗性 → 恒 100；
怪物→玩家直接 return true）。只有 **PvP 的直伤**才走真对抗。

## 三、数值从哪来

### 3.1 玩家抗性 `Res`

```
playerExtraNumeric(1033) = 装备/星魂/转生/宠物的 Res 之和 + CharacterGrowth换算(26)
CharacterGrowth 行键 = AttributeType*10 + 职业族，行 26x = { Spi: 0.00028, Sta: 1.2 }
```

| 玩家 | 抗性 | 说明 |
| --- | --- | --- |
| 空号（1 级带初始宠物） | **15.6** | 六维 Sta=Spi=13（宠物给 +12）→ `1.2×13 + 0.00028×13` |
| 毕业装实测（账号 `a12312304`） | **245.6** | 装备 `Res` 合计 230（懒惰 100 + 转·影※生者必灭衣·火 130）+ 六维派生 15.6 |

装备表里 `Res` 是 **1–170 的整数点数**（131 件装备带这个字段）。

### 3.2 玩家命中 `Hit`

```
playerExtraNumeric(1032) = 装备/星魂/转生/宠物的 Hit 之和 + CharacterGrowth换算(25)
CharacterGrowth 行 25x = { Quk: 0.00016 / 0.000125 / 0.00015 / 0.00025 }（按职业）
```

装备表里 `Hit` 是 **1–200 的整数点数**（116 件装备带这个字段）。毕业装实测 **191.29**。

### 3.3 怪物侧

| | 来源 | 值 |
| --- | --- | --- |
| 怪物命中 | `MonsterBase` 没有 `Hit` 字段 | **恒 0** |
| 怪物抗性 | `MonsterBase` 没有 `Res` 字段 | **恒 0** |

## 四、与状态判定无关的另一条路径：暴击

`battle_skill_runtime.go:1257` 的暴击判定**不经过** `statusContestChance`：

```go
chance    := CritRate(施法者)  - AntiCritRate(目标)
critValue := CritValue(施法者) - AntiCritValue(目标)
critical   = roll()*100 < chance
```

抗暴率/抗暴值（`Rpcri`/`Rmcri`/`Rpcrir`/`Rmcrir`）走的是这里，与"命中/抗性对抗"是两条独立的路。
所以**修状态判定不会影响抗暴**。

## 五、`Dvo` 不是「闪避」，是「辅助值」

排查中发现的命名坑，单独记一节：

| 来源 | 19 号槽位叫什么 | 映射 |
| --- | --- | --- |
| `ET.NumericType`（Unity.Model.dll） | 成员名 **`Dvo`** | `Dvo = 1017` |
| `Cal.AttributeType`（Hotfix.dll） | **`辅助值`** | 服务端 `gemKeyToNumeric[19] = 1017` |
| `EquipBase` 字段 | `Dvo` | `equipFieldToNumeric["Dvo"] = 1017` |
| 客户端装备 tooltip | **`辅助值:{0:p2}`** | tooltip 的 23 个标签正好覆盖 `AttributeType` 1–23，最后一项就是这个槽 |

四条佐证：

1. **量级**：`EquipBase.Dvo` 取值 **0.005–3.8**。当闪避意味着最高 **380% 闪避**（荒谬）；当辅助值（治疗加成）完全合理。
2. **服务端行为**：`battle_treatment.go` 的 `treatmentAmount` 读 `CombatAttributeAuxiliary`，而它映射到 1017 —— 与「辅助值」吻合。
3. **线上抓包**：三份抓包里比率字段全部以小数下发（`Dvo=0.05266`、`Pcrir=0.30`、`Pcri=0.48`），而 `1031/1032/1033` **一次都没出现过**。
4. **枚举成员表**：客户端 `ET.NumericType` 里**没有任何"闪避"成员**，服务端也没有 `CombatAttributeDodge`、没有任何闪避判定。

> 更正后的口径：**没有闪避这个机制**；`1017` 的语义是**辅助值**（治疗加成）。
> 11 文档 §2.5、26 文档的待验证项、以及 `battle.go` 的推送注释都已同步更正。

## 六、量纲：`Hit`/`Res` 是点数，不是比率

这是本次修复的根因。`ratioNumericType()` 曾把 `1032`/`1033` 算作"比率型"字段而 ×100。

| # | 证据 |
| --- | --- |
| 1 | `EquipBase` 里真正的比率字段取值 **0.005–0.9**（`Pcrir`/`Mcrir`/`Dvo`/`Rpcri`/`Nphyi`…），而 **`Hit`(1–200) / `Res`(1–170) 与 `PhyAtk`/`PhyDef`/`Hp` 一样是整数点数** |
| 2 | 客户端把小数显示成百分比的工具 `GetFloatPercent` **只覆盖到「辅助值」**，`Hit`/`Res` 不在名单里 |
| 3 | 线上抓包（3 份）里比率字段**全部以小数下发**，而 `1031/1032/1033` **一次都没出现过** |
| 4 | 服务端内部两条路径**自相矛盾**：整数路径 `baseAttribute` 对玩家返回 `191.29`，百分比路径 `basePointAttribute` 返回 `19129` |

×100 造成的后果（实测）：怪物 → 玩家 `0 ÷ 1560` ⇒ **6%**（状态永不生效）；
玩家 → 怪物 `19129 ÷ 0` ⇒ 放大 **192 倍**，配置 18% 被夹成 **100%**（状态必中）。

**修正后**：`ratioNumericType()` 只保留 `1013–1023`（那些确实是比率）。
**客户端不受影响** —— 下发给客户端的快照走 `playerExtraNumeric()`，本来就不含这个 ×100。

## 九、遗留与边界

| 项 | 状态 |
| --- | --- |
| **玩家命中在 PvE 里不起作用** | 不是 bug，是"怪物没有抗性数据"的必然结果。要让它有用，得先给怪物定一套基准抗性数值 —— 原版表里没有，只能凭空设，**没有原版依据** |
| **速度 `Spd`(1031) 无人读取** | 服务端没有行动顺序/出手频率的逻辑（所有单位共用 6 秒回合钟）。要用需要先设计一套速度影响出手的规则 |
| **闪避** | **不存在**，见 §5 |
| 原版到底想让抗性削减多少 | 无原版运行时证据。当前公式 `100/(100+抗性)` 是沿用代码里既有的形状，只修了量纲 |
