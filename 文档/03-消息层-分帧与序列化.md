# 03 — 消息层：分帧与序列化

> ## ⚠ 已更新（2026-08-14）
>
> 早期 KCP 结论已作废：客户端实际走 **TCP（TService）**，帧格式 =
> `[u16 LE 总长度(含 opcode)][u16 LE opcode][protobuf body]`（**PacketParser TCP 变体分帧**），
> 与 `server/tcp_srv.go` / `server/msg.go`（packOuter/parseOuter/readFrame）一致。
> 下文 §1 的"KCP 段无长度头"仅适用于 KCP 路径（未使用）；**TCP 路径有 2 字节长度头**。

> 本文档基于 `参考数据/kchannel_dump.txt`（HandleRecv RVA 0xFF00）、
> `session_dump.txt`（MessageSerializeHelper / PacketParser / Session.Send）还原。

## 1. KCP 流内的消息分帧（关键成果）

### 1.1 一条 KCP 消息 = 一条 Session 消息，无长度头

客户端 `KChannel.HandleRecv`（RVA 0xFF00）反汇编确认，收到一个 KCP 数据段后：

```csharp
// KcpRecv 把一段完整数据取入 receiveBuffer
// 之后直接按 ServiceType 跳位，不读长度头：
if (Service.ServiceType == ServiceType.Inner)   // Inner=1
    receiveStream.Seek(10, Begin);              // 跳过 ActorId(i64) + opcode(u16)
else                                            // Outer=0
    receiveStream.Seek(2, Begin);               // 跳过 opcode(u16)
Service.OnRead(Id, receiveStream);              // 直接把 stream 交给 Session
```

**含义**：KCP 段内**没有外层长度头**。KCP 可靠传输保证"一段 = 一条消息"，
`KcpRecv` 每次返回的恰好是发送方 `KcpSend` 整段写入的内容（KCP 会自动分片/重组）。

> ⚠️ 更正：早期分析曾假设 KCP 流内还有 2/4 字节长度头（依据 `PacketParser.Parse`）。
> 实际上 `PacketParser` 属于 **TCP 变体**（有 packetSize 状态机），KCP 路径（HandleRecv）
> 完全不用它。自建服务器**不要**在 KCP 段外加长度头。

### 1.2 两种消息格式（按 ServiceType 区分）

| ServiceType | 段内布局 | 说明 |
|-------------|----------|------|
| Outer (0) | `[u16 opcode LE][protobuf body]` | 客户端 ↔ 网关 |
| Inner (1) | `[i64 ActorId LE][u16 opcode LE][protobuf body]` | 服务器间 |

- Outer：opcode 占 **2 字节**（`WriteTo(stream, 0, opcode)`，写入前 `stream.SetLength(2)`、`Seek(0)`）。
- Inner：前 8 字节 ActorId（`WriteTo(stream, 8, actorId)`，即写入 offset 8），
  再 offset 8 处写 2 字节 opcode，body 从 offset 10 开始。
- `Send` 时先用 `GetStream(opcode)` 决定容量：Outer 2 字节前缀，Inner 8+2 前缀。

### 1.3 RpcId 是 protobuf 字段，不是独立线前缀

> ⚠️ 更正 `protocol.proto` 头部注释。该注释写"RpcId 时先 `[i64 RpcId]`"，
> 经 `MessageToStream` / `SerializeTo` 反汇编确认是**误导**：
> **RpcId 是消息里的 protobuf 字段（tag=90），随 body 一起被 protobuf 序列化**，
> 没有独立写在 opcode 与 body 之间的 8 字节线前缀。

`MessageToStream` 只做两件事：写 opcode（2/10 字节前缀），然后 `SerializeTo` 整个消息对象
（protobuf 编码，含 RpcId/Error/Message 等字段）。

## 2. 序列化规则（opcode 分界）

`MessageSerializeHelper.DeserializeFrom` / `SerializeTo` 反汇编：

```
if (opcode < 40000)          → protobuf（ToStream / FromStream）
else if (opcode < 51000)     → JSON（ToJson → UTF-8 / FromJson）
else                         → 抛异常 'client no message: {0}'
```

- 全部 429 条消息 opcode 集中在 20000~49999 区间（实际最大 < 50000），**基本全走 protobuf**。
- JSON 区间（40000~50999）用于临时/调试消息，本游戏协议未用。

## 3. MessageToStream 具体行为（反汇编）

`MessageToStream(serviceType, message, actorId)`：

```csharp
int prefix = (serviceType == Inner) ? 8 : 0;   // Inner 先留 8 字节给 ActorId
var stream = GetStream(prefix + 2 + actorId);  // 容量 = 前缀 + opcode(2) + body
ushort opcode = GetOpcode(message.GetType());

stream.Seek(prefix + 2, Begin); stream.SetLength(prefix + 2);  // 先占满前缀+opcode 区
stream.GetBuffer(); WriteTo(buffer, 0, actorId);               // Inner 才写：ActorId → offset 0..8
stream.GetBuffer(); WriteTo(buffer, prefix, opcode);           // opcode → offset prefix
SerializeTo(opcode, message, stream);                          // body → 追加在 opcode 之后
stream.Seek(0, Begin);
return (opcode, stream);                                       // 交给 KChannel.Send
```

2 参版本 `MessageToStream(message, actorId=0)` 等价于 Outer 路径（prefix=0）。

## 4. Session.Send / OnRead 行为

- `Session.Send(msg)`：`MessageToStream` → `LogMsg` → `AService.SendStream(Id, stream)`。
- `Session.OnRead(msg)`：先查 `requestCallbacks[RpcId]`（`TryGetValue`），
  若命中说明是对某个 RPC 请求的响应 → `Remove(RpcId)` 后按 `msg.Error` 决定：
  - `Error != 0` 且 `IsRpcNeedThrowException` → `Tcs.SetException(...)`
  - 否则 `Tcs.SetResult(msg)`。
- `Session.Reply(resp)` = 直接 `Send(resp)`（服务器侧对 RPC 的应答也走普通 Send，
  靠 RpcId 字段配对，见 06 文档）。

## 5. 对自建服务器（Go）的含义

1. **Outer 段**：发送时拼 `[opcode u16 LE][protobuf body]`，body 里要含 `RpcId` 字段（tag=90）以配对响应。
2. **接收**：KCP 段去掉 2 字节 opcode 后，剩余即 protobuf body，按 opcode 反序列化。
3. **不要**在 KCP 段里加额外长度头；KCP 保证消息边界。
4. protobuf 用 proto3 语义：客户端 ET 用 `ProtobufHelper.ToStream`（标准 proto3），
   零值字段默认不写；Go 侧 `proto.Unmarshal` 可正常读缺省字段。
5. 若某消息 opcode ≥ 40000 则用 JSON（UTF-8）编解码——本游戏暂无此情况。
