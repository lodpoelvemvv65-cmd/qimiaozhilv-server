# 23-签到与活动配置生效边界

> 核对日期：2026-08-18。依据 `Hotfix.dll`、`HotfixView.dll`、协议字段、线上
> `SignInRewardConfig/SignInRewardMonth/ActivePerDayConfig` 表和当前 Go 实现。
> `client-test` 已通过 `tools/_patch_datatable.py` 补齐当前年份的月累计模板；服务端线上奖励映射不变。

## 1. 客户端签到的真实行为

`M2C_SendActiveInfo(20423)` 的有效字段是：

| tag | 字段 | 客户端用途 |
|-----|------|------------|
| 1 | `signinCurrId` | 当天 `SignInRewardConfig._id` |
| 2 | `isGetSininReward` | 当天是否已经领取 |
| 3 | `gotSignInMonthList` | 已领取的累计签到天数 `Times`，不是配置 `_id` |
| 4 | `signinInMonthCount` | 当月已经签到的天数 |

`ActiveUI.<ShowMonth>b__0` 从 `currSigninConfigId` 开始，依次读取 30 个连续 ID。只有
`currSigninConfigId` 对应的行显示为当天可领，点击发送
`C2M_GetSigninReward{configId=config.Id}(20419)`。因此服务端必须返回客户端本地表中真实存在的 ID，
并且必须校验请求 ID，不能忽略请求后按服务器自己的任意奖励发放。

累计签到面板走另一条逻辑：`ActiveUI.<ShowMonth>b__1` 使用 `DateTime.UtcNow`，调用
`SignInRewardMonthCategory.GetList(now)` 按当前年月读取客户端本地表。领取后客户端向
`gotSigninMonthTimesList` 添加 `config.Times`；这证明 20423 tag 3 必须发送 7/14/21 这类天数。

## 2. 原始原版表的日期缺口

- `SignInRewardConfig` 只有 2025-01-03 至 2025-12-31，以及 2026-01-01，共 364 行；
- `SignInRewardMonth` 的月累计配置只到 2025-12；
- 当前日期为 2026-08-18，客户端没有 2026-08 的每日行和月累计行。

旧服务端按 2026-08-18 精确查表，结果 `signinCurrId=0`；领取时又私自发 `110305 x10`，并非表中
线上奖励。月累计已领取列表还错误发送了 `_id`，客户端会继续显示成未领取。

## 3. 当前服务端修复

服务端采用可验证的保守兼容规则：

1. 当前年月日不存在时，复用客户端表中相同月日、年份最新的线上行；2026-08-18 映射到
   2025-08-18 `_id=2566`，奖励严格为该行 `110204 x30`。
2. 20419 只接受当天映射后的 ID；伪造、过期或未来 ID 返回业务消息，不发奖励。
3. 删除服务器自造的药水兜底；空配置直接报配置错误。
4. 整批奖励先在背包副本中试放，全部能放下才提交。背包满不会部分发奖，也不会标记已签到。
5. UTC 日期相同只允许领取一次；成功后更新 `LastDay/MonthCount`，落库到 **MySQL 规范化表**：
   签到状态列在 **`player_activity`**（`last_day` / `last_month` / `month_count` / `month_got_month`），
   已领的月累计奖励 ID 逐条写 **`player_month_rewards(player_id, reward_id)`**。
   ⚠ 原书写“写入 SQLite `signin_json`”**双重过时**：引擎早已是 MySQL，且迁移时
   `signin_json` 这类 legacy JSON 列**已被删除并规范化**
   （`internal/mysqlschema/schema_integration_test.go` 会断言 `players`/`families`/`consignment_items`
   上不存在 `signin_json`、`bag_json`、`pet_json` 等列）。
6. 跨 UTC 月份自动清空 `MonthCount/MonthGotIDs`，重置结果持久化。
7. 月累计请求只能使用当前月份映射模板中的 ID，并同时校验 `Times <= MonthCount`。
8. 服务端内部仍存累计奖励 `_id` 用于防重，但 20423 tag 3 推送前转换为客户端需要的 `Times`。

每日签到按钮仍映射到同月同日最新线上行，因此物品、数量和 ConfigId 都来自原表。月累计面板无法通过
网络响应动态注入 datatable 行，所以 `tools/_patch_datatable.py` 另把 `SignInRewardMonth` 最新完整年度
模板的 `Year` 滚动到当前 UTC 年，保留 `_id/Times/RewardsArr`。2026-08 实际生成：

| `_id` | 天数 | 奖励 |
|-------|------|------|
| 1154 | 7 | 20149 ×1 |
| 1155 | 14 | 110363 ×1 |
| 1156 | 21 | 110828 ×1 |

补丁幂等，只改 `client-test` 的 datatable bundle，不改 DLL。客户端必须完全退出再启动才能重新载入表。

## 4. 活动配置能否只改服务端后生效

结论不是统一的“能”或“不能”，取决于配置由哪一端读取。

服务器运行时从 MySQL `game_config_nodes` 加载配置，不读取 `datatable_json/*.json`。`datatable_json` 仅作为
客户端逆向/离线参考；服务端可编辑配置必须先写入 YAML/YML，再发布到 MySQL。
监听、管理命令或热重载。因此即使是纯服务端字段，编辑 JSON 后对正在运行的进程也不生效，必须重启。

| 改动 | 只改服务端 JSON 并重启 | 原因 |
|------|-------------------------|------|
| 已有活动 ID 的服务端等级门槛、体力成本、怪物 HP/攻防、经验、掉落、奖励数量 | 可以影响服务端判定和结算 | 权威运算在服务端 |
| 已有活动 ID 对应的阶段怪物组合 | 可以改变实际进场阵容，但模型必须是客户端已有 ID | 服务端发 MonsterId，客户端按本地表找模型 |
| 活动名称、说明、图标、开放日、按钮排列 | 不可以改变客户端显示 | `ActiveUI.ShowDay` 读取客户端本地 `ActivePerDayConfig.activeIdDic` |
| 新增一个客户端不存在的活动 ID | 不会自动出现入口 | 客户端没有该行和按钮来源 |
| 怪物名称、Prefab、Skin、Effect | 不可以只靠服务端新增资源 | 客户端本地表和 bundle 决定显示资源 |
| 2026 月累计签到按钮 | 不可以只改服务端；当前 `client-test` 已同步补表 | 客户端按 `UtcNow` 的年月筛本地 `SignInRewardMonth` |
| 已有 ID 的后台开放/关闭校验 | 可以 | 服务器可以拒绝或允许请求，但客户端入口文字和状态不会随之自动改变 |

还有两个安全条件：

- 双方共享的 ConfigId 必须在客户端本地表存在；服务端发一个客户端未知 ID，轻则空白，重则 `Get` 返回
  null 后界面异常。
- 只改服务端数值时，客户端预览仍可能显示旧值。实际结算可以正确，但“展示与实际一致”要求双方表同步。

因此目前可行的运维方式是：修改服务端已有 ID 的后台规则，重启后生效；凡涉及入口、文字、日期、模型、
图标或特效，都不能承诺仅改服务端完整生效。月累计签到属于双方表同步，已由幂等补丁处理；仍没有热重载。

## 5. 验证基线

```text
go test ./...
go vet ./...
python verify_signin.py
python tools/_patch_datatable.py
```

`signin_test.go` 覆盖日期模板、错误 ID、线上奖励、重复领取、背包满原子性、跨月清零、tag 3 `Times`
和 **MySQL 重载**；`verify_signin.py` 通过正式 TCP 新建隔离账号验证 20423/20419/20420 及落库状态。

2026-08-18 实测：玩家 3250 收到 `signinCurrId=2566`，领取严格得到 `110204 x30`，重复请求被拒绝，
数据库恢复出 `LastDay=20260818、MonthCount=1`。补丁后 bundle 已核对出 2026-08 三档 `1154/1155/1156`；
再次运行补丁输出 `already contains year 2026`，不会重复改行。
