# 客户端基准全功能差距分析（2026-08-26）

> 分析日期：2026-08-26（Asia/Shanghai）  
> 客户端基准：`client-test/`  
> 唯一现行服务端：`server-mysql/`（MySQL + Redis + TCP）  
> 离线参考：`datatable_json/`、`参考数据/protocol_dump.txt`、客户端 Hotfix/HotfixView 反汇编  
> 本文是差距审计，不代表已经完成真客户端逐项验收；`server/` 旧 SQLite 实现不作为完成度依据。

## 1. 总结论

当前版本已经不是“只有协议空回包”的状态：主线、试炼、世界 Boss、家族 Boss、手工副本、
星空旅行、多人战斗、技能状态机、线上血量和大部分掉落链都有实际服务端实现，也有较多 Go
回归覆盖。但按“必须与客户端一致、功能完整可玩”的标准，**目前仍不能判定为完美完成**。

最重要的结论如下：

1. **家族 Boss 血量链已补齐，但真实 HUD 仍未画面验收。** 发起者收到 `20144`，队友收到一次
   `M2C_ReSendFamilyBossInfo(20145)`，战斗中的 HP 变化继续走权威 `20169`；服务端回归已覆盖顺序、
   初始 HP、残血持久化和退出重登位置，但尚未用 Unity 截图证明 HUD 像素/文本可见。
2. **Boss/副本怪已改用模型原生 Attack/Hurt，但外加技能光效仍不是逐 Boss 还原。** 42 个怪物技能的线上
   `SkillConfig.EffectId/HurtEffectId` 都为空；现行服务端通过 `20076` 播放施法者模型 Attack、通过
   `20078` 播放目标 Hurt，不再臆造 `3001/3002`。模型动作链已经可测，逐 Boss 外加弹道/范围光效仍无权威配置。
3. **战斗掉落的背包满分支已改为邮件保管。** 普通物品和装备无法入包时生成可领取系统邮件，
   货币仍只结算一次；领取链保持原子性，不再静默丢失物品。
4. **社交频道和好友离线一致性已修复。** 普通/队伍/家族/阵营/世界频道按范围路由，System 伪造被拒；
   好友查找、申请、同意、删除均支持离线目标并做 MySQL 双向关系维护。
5. **邮件已实现客户端页码、过期清理和确认删除语义。** 每页 10 封，`MailCount` 为总页数；过期邮件在
   访问/领取/删除前清理；单删和一键删允许客户端确认后移除未领取附件。
6. **右侧光圈的客户端目标集合已做配置全覆盖回归，但“能进图”不等于“玩法完整”。** 主线、试炼、
   Boss、手工副本已有配置级测试；`10030-10032` 三个 PVP 场景直接换图后没有独立地图玩法，真正
   PVP 由匹配/切磋协议启动；仍需真实客户端逐按钮画面验收。
7. **转生主链路已实现，但还不能称为完美。** 0-3 转、两个客户端入口、累计等级阈值、属性加成、
   持久化和数值溢出保护均已实现；但 `Level=2` 的权威语义、额外消耗/任务条件、真实客户端刷新和
   12 个职业/转生组合的完整端到端表现仍未由原服抓包或真客户端 TCP 回归证明。

## 2. 审计口径与证据等级

本文按下面三类证据区分“已实现”和“已验收”：

| 等级 | 含义 |
|------|------|
| A | 客户端反汇编/原版表、现行服务端实现、自动测试三者能够互相对应 |
| B | 客户端与服务端逻辑能对应，Go/协议测试通过，但缺少真实客户端画面或完整 TCP 验收 |
| C | 只有静态代码或推断，或者已有用户问题但没有稳定复现闭环 |

状态含义：

- **已实现**：核心行为存在，但仍可能需要画面验收。
- **部分实现**：主链存在，仍有明确简化或缺口。
- **未验收**：代码看似存在，但不能据此宣布客户端功能正常。
- **明确缺陷**：已经能从代码或客户端行为证明不一致。

## 4. 战斗表现：攻击、技能名、特效与弹道

### 4.1 当前服务端实际发送链

怪物攻击不是只扣后台数值。现行链路会发送：

1. `M2C_PlaySkill(20075)`：客户端技能名称/施法提示。
2. `M2C_MonsterPlaySkill(20076)`：客户端怪物攻击动作。
3. `M2C_PlaySkillEffect(20077)`：视觉或弹道。
4. `M2C_BattleSkillRet(20078)`：受击动作、飘字、暴击标记。
5. `M2C_SyncUnitAttribute(20169)`：当前/最大 HP 权威同步。

服务端技能选择来自 `MonsterBase.SkillGroupId → SkillGroupBase.SkillsArr`，不是所有怪固定一个技能。
对应代码主要在：

- `server-mysql/battle_skill_runtime.go`
- `server-mysql/battle_skill_events.go`
- `server-mysql/battle_skill_projectile.go`
- `server-mysql/battle_actions.go`

`battle_presentation_test.go` 已验证一次怪物攻击同时出现技能名、原生怪物攻击动作、受击和 HP 包。

### 4.2 Boss/副本怪特效的确定差距

离线核对 `datatable_json/SkillConfig.json`：怪物技能 `50000100..50004200` 共 42 行，
42 行的 `EffectId` 和 `HurtEffectId` 都为空。提交 `7fdd0ab` 后，怪物统一使用其模型原生动画，
服务端不再为怪物臆造 `3001/3002`，也会过滤怪物技能逻辑内的 `20077` 表现节点，但保留其子节点中的
伤害、治疗、护盾、状态和其他权威数值逻辑：

```text
20075 PlaySkill          → 技能名称/提示
20076 MonsterPlaySkill   → Boss/副本怪模型播放 Attack
20078 BattleSkillRet     → 目标模型播放 Hurt、显示伤害飘字
20169 SyncUnitAttribute  → 权威 HP 更新
```

`Hurt` 是目标受击动画，不能单独代替施法者动作；与 `20076` 的模型 `Attack` 配合后构成完整攻击表现。
治疗、护盾、无敌等不造成伤害的技能不会伪发 `20078`，避免把增益表现成受击。

因此当前状态应表述为：

- 攻击动作：有。
- 技能名称：有。
- 伤害与血量：有。
- 模型 Attack/Hurt：有，并且不依赖缺失的 `EffectId/HurtEffectId`。
- 外加弹道/范围光效：怪物默认不发送；客户端表没有权威配置时不猜测。

当前对应实现为：`battle_presentation_test.go:71`
`TestMonsterSkillsPreserveProjectilesAndIncludeConfiguredModifierVisuals` 遍历 42 个可释放怪物技能，

`battle_presentation_test.go:181` `TestMissingMonsterVisualUsesModelAttackAndHurt` 验证实际服务端输出包含

### 4.3 “特效偶发消失”日志专项

2026-08-26 12:51:09 前的本地客户端 `Player.log` 连续记录了 17 次相同异常：

```text
System.NullReferenceException: Object reference not set to an instance of an object
  at ET.M2C_BattleChangeStateHandler+<Run>d__0.MoveNext () [0x000bc]
```

客户端反汇编确认了异常链：玩家 Unit 创建时会添加 `BuffComponent`，Boss/副本怪创建分支只添加
`NumericComponent`；而 `M2C_BattleChangeState(20080)` 处理器取得目标 Unit 后，会直接执行
`GetComponent<BuffComponent>().AddBuff()`，没有空值保护。服务端此前会把怪物 Buff、Debuff、Modifier
以及战斗结束清理状态也广播成怪物目标 `20080`，其中胜利清理会在同一时段集中触发异常。该异常会中断
客户端消息处理协程，因此玩家看到的现象可能表现为 Boss 攻击、受击或后续技能特效偶发缺失，而不只是
一个不可见的 Buff 图标错误。

提交 `a8b21af` 已按客户端实际组件边界修复：只有目标为玩家的战斗状态才发送 `20080`；怪物的状态、
修饰器和伤害计算仍在服务端生效，不向缺少 `BuffComponent` 的怪物发送客户端无法处理的状态包。
`20075/20076/20078/20169` 攻击链没有被删改。

验证结果：

- `go test ./... -count=1` 全部通过。
- `test/verify_taskbattle.py` 通过，胜利清理阶段没有怪物目标 `20080`。
- `test/verify_multiplayer.py` 通过，两名真实 TCP 玩家均收到 Boss `20076 Attack`、`20078 Hurt` 和
  `20169 HP`，Boss UnitId 没有出现在任何 `20080.TargetUnitId`。
- `test/verify_five_member_dungeon.py` 通过，5 名真实 TCP 玩家可组队进入副本战斗。

修复前日志最后写入时间早于修复后服务端启动时间，因此其中 17 次异常均属于修复前会话。
13:14:23 已重新启动 `client-test`；新日志在启动阶段的 `M2C_BattleChangeStateHandler` 和
`NullReferenceException` 计数均为 0。协议级根因已经关闭，但新会话尚未完成战斗；仍需连续进行世界 Boss、
家族 Boss 和副本战斗，再检查新 `Player.log` 与实际画面，才能完成 Unity 真机闭环。

### 4.4 人物攻击特效与弹道

人物技能的情况好于怪物技能：

- `withConfiguredSkillPresentation()` 使用线上 `SkillConfig.EffectId/HurtEffectId/DelayTime`。

- 弹道从施法者 `AtkPosition` 移到目标 `AtkPosition`，时间为 `Time / 1000` 秒，证明服务端毫秒单位正确。
- ⚠ **2026-09-14 更正**：测试名已改，现为
  `TestEveryDamagingPlayerSkillHasClientPresentation`（`battle_presentation_test.go:14`）；

## 6. 掉落物品与奖励结算

### 6.1 线上掉落链

现行通用掉落逻辑为：

```text
MonsterBase.Dropasubset / FamilyBossConfig.Dropasubset
  → Parentset.SubsetArr（每个子集都处理）
  → SonSet.DropArr（按 Weight 选一个）
  → _Id=0 表示本子集未掉落
  → MinCount..MaxCount 随机数量
```

特殊物品 `110201/110202/110203/110204` 分别进入经验、元宝、金币、代金券，不占普通背包格；
其他物品按线上堆叠限制入包。

当前主要来源：

| 来源 | 当前实现 |
|------|----------|
| 普通/主线/世界 Boss | 读取各 `MonsterBase.Dropasubset`，按 `CopyRewordConfig` 是否允许怪物掉落结算 |
| 试炼 | 每只怪的经验和 Parentset 链；记录最高层；另有每日汇总领取 |

## 13. 转生系统专项结论

### 13.1 客户端已确认行为

- `Quest1UI.TransLevel` 发送 `C2M_TransLevel{Level=1}`。
- `ButlerUI.AddTransLevel2` 发送 `C2M_TransLevel{Level=2}`。
- 响应 `Message` 非空时弹提示，成功后客户端没有本地加转逻辑，必须依赖服务端同步。
- 客户端等级文案同时读取累计等级 `1026` 和转生层数 `1029`。
- 客户端累计等级分段为 `0 / 6000 / 13000 / 21500 / 31500`。

### 13.2 当前服务端已实现

- 只接受 `Level=1` 或 `2`。
- ⚠ **2026-09-14 更正**：原文写「当前实现把请求值解释为“增加 1 转/增加 2 转”」，**这是错的**。
  实现把请求值解释为**目标阶数本身**，并在 `newTrans <= 当前阶` 时拒绝（回「已达转生等级」），
  不是叠加（`server-mysql/trans.go:120-138`，回归 `trans_test.go`）。上限 3 转正确。
- 新转生层数对应最低累计等级：一转 6000、二转 13000、三转 21500。
- 保存累计等级而不是重置后的局部等级；旧局部等级存档会迁移。
- `TransmigrationAddConfig` 12 行（4 职业族 × 3 转）按 `jobType*10+trans` 读取。
- `AddAttributeArr` 通过完整 `AttributeType → NumericType` 映射进入 `transBonus`，包括整数属性和比例属性。
- 成功后发送 `20169(1029)`、`20257 SendCharacter` 和完整属性刷新，并保存 MySQL。
- 高等级成长计算和属性求和有 int32 饱和保护，不会绕回负数。

### 13.3 为什么仍不能称为完美

1. 客户端只证明两个入口分别发送字面量 1 和 2，不能单独证明线上服务端把 2 解释为“一次增加两转”；
   它也可能是入口类型或目标模式。需要原服请求/响应和同步后的 `Trans` 抓包。
2. 当前 `TransmigrationAddConfig` 只有属性加成，没有任务、物品、货币、经验消耗字段；服务端也只校验累计等级。
   是否还有其他前置条件尚无权威证据，不能擅自添加，也不能宣称一定没有。
3. 没有找到正式 TCP 脚本覆盖 `20342 → 20343 → 20169/20257`。
4. 没有真实客户端验证 0→1、0→2、1→3、越级失败、满转失败、重登后等级文案和全部属性面板。
5. 现有测试验证属性进入服务端数值通道，但仍需验证 12 个组合在伤害、命中、抵抗、暴击、治疗、免伤、
   控制命中/抗性和排行榜战力中都按同一套数值生效。（**没有"闪避"这一项**：客户端枚举里不存在闪避，
   `Dvo=1017` 的真实语义是辅助值，见 11 文档 §2.5 的命名更正。）

因此转生结论是：**服务端主链和数值框架已经较完整，但未达到“与客户端/原服完美一致”的证据标准。**
