## 1. 总体架构（历史 UDP/KCP 稿，已过时）

```
Unity 客户端 (Mono, ET框架)                    Go 服务器
  UDP Socket ──SYN/ACK/FIN/MSG──>  net.ListenUDP("udp", :7756)
      │                                │  单 goroutine 收包循环
      │                                ▼
      │                        ┌──────────────────┐
      └───── MSG [0x04][C][KCP] │ channel 表        │  key = 客户端 LocalConn C
                                │  conv → channel   │
                                └──────────────────┘
                                      每个 channel:
                                       ├ KCP 实例 (kcp-go, conv=S)
                                       ├ 会话状态 (登录态/玩家数据/RPC 待回)
                                       └ 输出回调 → 拼 [0x04][S][KCP段(段头改C)]
```

- 单一 UDP 端口 7756 同时承担"登录/网关"两种角色（先用同一端口，按消息类型区分）。
- 每个客户端 = 一个 `channel` 对象：`{ LocalConn: S, RemoteConn: C, RemoteAddr, kcp, session }`。

## 4. UDP 收包与握手状态机

### 4.1 收包循环

```go
buf := make([]byte, 2048)
for {
    n, addr, _ := conn.ReadFromUDP(buf)
    switch buf[0] {
    case 0x01: handleSYN(buf[:n], addr)   // SYN
    case 0x02:                            // ACK —— 服务器一般不发主动连，忽略
    case 0x03: handleFIN(buf[:n], addr)   // FIN
    case 0x04: handleMSG(buf[:n], addr)   // MSG
    }
}
```

### 4.2 SYN（0x01，9 字节）

```
[0x01][LocalConn C u32][RemoteConn 0 u32]
```

```go
func handleSYN(b []byte, addr *net.UDPAddr) {
    if len(b) != 9 { return }
    c := le.Uint32(b[1:5])                       // 客户端 LocalConn C
    if _, dup := channels[c]; dup { return }     // 已存在则忽略
    s := CreateRandomLocalConn()                 // 0x40000000 | rand
    ch := newChannel(s, c, addr)                 // LocalConn=S, RemoteConn=C
    channels[s] = ch                             // 路由表：S → channel（MSG 按段头 conv=S 命中，见 §4.4）
    send(addr, 0x02, s, c)                       // ACK [0x02][S][C]
}
```

- 收包路由表用 `channels[客户端 LocalConn C]`。为什么？见 §5.3 的 conv 说明。
- 服务器不校验"来自同一地址的重复 SYN"过多的情况可加个计时器清理（超时无 MSG 则删）。

### 4.3 FIN（0x03，13 字节）

```
[0x03][localConn u32][remoteConn u32][error i32]
```

收到 FIN：按 `channels[remoteConn]`（FIN 里 remoteConn = 服务器 LocalConn S）找 channel，
校验地址一致后删除 channel、清理 KCP、通知上层下线。

### 4.4 MSG（0x04，长度 ≥ 9）

```
[0x04][发送方LocalConn u32][KCP段，从 offset 5 开始]
```

```go
func handleMSG(b []byte, addr *net.UDPAddr) {
    sender := le.Uint32(b[1:5])     // = 客户端 C
    conv   := le.Uint32(b[5:9])     // KCP 段头 conv —— 客户端发来的恒为 S（见 §5）
    ch := channels[conv]            // ET 语义：GetByLocalConn(段头conv)
    if ch == nil { sendFIN(addr, 0, sender, 100216); return }
    if ch.RemoteConn != sender { return }   // 校验发送方 == 客户端 LocalConn
    if addr.String() != ch.RemoteAddr.String() { return } // 可选地址校验
    kcp.Input(b[5:])                // 喂给该 channel 的 KCP 实例
    // 驱动 kcp.Update 后收出完整消息 → ch.session.dispatch(stream)
}
```

> `conv` 恒等于 S（服务器 LocalConn），因为客户端 KCP 实例 conv=S（02 文档 §3.2）。
> 用 `channels[conv]` 即 `channels[S]` → 直接命中本 channel（每个 channel 记录自己的 S）。

## 5. KCP 实例管理（conv 校验问题与解法）

### 5.1 背景（回忆 02 文档 §3）

- 客户端 KCP 实例 conv = **S**（服务器 LocalConn），发送段头恒为 S。
- ET 服务器 KCP 实例 conv = **C**（客户端 LocalConn），发送段头恒为 C。
- **ET 在两端都禁用了 KCP 内部 conv 校验**（ikcp_input 不比对），否则收发段头不同会互相拒绝。
- 客户端收包路由：`GetByLocalConn(段头 conv=C)`。

### 5.2 问题

kcp-go 的 `KCP.Input` **默认校验**段头 conv 与实例 conv 一致，不一致返回 -1 并回 WASK。
若照搬 ET（服务器实例 conv=C），客户端发来的段头是 S → 校验失败 → 无法通信。

### 5.3 解法（推荐：段头改写，不改库）

让服务器 KCP 实例 conv = **S**（= 自己的 LocalConn），并在输出回调里把**所有**段头改写为 C：

```
服务器 KCP 实例:  NewKCP(S, output)          // 实例 conv = S
接收:            客户端段头 S → Input 校验 S==S ✓（无需改库）
发送:            output 回调拿到的段头是 S → 改为 C → 拼 [0x04][S][段]
客户端接收:      段头 C → GetByLocalConn(C) 命中 ✓（客户端本地 key 只有 C）
```

```go
output := func(buf []byte, size int) {
    // buf 前 4 字节是 KCP 段头 conv，改写为客户端 LocalConn C
    le.PutUint32(buf[:4], ch.RemoteConn)   // C
    out := make([]byte, 5+size)
    out[0] = 0x04
    le.PutUint32(out[1:5], ch.LocalConn)   // S
    copy(out[5:], buf[:size])
    conn.WriteToUDP(out, ch.RemoteAddr)
}
kcp := kcp.NewKCP(S, output)   // conv = S
kcp.NoDelay(1, 10, 2, 1)       // 注意：kcp-go v5 方法名是 NoDelay/WndSize，无 Set 前缀
kcp.WndSize(128, 128)
kcp.SetMtu(470)                // 必须与客户端 Outer 一致
```

> 为什么改段头不影响 KCP 状态机？KCP 段头 conv 只用于对端路由/校验，不参与序号、窗口、
> ACK 等逻辑；客户端禁用校验，收到 C 段头照常处理。服务器的 Input 校验对象是"客户端发来的段头"
> = S，与实例 conv S 一致，天然通过。

### 5.4 备选（不改段头，改库）

fork `kcp-go`，删掉/注释 `Input` 中 `if k.conv != conv` 的拒绝分支（保留 WASK 可选）。
此时可保持 ET 完全语义：服务器实例 conv=C，段头不改写。缺点是要维护 fork 依赖。

## 6. 消息分帧与序列化（Outer）

### 6.1 接收：KCP 段 → 一条 Session 消息

- 每从 `kcp.Recv` 取出一段（`kcp-go` 自动重组分片），该段即一条 Outer 消息。
- 布局：`[u16 opcode LE][protobuf body]`，**无长度头**（03 文档 §1）。
- 取 opcode：`binary.LittleEndian.Uint16(seg[:2])`；body = `seg[2:]`。
- 反序列化：opcode < 40000 用 `proto.Unmarshal(body, msg)`；≥40000 用 JSON（本游戏不涉及）。

### 6.2 发送：封装一条 Outer 消息

```go
func packOuter(opcode uint16, body []byte) []byte {
    out := make([]byte, 2+len(body))
    le.PutUint16(out, opcode)
    copy(out[2:], body)
    return out    // 之后 ch.kcp.Send(out)
}
```

> 注意：ET 里 opcode 是 u16（WriteTo 2 字节）。429 条消息 opcode 最大 < 65535，够用。

### 6.3 protobuf 兼容

- 客户端 ET 用标准 proto3（`ProtobufHelper.ToStream`）：零值字段不写、varint 定长。
- Go 侧 `proto.Marshal` / `proto.Unmarshal` 天然兼容；字段 tag 以 `protocol.proto` 为准。
- 注意 `RpcId`（tag=90）是普通 protobuf 字段，随 body 一起编解码（03 文档 §1.3）。

## 7. 登录流程处理

统一入口：按 opcode 分发到 handler。响应一律 `RpcId` 原样回填。

```
┌─ opcode 20008 C2R_Login ────────────────┐
│  校验账号/密码 → 生成 Key(int64)         │
│  回 R2C_Login{Address:"127.0.0.1:7756", │
│              Key, GateId:1,             │
│              LoginVoucher, RpcId:回填}   │
└─────────────────────────────────────────┘
┌─ opcode 20014 C2G_LoginGate ────────────┐
│  校验 Key 是本服签发 + GateId 匹配       │
│  建玩家会话 → 回 G2C_LoginGate{         │
│     PlayerId, HasRole:true, JobId,      │
│     ServerTime, SkinId, RpcId:回填}      │
└─────────────────────────────────────────┘
┌─ opcode 20027 C2G_EnterGame ────────────┐
│  确认角色 → 回 G2C_EnterGame{           │
│     Id, SkinId, JobId, IsOnline,        │
│     RpcId:回填}                          │
└─────────────────────────────────────────┘
```

- 错误时：`resp.Error = 错误码`（非 0），客户端按 `IsRpcNeedThrowException` 处理。
- `HasRole` 为 false 时客户端可能先走 `C2R_CreateRole`（20016）建角色，再登录。
- `ServerTime` 用服务器 Unix 毫秒即可。

## 8. 心跳与保活

- `C2G_HeartBeat`(20012) → 回 `G2C_HeartBeat{ DelayTime, Key, RpcId 回填 }`。
- 客户端 SYN 握手超时 10s、发送队列上限（Outer 10240）由客户端自身控制，服务器无需干预。
- 服务器侧清理：channel 连续 N 秒无任何 MSG（或 KCP 层检测对端失联）→ 发 FIN 删除。
