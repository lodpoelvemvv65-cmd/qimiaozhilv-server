## 0. 结论

| 问题 | 答案 |
|------|------|
| 怪物有没有控制技能？ | **有，9 个 modifier**：眩晕 ×5（stateK 9）、沉默 ×2（stateK 8）、石化 ×2（stateK 11） |
| 覆盖多少怪物？ | **276 / 713 只（38.7%）** 的技能组里含至少一个控制技能 |
| 对人物生效吗？ | **生效。** 线上日志实证：`500041` 命中玩家 → 下发 `20080` → 玩家随后两次施法被拒 `cannot cast`，间隔正好 6 秒 ×2 = 12 秒，与配置的 12 秒时长吻合 |

### 2.2 拦截点在代码里的位置

```go
// battle_skill_runtime.go:192 —— 玩家施法的唯一闸门
if !battle.runtime.CanCast(battle.runtime.Player()) {
    return reject("cannot cast")
}
```

```go
// battle_effects.go:698-708
func (r *CombatRuntime) CanAct(ref CombatUnitRef) bool {
	...
	return !r.hasAnyStatus(unit.Ref, CombatStatusStunned, CombatStatusFrozen, CombatStatusPetrified)
}
func (r *CombatRuntime) CanCast(ref CombatUnitRef) bool {
	return r.CanAct(ref) && !r.HasStatus(ref, CombatStatusSilenced)
}
```

- 眩晕 / 冰冻 / 石化 → `CanAct` 为假 → 什么都不能做；
- 沉默 → `CanAct` 仍为真，但 `CanCast` 为假 → 不能用技能（普攻另走 `battle_actions.go` 的路径）。

### 2.2.1 ★「怪物打玩家是必中的」—— 对，但只对**直伤**成立；**状态**照常对抗

代码里两件事走**完全不同的路**，很容易混为一谈：

```go
// battle_damage_accuracy.go:17-19 —— 怪物→玩家的直伤：写死必中
if source.Side == CombatSideMonster && target.Side == CombatSidePlayer {
    return true
}
```

文件注释解释了原因：

> Online MonsterBase has no Hit/Res fields on any encounter monster. Applying a
> player's percentage-form Resistance to direct monster damage therefore makes
> late-game monsters miss almost forever. **Resistance still contests harmful
> monster statuses** through statusContestChance; only the direct PvE damage
> component is guaranteed to land.

| 通道 | 是否对抗 | 依据 |
|------|----------|------|
| 怪物 → 玩家的**直接伤害** | **必中**（`return true`） | `battle_damage_accuracy.go:17` |
| 怪物 → 玩家的**有害状态**（眩晕/沉默/石化/中毒…） | **看玩家抗性** | `battle_status_accuracy.go` `statusContestChance` |

**所以「用钱砸死你 是必中的」这句话：**
- 说**伤害**必中 → **对**，130% 物理伤害不打折地必中；
- 说**眩晕**也必中、不看抗性 → **不对**，见下。

### 2.3 控制几率会被玩家抵抗削减

怪物 → 玩家方向的对抗（`battle_status_accuracy.go`）：

```
线上 MonsterBase 没有 Hit 字段 ⇒ 怪物命中恒为 0
有效几率 = 配置几率 × 100 / (100 + 玩家抗性)
```

实测（新增测试 `TestMonsterControlChanceIsReducedByPlayerResistance`，500041 跑 4000 次）：

```
500041 眩晕落地率：抗性 0 → 0.947（配置 95%）, 抗性 245.6 → 0.270（期望 0.275）
```

即：**空号几乎必被控（94.7%），毕业装玩家只剩 27%。** 玩家堆「抵抗」在 PvE 里是有意义的。

## 4. 顺带发现的三处**配置侧**瑕疵（都不影响功能）

## 4.5 ★ 全量 stateK 覆盖审计 —— 发现一处真实缺口（`stateK=14` 必定暴击）

把 `SkillLogicConfig` 里**所有**非零 `stateK` 列出来，逐个对照 `combatStatusForStateKey`：

| stateK | 服务端映射 | 用例数 | 兜底 | 判定 |
|--------|-----------|--------|------|------|
| 1 | Invincible | 2 | — | ✓ |
| 4 / 5 | Undying | 1 / 1 | — | ✓ |
| 8 | Silenced | 6 | — | ✓ |
| 9 | Stunned | 9 | — | ✓ |
| 10 | Frozen | 3 | — | ✓ |
| 11 | Petrified | 4 | — | ✓ |
| **14** | **无映射 → `CombatStatusNone`** | **1** | **无** | **★ 缺口** |
| 15 | Invisible | 1 | — | ✓ |
| 100 | 无映射 | 5 | 子节点 `shield` | ✓ |
| 101 | 无映射 | 2 | 子节点 `reflect` | ✓ |
| 102 | 无映射 | 3 | 子节点 `counter` | ✓ |
| 104 / 105 / 106 | 无映射 | 5 / 7 / 5 | 子节点 DoT（中毒/流血/点燃） | ✓ |
| 107 | 无映射 | 1 | 子节点 HoT | ✓ |

> `100/101/102/104~107` 这批**不是缺口**：它们只是客户端的图标槽（`effectMeta` 用），
> 真正的效果由**子节点**（`SkillOption_护盾` / `_反伤` / `_反击` / DoT / HoT）承载。
> doc 32 §4.4 已记录同一结论。

### ★ 缺口：`stateK=14`「必定暴击」

**技能**：210601 **猛虎式射门**（体育生，CD 12s）
**desc**：「其势如虎，其速如风，给敌人致命1击，造成巨额物理伤害。对敌方造成物理伤害，**必定暴击**，增加物理攻击力，几率降低对方物理攻击和防御。」

配置里的执行树（从 `plan_snapshot.json` 还原，**顺序很关键**）：

```
projectile ev=1 → cast_target
  └ status 21060116 (ev=1, 伤害 modifier，挂到敌人身上)
      ├ damage   ev=0   self=258% 物理, can_crit=True     ← 伤害在这里
      ├ chance   ev=0   → 35%: status 21060114 (stateK=9 眩晕)
      ├ status   ev=24  mod=21060117  stateK=14  dur=1s  target=self   ← 必定暴击
      └ status   ev=24  mod=21060111  stateK=0   dur=8s  target=self   ← +物攻
```

`event 24` = 「本 modifier 创建之前」（`applyStatusEffectWithContext` 里 event-24 循环跑在
属性/控制/子节点之前）。**所以「必定暴击」确实先于伤害生效，设计意图明确。**

服务端的实际结果：

| 环节 | 结果 |
|------|------|
| `combatStatusForStateKey(14)` | `CombatStatusNone` → 控制分支跳过 |
| `combatAttributesForValueKey(0)` | `nil` → 属性分支跳过 |
| `modifierEventDic` | `null` → 无子节点 |
| `iconId = "0"` | `normalizeClientBuffIcon` 失败 → **连 20080 都不发** |
| 最终 | 只落一个惰性 `CombatStatusMarker`（duration 1s） |

**→ 伤害仍然按普通暴击率掷骰，「必定暴击」完全没有实现。**
全仓库 `grep 必定暴击|guaranteedCrit|AlwaysCrit` **零命中**。

而且 `statusPolarity` 的注释里明确把 `stateK=14` 列为已知的有益状态
（"beneficial states (invincible, undying, **guaranteed-crit**, shield, counter, reflect and invisibility)"），
`case 1, 4, 5, 14, 15, 100, 101, 102, 107: return CombatEffectBeneficial` —— 
**极性表认了它，状态映射表却漏了它**，是一处自相矛盾。

**建议的修法**（未实施，按项目规则需单独提交）：

1. `CombatStatus` 加一个 `CombatStatusGuaranteedCrit`；
2. `combatStatusForStateKey` 加 `case 14`；
3. `damageOutcome` 里，若 `source` 身上有该状态则 `critical = true`（跳过掷骰）。

**回归测试**：`TestGuaranteedCritModifierIsConfiguredButUnmapped`
（锁住配置契约 —— self / event 24 / 1s / modifier 21060117 —— 并在实现后自动 `t.Skip` 提醒补断言）。
