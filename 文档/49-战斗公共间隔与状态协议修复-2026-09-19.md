## 2. 公共出手间隔

### 2.1 线上抓包证据

`20237 M2C_StartCD` 的 tag 1 是角色自己的公共出手间隔，不是职业常量，也不是全局 6000ms：

| 客户端端口 | 角色 | 帧数 | tag 1 |
|---:|---:|---:|---:|
| 61643 | 22233（运动员） | 49 | 4554ms |
| 61674 | 其它角色 | 59 | 4000ms |
| 61713 | 其它角色 | 40 | 4000ms |
| 61738 | 其它角色 | 64 | 4000ms |
| 62269 | 其它角色 | 24 | 4000ms |

22233 的连续施法时刻为 `77.483604 / 82.037170 / 86.591495 / 91.145792 / 95.702339`，相邻间隔约 4.554 秒，与 `20237[1]=4554` 一致。历史抓包另有 4746ms 和 6000ms，同职业也可出现不同值，因此不能按职业写死。

### 2.2 修复公式与边界

当前实现用角色完整属性 `Speed(1031)` 拟合已知样本：

```text
public_interval_ms = clamp(round(6000 - Speed), 4000, 6000)
```

校验点：`Speed=0 → 6000`、`1254 → 4746`、`1446 → 4554`、`Speed>=2000 → 4000`。

Speed 来自当前角色完整数值链，包括 CharacterGrowth、装备、星魂、转生和宠物。该公式同时用于：

- 下一次玩家权威出手时间；
- 自动战斗下一次可施法时间；
- `20237 M2C_StartCD.Time` 的客户端公共 CD 表现。

> 2026-09-20 复核更正：怪物并非全部固定 6000ms。普通怪物当前按
> `round(Level*0.045)` 拟合 Speed 后复用 `6000-Speed` 换算；五阶家族 BOSS 使用独立的
> 4710ms 网格。控制只让 BOSS 跳过完整拍点，不改变基础周期。详见文档 50。

怪物仍使用独立于玩家的动作时钟；开场首击仍为开战后 5 秒。玩家自动出手不再被怪物波次拖慢。

证据边界：这是根据当前线上样本拟合出的公式，不是从线上服务端源码恢复的公式。以后出现不符合 `6000-Speed` 的新样本时，应以新抓包修正。

## 3. `20080 M2C_BattleChangeState.Id`

### 3.1 差异与客户端语义

线上单流 570 个 `20080` 帧有 570 个不同的 19 位 ID；同一目标重复中毒、眩晕也每次换新 ID。同一 tick 给五人加盾时 ID 连续变化，不复用 modifier ID。

客户端 `BuffComponent.AddBuff` 实际执行：

```text
buffList[BuffStateInfo.Id] = BuffStateInfo
```

因此 ID 是客户端字典键，不是展示字段。旧实现固定发送 `meta.modifierID`，重复施加会覆盖同一字典项，与线上不一致。

### 3.2 修复后生命周期

- `Applied / Refreshed / Stacked` 每次 Add 都生成进程内唯一、单调递增的 19 位实例 ID。
- 同一事件广播给多名队员前只生成一次 ID，因此所有接收者看到同一个状态实例。
- 每个会话按 `(TargetUnitId, Id)` 跟踪实例，并记录效果键、图标、`IsBuff` 和到期时间。
- 自然到期只删除服务端跟踪，不发送 `Reduce`，与抓包 570 帧全部为 Add 一致。
- 本地强制清理、离图或当前实现中的驱散会取出该效果全部仍存活实例，并用每个 Add 的原 ID 发送 `Time=0` 的配对 Reduce。

ID 生成器匹配“19 位、每次施加唯一、进程内单调”的已证语义；没有声称复刻线上雪花 ID 的节点位布局。线上真正发生驱散时是否发送 Reduce 仍无抓包样本，继续列为待确认。

## 4. `20075 M2C_PlaySkill` 字段

线上全包 1490 帧 `20075` 只包含：

```text
tag 1  UnitId
tag 2  SkillId
```

旧实现的玩家即时施法、队伍波次排队和旧兼容路径还填写 `CoolTime(tag 3)`、`TargetId(tag 4)`、`MpCost(tag 5)`。其中客户端会消费 `CoolTime`，可能造成与 `20237` 重复的技能冷却表现；其余字段也属于 wire 差异。

修复后所有玩家和怪物发送路径统一只发 tag 1/2：

- 公共间隔：`20237.Time`；
- 技能自身 CD：`20237.SkillCD`；
- 目标：由 `20077 M2C_PlaySkillEffect.TargetId` 及后续伤害/治疗帧表达；
- MP 消耗：由权威属性同步表达。

Go 回归直接解析 protobuf wire tag，要求即时施法和队伍排队路径的字段集合严格等于 `{1,2}`；TCP 实测脚本也同步采用该口径。

## 8. 本地实战发现的断线死锁与修复

2026-09-19 22:14 的五人家族 BOSS 本地实战在团灭回城后出现客户端陆续掉线。现场不是进程崩溃：

- 服务端 PID 仍存在、7756 仍显示监听；
- `S=8~12` 客户端已经停止心跳并关闭 TCP，但服务端没有打印 `conn closed`；
- 新连接能完成操作系统 TCP 握手，却没有服务端 `CONNECT` 日志；
- 进程 CPU 约 0、内存约 71MB，无 panic/fatal。

根因是断线清理在持有全局连接表锁 `Server.mu` 时调用 `stopAutoBattle()` 等待角色 `battleMu`；
组队战斗线程可能正持有多个角色的 `battleMu`，并阻塞在向另一个停止读取的客户端写包，形成锁链。
结果是 accept、在线路由和其它断线清理全部等待同一个 `Server.mu`。

修复提交：`3cf2a34 fix(network): avoid disconnect registry deadlock`。

- 先关闭当前传输，解除并发阻塞写；
- `Server.mu` 内只删除连接路由项，不再等待任何 session/战斗锁；
- 自动战斗停止和完整下线清理移到全局锁外；
- 每次 TCP 写设置 5 秒上限，超时即关闭坏连接，防止无限占住战斗锁；
- 新增回归，明确验证持有 `battleMu` 时连接表仍能查询、掉线连接已经不可路由；
- `go test -race -run TestRemoveChannel` 与 `go test ./... -count=1` 均通过。
