# 20-组队系统

> 逆向还原《梦幻奇遇记》的组队系统：邀请 / 申请入队 / 处理请求 / 转让队长 / 退出 / 踢人，
> 含完整协议（Hotfix.dll 消息类）、客户端菜单与请求 UI 链路（HotfixView.dll 反汇编）、
> 当前服务器实现与真实双连接、五连接回归。
>
> 结论先行：组队 = **全量同步**模型。服务器在队伍任何变化后向所有成员推送
> `M2C_TeamMember{LeaderId, UnitIds}`，客户端 `TeamComponent` 全量重建队伍。
> 邀请/申请只走**异步通知**（`M2C_InviteList`/`M2C_RequestList` 推给目标方弹出请求条），
> 同意/拒绝回 `C2M_HandleTeam`。

## 1. 协议总表

### 1.1 请求→响应（RPC）

| opcode | 消息 | 字段 | 说明 |
|--------|------|------|------|
| 20154→20155 | `C2M_RequestTeam{TargetId=1}` → `M2C_RequestTeam` | TargetId=目标玩家 UnitId | **申请加入** TargetId 的队伍 |
| 20156→20157 | `C2M_InviteTeam{TargetId=1}` → `M2C_InviteTeam` | TargetId=目标玩家 UnitId | **邀请** TargetId 加入我的队伍 |
| 20160→20161 | `C2M_HandleTeam{HandleInfo=1, IsRequest=2}` → `M2C_HandleTeam` | HandleInfo=`ET.HandleInfo`，IsRequest=bool | 处理收到的邀请/申请（同意或拒绝） |
| 20163→20164 | `C2M_TransferTeamLeader{UnitId=1}` → `M2C_TransferTeamLeader` | UnitId=新队长 | 转让队长 |
| 20165→20166 | `C2M_QuitTeam{}` → `M2C_QuitTeam` | — | 退出队伍 |
| 20167→20168 | `C2M_KickoutTeam{TargetId=1}` → `M2C_KickoutTeam` | TargetId=被踢队员 | 踢出队员（仅队长） |
| 20073→20074 | `C2M_SelectTeamMember{Id=1}` → `M2C_SelectTeamMember` | Id=队员 UnitId | 选中队员（战斗内切换目标） |

### 1.2 服务器推送（无请求）

| opcode | 消息 | 字段 | 说明 |
|--------|------|------|------|
| 20158 | `M2C_RequestList{UnitId=1, TimeOut=2}` | UnitId=申请者, TimeOut=超时毫秒 | 推给**队长**：有人申请入队（RequstLabalType=1） |
| 20159 | `M2C_InviteList{UnitId=1, TimeOut=2}` | UnitId=邀请者, TimeOut=超时毫秒 | 推给**被邀请方**：被邀请入队（RequstLabalType=0） |
| 20162 | `M2C_TeamMember{LeaderId=1, UnitIds=2}` | LeaderId=队长, UnitIds=repeated int64（**字段级 List**） | 队伍成员**全量**推送（组队/加人/踢人/退队/转让后都推） |

### 1.3 消息字段详情（_dump_prop.py）

```
HandleInfo{ Id=1(int64), Bool=2(bool) }        ← 注意：不是 TeamRequestInfo！
C2M_HandleTeam{ HandleInfo=1, IsRequest=2 }
M2C_RequestList{ UnitId=1(int64), TimeOut=2(int32) }
M2C_InviteList{ UnitId=1(int64), TimeOut=2(int32) }
M2C_TeamMember{ LeaderId=1(int64), UnitIds=2(repeated int64, 字段级 List) }
```

> ⚠️ `M2C_TeamMember.UnitIds` 是**字段级 ProtoMember**（List 类型），与 BagMapList 一样
> protoc 生成代码不含 → 服务器用手工 protobuf 编码追加（tag=2，wire 2，每个元素 = varint）。

### 1.4 辅助类型

```
RequstLabalType 枚举：0=组队邀请, 1=申请入队
TeamRequestInfo（客户端内部渲染用，非网络消息）：
  Id(long), type(RequstLabalType), name(string), level(int), timeOut(int), job(JobType)
```

### 2.3 队伍成员全量同步

**M2C_TeamMemberHandler**（rid 248，20162）：
1. `TeamComponent.Clear()` — 清空所有队伍
2. `TeamComponent.CreateTeam(message.LeaderId)` — 建队（key=LeaderId）
3. `GlobalVariable.LeaderId = message.LeaderId`
4. 遍历 `message.UnitIds`：
   - `unit = UnitComponent.Get(unitId)`（无空检查，单位缺失会 NRE）
   - `unit.LeaderId = message.LeaderId`
   - **若 `unitId != GlobalVariable.MyId`：`unit.UnitType = UnitType.TeamMember(5)`**
     （IL 实证：beq.s 跳过 → ldc.i4.5 + set_UnitType；给**其他成员**打队伍标记，自己不打）
   - `team.Add(unit)` → `Team.UpdateTeamUI` → Publish `UpdateTeamHeadInfo`

**Team**（rid 397）：`teamMemberDic: Dictionary<long, Entity>`；Add/Remove/RemoveAll 都触发
`UpdateTeamUI`；`MemberCount`、`GetAll()`（OperaComponent.ClickTarget 用的就是它）。

**TeamComponent**（rid 400）：`TeamDic: Dictionary<long, Team>`（key=LeaderId）；

**UpdateTeamHeadInfoEvent**（rid 146）：清空 `TeamMemberHeadInfoDic` →

## 3. 当前服务器实现（Go）

### 3.1 运行态队伍模型

> ⚠ **2026-09-14 更正：下面这段 Go 结构已不是当前实现。**
> `type teamInfo` 与全局 `memberTeam` **在 `server-mysql/` 中都不存在**
> （`memberTeam` 现在只是 `dungeon_team_entry_test.go` 里的一个局部变量名）。
> 现行结构是：
>
> ```go
> type teamState struct {
>     LeaderId int64   // 队长 playerID
>     Members  []int64 // 成员 playerID 列表（首个 = 队长/转让后的新队长）

> ```
>
> `teams` **以生成的队伍 id（`teamSeq`）为键**，不再是「leaderID → team」；
> 成员归属用**每会话的 `session.teamID`** 指针 + `teamEntryOf` 扫描查找，不再维护全局反查表。
> 待处理邀请/申请也不在这个结构里。见 `server-mysql/team.go:73-97`、`session.go:173`。
>
> ~~以下为旧结构（已作废，留档）~~
>
> ```go
> type teamInfo struct {
>     leaderID int64
>     members  map[int64]bool // 成员 UnitId 集合
>     requests map[int64]int64 // 待处理请求：申请者/被邀请者 UnitId → 过期时间戳
> }
> var teams = map[int64]*teamInfo{} // leaderID → team

当前代码位于 **`server-mysql/team.go`**（⚠ 原文写 `server/team.go`，那是已退役的 SQLite 实现；
本文其它位置（§第 186/230 行附近）也已按 `server-mysql/` 书写）。队伍、待处理邀请和申请是在线运行态，不属于角色成长数据；断线会从队伍
移除成员，服务器重启后不会恢复旧队伍。`teamMu` 只保护队伍结构，网络查找和发包均在释放锁后进行，
避免与连接关闭清理形成反向锁顺序。

### 3.2 各 opcode 当前行为

| 消息 | 服务端逻辑 |
|------|-----------|
| `C2M_RequestTeam{TargetId}` | 校验目标在线且与请求方在同一地图；给队长推 `M2C_RequestList{UnitId=请求方, TimeOut=30000}`；响应 20155 `Message="正在申请..."`，打开申请方原生状态框 |
| `C2M_InviteTeam{TargetId}` | 校验目标在线、双方同图且未处于冲突队伍；给目标推 `M2C_InviteList{UnitId=自己, TimeOut=30000}`；响应 20157 `Message="正在邀请..."`，打开邀请方原生状态框 |
| `C2M_HandleTeam{HandleInfo{Id, Bool}, IsRequest}` | Bool=false → 给原发起方推 20262“对方已拒绝”；Bool=true → 完成入队并向所有成员推完整 20162，再给原发起方推 20262“对方已同意”；20262 会复用并改写原状态框 |
| `C2M_TransferTeamLeader{UnitId}` | 仅队长：改 leaderID → 全队推 20162 |
| `C2M_QuitTeam{}` | 移除自己；若自己是队长 → 转让给最早成员或解散；向剩余成员推 20162；给自己推 20162（空队 LeaderId=自己 或单独处理） |
| `C2M_KickoutTeam{TargetId}` | 仅队长：移除 TargetId → 全队推 20162 |
| `C2M_SelectTeamMember{Id}` | 校验 Id 是自己队员并记录战斗内友方目标 |

### 3.3 关键点

- **M2C_TeamMember 必须全量**（UnitIds 含全部成员，客户端 Clear 后重建）；
- 进游戏时也推一次（自建服当前在 `C2M_GetStateReback(20030)` 后推单人队伍，
  `LeaderId=玩家、UnitIds=[玩家]`——这是 ClickTarget 不 NRE 的前提，已实现）；
- 20158/20159 的 `UnitId` 客户端要求该单位**已存在于 UnitComponent**（Handler 里
  `Get(UnitId)` 失败会 Log.Error 丢弃），所以推 20158/20159 前要确保目标场景已有
  对方单位（同地图组队场景天然满足；跨图时对方看不到请求条）；
- 超时：客户端按 `TimeOut*0.001` 秒自动清除请求条（TweenValue 倒计时），服务器也要
  清理 requests，超时后 HandleTeam 视为无效；
- 队伍锁内不进行 `findChannelByPlayerID` 或网络写入；变更时先复制成员快照，解锁后向每个在线成员
  推送相同的全量 20162；
- 断线按玩家 ID 清理队伍，不依赖未加锁读取会话的旧 `teamID`。

## 4. 验证要点

真实 TCP 双连接 `server-mysql/test/verify_team.py` 当前覆盖：
1. A 组队后（LeaderId=A, UnitIds=[A]），B 发 `20154 C2M_RequestTeam{TargetId=A}`；
   A 收到 20158 `M2C_RequestList{UnitId=B, TimeOut}`；B 收到 20155“正在申请...”。
2. A 发 `20160 C2M_HandleTeam{HandleInfo{Id=B, Bool=true}, IsRequest=true}`（同意申请；
   B 发的是申请入队 type=1 → IsRequest=true）；
   A 与 B **都**收到 20162 `M2C_TeamMember{LeaderId=A, UnitIds=[A,B]}`，B 同时收到
   20262“对方已同意”，原状态框文字被替换。
3. B 发 `20165 QuitTeam` → A 收到 20162 `UnitIds=[A]`；B 收到空队。
4. A 邀请 B：20157 返回“正在邀请...”，B 收到 20159 `M2C_InviteList{UnitId=A}`；
   B 回 `20160 C2M_HandleTeam{HandleInfo{Id=A, Bool=true}, IsRequest=false}`（被邀请 type=0
   → IsRequest=false，同意后 B 加入 A 的队伍）→ 全队同步。
5. 转让队长：A 发 `20163 TransferTeamLeader{UnitId=B}` → 全队 20162 `LeaderId=B`。
6. 客户端实机：点击野外玩家 → 菜单"邀请组队"；对方右上角弹"组队邀请"条 →
   同意 → 双方头像栏显示 2 人；点击队员头像 → 踢出/转让/退出。

2026-08-17 回归结果为 19 项全部通过；另有 `social_multiplayer_test.go` 校验跨图邀请被拒绝、同图邀请
双方收到完全一致的 `M2C_TeamMember`。

### 5.1 当前多人 BOSS 战斗

- 客户端战斗阵型只有五个玩家位，且 HP 难度表正好为五档 `0/0.5/0.96/1.37/1.72`；服务端因此把
  队伍上限固定为 5。邀请、申请及最终接受三个入口都会检查满队，不能产生客户端无法摆放的第六人。
- 队伍进入普通/家族 BOSS 时，在线同图成员加入同一个 `partyBattle`，所有人的 battleState 引用同一组
  `monsterUnit`；怪物 `UnitId/MonsterId/HP/alive` 只有一份权威状态，不会各打各的或出现两套模型。
- 每个成员仍保留独立的玩家 UnitId、HP、MP、CD 和自动战斗状态；共享效果运行时可以正确处理队友治疗、
  护盾和增益，不会把队友当成怪物。
- 展示 BOSS 前，每个客户端先收到同一份 `M2C_TeamMember`，再收到全部参战玩家 1001-1004 Numeric，
  最后才发送 BOSS 展示包，满足客户端 handler 对 TeamComponent 和 NumericComponent 的前置要求。
- 任一成员施放技能，`M2C_PlaySkill`、伤害 `M2C_BattleSkillRet`、绝对 HP `M2C_SyncUnitAttribute`、
  怪物死亡和最终胜负都会发给所有仍在战斗中的队员。单个成员退出只摘除该成员及其临时效果；剩余队员
  可以继续。整场结算会清除所有成员的 battleState。
- `server-mysql/test/verify_multiplayer.py` 通过真实 TCP 建立两个新账号、邀请组队、共同进入海滩 BOSS 层，由第二名队员
  出手，验证两端的怪物列表、技能、伤害、绝对血量和退出 `BattleEnd` 完全一致。

### 5.2 试炼之地是个人副本

- `CopyConfig 10004 TrialCopyBattle` 明确为 `CanTeam=false`。客户端 `StartTrialCopyFightEvent` 只读取
  `UnitComponent.MyUnit` 布置玩家阵位，不遍历 `TeamComponent`，与主线和 BOSS 的多人阵型逻辑不同。
- 队伍成员进入相同试炼层时仍属于不同的个人实例：互相不可见、各自创建怪物 UnitId 和 battleState，
  怪物 HP 不按队伍人数放大；任一人的胜负、奖励、最高层记录和换层都不影响其他成员。
- 队长点击试炼入口时只移动队长本人。进入或离开试炼后，客户端队伍快照按当前可见实例重建，避免
  `TeamComponent` 引用已经离开当前场景的 Unit；真实队伍关系仍保留，回到同一公共场景后恢复显示。
